# Skill: Bug Finder（コード能動スキャン → 潜在バグ発見）

> **バグは報告を待たず、コードの中に潜んでいる — 先に見つけ、先に手を打て**

## Instructions

### ワークフロー内の位置

各 Step の完了時に **review スキル** による Review Gate を通過してから次の Step に進む。
Gate を通過できなかった場合は、該当 Step に戻って修正する。
これにより、**誤った前提・見落とし・偽陽性をスキャン途中で排除**し、最終レポートの信頼性を担保する。

```
リポジトリ / ディレクトリ / ファイル（コードパス指定）
  ↓
[bug-finder]
  ├─ Step 1: スキャン対象の定義とスコープ確定
  │   └─ 📋 Review Gate 1（スコープ定義の完全性・適切性レビュー）
  ├─ Step 2: コードベースの構造把握と高リスクゾーン特定
  │   └─ 📋 Review Gate 2（構造把握の網羅性・優先順位の妥当性レビュー）
  ├─ Step 3: 静的型・Null 安全性スキャン
  │   └─ 📋 Review Gate 3（Null/型バグ候補の証拠・網羅性レビュー）
  ├─ Step 4: ロジック・制御フロー分析
  │   └─ 📋 Review Gate 4（ロジックバグ候補の条件・整合性レビュー）
  ├─ Step 5: 非同期・並行処理スキャン
  │   └─ 📋 Review Gate 5（競合状態・リソースリーク証拠レビュー）
  ├─ Step 6: セキュリティ・脆弱性スキャン
  │   └─ 📋 Review Gate 6（セキュリティ欠陥の証拠・OWASP 網羅性レビュー）
  └─ Step 7: 発見結果の分類・優先度付け・レポート出力
      └─ 📋 Review Gate 7（最終レポートの総合品質レビュー）
  ↓
バグ発見レポート（重大度別 / ファイル:行番号付き / 修正方向示唆）
  ↓
bug-triage-fix（個別バグの根本調査・修正に引き継ぎ）
```

### 入力

| 入力 | 説明 | 例 |
|:---|:---|:---|
| スキャン対象パス | リポジトリルート、ディレクトリ、またはファイルパス | `./src/`, `./api/users.py`, リポジトリ全体 |
| フォーカスカテゴリ（任意） | 特定のバグカテゴリを優先する | `security`, `null-safety`, `concurrency` |
| 除外パス（任意） | スキャン対象から除外するパス | `node_modules/`, `*.test.ts`, `__pycache__/` |
| 言語（任意） | 対象言語が明示される場合 | `TypeScript`, `Python`, `Go` |

### 出力

| 出力 | 形式 | 説明 |
|:---|:---|:---|
| バグ発見レポート | Markdown | 重大度別・カテゴリ別の発見バグ一覧（ファイル:行番号付き） |
| スキャンサマリー | テーブル | Critical/High/Medium/Low の件数と優先対応推奨 |
| 修正方向示唆 | 箇条書き | 各バグに対する短い修正アドバイス（bug-triage-fix への引き継ぎ用） |

## Step 1: スキャン対象の定義とスコープ確定

スキャン範囲を明確にし、重要ファイルの見逃しとノイズの両方を防ぐ。**スコープが曖昧なままスキャンすると、致命的な見落としや膨大な偽陽性が発生する**。

### 1a. 対象パスの特定と言語検出

| 確認項目 | 判断基準 |
|:---|:---|
| パスの存在確認 | 存在しない場合はユーザーに再確認 |
| 対象タイプ判定 | ファイル / ディレクトリ / リポジトリルートでスキャン戦略を変える |
| 言語自動検出 | 拡張子・設定ファイル（package.json, pyproject.toml 等）で言語を特定 |
| ファイル数・規模 | 50 ファイル以下: 全件精査 / 50〜100: 高リスク優先 / 100 超: 差分+コアに絞る |

### 1b. 除外スコープの設定

以下のパスは原則スキャン対象外（ユーザー指定で変更可）:

```
デフォルト除外:
- node_modules/, vendor/, .venv/, __pycache__/
- *.test.ts, *.spec.py, *_test.go（テストコード）
- *.generated.ts, *.pb.go（生成コード）
- dist/, build/, .next/（ビルド成果物）
```

**チェックリスト**:
- [ ] スキャン対象パスを特定し、存在を確認した
- [ ] 言語を特定した（複数言語の場合はすべて列挙）
- [ ] ファイル数・規模を把握し、スキャン戦略を決定した
- [ ] 除外スコープを設定した
- [ ] フォーカスカテゴリがある場合は記録した

### 📋 Review Gate 1: スコープ定義の完全性・適切性レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Step 2 に進む。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| スコープの網羅性 | A-1（要件カバレッジ） | ユーザー指定の対象（リポジトリ/ディレクトリ/ファイル）が漏れなくスキャン対象に含まれているか |
| 規模見積もりの妥当性 | A-3（数値妥当性） | ファイル数・スキャン戦略の判断根拠が適切か。過小評価（見落とし）や過大評価（ノイズ）がないか |
| 機密ファイルの配慮 | B-4（プライバシー） | `.env`, シークレット設定ファイルをスキャンする場合、機密情報をレポートに含めない方針が確認されているか |

**通過条件**: Critical / Major 指摘がゼロ。Minor 指摘は記録して続行可。

**不合格時**: 指摘に基づきスコープを修正し、Step 1a から再確認する。

---

## Step 2: コードベースの構造把握と高リスクゾーン特定

コードの全体像を把握し、**バグが潜みやすい箇所**（認証・データアクセス・非同期処理・外部連携）を優先スキャン対象として特定する。

### 2a. ファイル構造の探索

| 確認対象 | 目的 |
|:---|:---|
| エントリポイント | リクエストが最初に触れるコード（main.py, index.ts 等） |
| ビジネスロジック集中箇所 | services/, domain/, handlers/ 等 |
| データアクセス層 | DB クエリ、ORM モデル、リポジトリパターン |
| 認証・認可コード | auth/, middleware/, guards/ 等 |
| 外部 API 連携コード | clients/, integrations/ 等 |
| 設定・シークレット管理 | config/, env/ — ハードコード確認 |

### 2b. 高リスクファイルの特定

| 高リスク指標 | 判断基準 |
|:---|:---|
| LOC が多い | 500 行超のファイル |
| 循環複雑度が高そう | 深いネスト、多数の if/switch |
| 最近変更された | git log で直近 2 週間以内の変更 |
| エラーハンドリングが薄い | try-catch が少ない / エラーを握りつぶしている |

**チェックリスト**:
- [ ] ファイル構造を把握し、エントリポイントを特定した
- [ ] 高リスクファイル（LOC・複雑度・最近変更）を特定した
- [ ] データアクセス層・認証コードを確認リストに挙げた
- [ ] 設定ファイル（.env, config.yaml 等）のシークレット有無を確認した
- [ ] スキャン優先順位を決定した（高リスク順に並べた）

### 📋 Review Gate 2: 構造把握の網羅性・優先順位の妥当性レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Step 3 に進む。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| 高リスクゾーンの網羅性 | A-1（要件カバレッジ） | 認証・データアクセス・外部API連携・非同期処理の主要コードが高リスクリストに含まれているか |
| 優先順位の整合性 | A-2（章間整合性） | 高リスクと判断した根拠（LOC・変更履歴・複雑度）がスキャン優先順位と一致しているか |
| 境界系の考慮 | B-3（境界値攻撃） | 設定ファイル・環境変数・シークレット管理の箇所がリストに含まれているか |

**通過条件**: Critical / Major 指摘がゼロ。特に「認証コードが高リスクリストにない」は Critical 扱い。

**不合格時**: 指摘に基づき高リスクリストを補完し、Step 2a から再確認する。

## Step 3: 静的型・Null 安全性スキャン

**最も発生頻度が高いバグカテゴリ** — Null/undefined 参照、型の誤用、未初期化変数を検出する。

### 3a. Null / undefined 参照チェック

| バグパターン | 検出方法 | 言語別注意点 |
|:---|:---|:---|
| null / undefined への直接アクセス | `.property` / `[index]` の前に null チェックがない | TypeScript: `strictNullChecks` オフ時に多発 |
| オプショナルチェーンの欠落 | `obj.a.b.c` のような深いアクセス | JS/TS では `?.` で保護すべき |
| 配列の境界外アクセス | `array[array.length]` や負インデックス | Go: slice 境界チェック |
| Null を返す可能性のある関数の戻り値未チェック | `find()` / `querySelector()` / DB クエリ結果 | どの言語でも多発 |

### 3b. 型変換・型強制バグ

| バグパターン | 例（悪い） | 例（良い） |
|:---|:---|:---|
| 暗黙の型強制 | `"3" + 5` → `"35"` (JS) | `Number("3") + 5` |
| 基数未指定の parseInt | `parseInt("08")` → `0` | `parseInt("08", 10)` |
| 浮動小数点の金額計算 | `0.1 + 0.2 !== 0.3` | `Decimal` / 整数演算を使用 |

**チェックリスト**:
- [ ] Null/undefined 参照の可能性がある箇所を特定した
- [ ] 型変換・型強制バグを確認した
- [ ] 境界外アクセスの可能性を確認した
- [ ] 未使用変数・到達不能コードを記録した

### 📋 Review Gate 3: Null / 型バグ候補の証拠・網羅性レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Step 4 に進む。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| 発見候補の証拠の十分性 | A-3（数値・データの妥当性） | 各バグ候補に「どのコードパスで、どの値のときに発現するか」の具体的証拠が記録されているか |
| 境界値パターンの網羅性 | B-3（境界値攻撃） | null/undefined・空配列・空文字・最大値・負数といった境界パターンが確認されているか |
| 偽陽性の除外 | A-2（章間整合性） | 「バグ候補」と「言語仕様上の正常な挙動」が混同されていないか |

**通過条件**: Critical / Major 指摘がゼロ。「証拠なしに候補として列挙されている」は Major 扱い。

**不合格時**: 証拠不足の候補を再調査するか偽陽性として除外し、Step 3a から再スキャンする。

## Step 4: ロジック・制御フロー分析

**症状が出にくいが影響が大きいバグ** — 「動いているように見えて、特定条件で破綻する」パターンを検出する。

### 4a. 条件分岐のバグ

| バグパターン | 例 | 検出のポイント |
|:---|:---|:---|
| **オフバイワン** | `for (i = 0; i <= arr.length; i++)` | ループ境界条件を精査 |
| **全分岐を網羅しない switch** | default ケース欠如でサイレント失敗 | switch の default 有無を確認 |
| **短絡評価の誤用** | `obj && obj.process()` で副作用あり | `&&` で呼び出す関数に副作用がないか |
| **論理演算子の優先度** | `a \|\| b && c` が `a \|\| (b && c)` として評価 | 括弧で意図を明示すべき |

### 4b. 例外・戻り値の扱いミス

```
発見すべきパターン:
- 例外を catch して何もしない（空の catch ブロック）
- エラーを握りつぶして false / null を返す
- async 関数で await を忘れて Promise オブジェクトを返してしまう
- forEach + async/await（forEach は await を待たない）
```

**チェックリスト**:
- [ ] オフバイワンの可能性があるループ境界を確認した
- [ ] switch/if-else の全分岐を網羅しているか確認した
- [ ] 空の catch ブロック・エラーの握りつぶしを確認した
- [ ] async/await の欠落・Promise の未処理を確認した（JS/TS）

### 📋 Review Gate 4: ロジックバグ候補の条件・整合性レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Step 5 に進む。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| バグ発現条件の明確さ | A-2（章間整合性） | 各候補に「どの条件が満たされたときに発現するか」が一貫して記述されているか |
| エッジケースの網羅 | B-3（境界値攻撃） | ループ境界・switch の default・空配列・undefined 引数といったエッジケースが検証されているか |
| 偽陽性の除外 | A-1（要件カバレッジ） | 「意図的なサイレント失敗」（設計上 noop の catch 等）が誤ってバグ候補に含まれていないか |

**通過条件**: Critical / Major 指摘がゼロ。

**不合格時**: 発現条件が不明確な候補を再調査し、Step 4a または 4b に戻る。

## Step 5: 非同期・並行処理スキャン

**最も発見・修正が難しいバグカテゴリ** — 間欠的に発生し、本番環境のみで顕在化することが多い。

### 5a. 競合状態（Race Condition）

| パターン | 症状 | 検出ポイント |
|:---|:---|:---|
| **Check-Then-Act** | ファイル存在確認後に別プロセスが削除 | `if (exists) { use() }` のペア |
| **Read-Modify-Write** | 複数スレッドが同じカウンターを更新 | 共有変数への非アトミックな更新 |
| **DB 更新の競合** | 同時リクエストが同一レコードを更新 | トランザクション境界・ロック不足 |

### 5b. リソースリーク

| リソース | リーク原因 | 確認箇所 |
|:---|:---|:---|
| **DB コネクション** | finally ブロックで close しない | コネクション取得後の finally / with |
| **ファイルハンドル** | open 後に close しない | open() が with ステートメント外 |
| **タイマー / インターバル** | clearInterval / clearTimeout されない | setInterval が clearInterval とペアか |
| **イベントリスナー** | removeEventListener されない | addEventListener の cleanup 処理 |

**チェックリスト**:
- [ ] 共有状態への並行アクセスを確認した
- [ ] DB/ファイル/ネットワークリソースの close/release を確認した
- [ ] Promise チェーンに catch が付いているか確認した
- [ ] タイマー・イベントリスナーの cleanup を確認した

### 📋 Review Gate 5: 競合状態・リソースリーク証拠レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Step 6 に進む。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| 競合状態の証拠の具体性 | A-3（数値妥当性） | 競合状態の候補に「どのスレッド/リクエストが、どの順序で共有資源にアクセスするか」が記述されているか |
| リソースリークの発現確率 | B-5（Performance & Scalability） | リソースリークがパフォーマンス・安定性に与える影響規模が評価されているか |
| 境界系の考慮 | B-3（境界値攻撃） | タイムアウト・キャンセル・接続切断といった異常系パスでもリソースが解放されるか確認したか |

**通過条件**: Critical / Major 指摘がゼロ。「競合状態の証拠が推測だけ」は Major 扱い。

**不合格時**: 証拠不足の候補を再調査し、Step 5a または 5b に戻る。

## Step 6: セキュリティ・脆弱性スキャン

**発見時の影響が最大** — セキュリティバグは攻撃者に悪用されるまで潜伏する。

### 6a. インジェクション脆弱性

| 種別 | バグパターン | 検出方法 |
|:---|:---|:---|
| **SQL インジェクション** | ユーザー入力を文字列結合でクエリに組み込む | `"SELECT ... WHERE id=" + userId` を探す |
| **コマンドインジェクション** | ユーザー入力を shell 実行に渡す | `exec(cmd + userInput)` / `subprocess.run(shell=True)` |
| **XSS** | ユーザー入力を HTML に直接埋め込む | `innerHTML = userInput` / テンプレートの raw 出力 |
| **パスインジェクション** | ユーザー入力でファイルパスを構築 | `os.path.join(base, userInput)` のバリデーションなし |

### 6b. 認証・認可の欠陥と機密情報の露出

```
検出すべきパターン:
- 認証ミドルウェアの適用漏れ
- JWT/セッショントークンの検証が不十分
- パスワードの平文保存・弱いハッシュ（MD5/SHA1）
- ハードコードされた認証情報・API キー
- ログへの機密情報（PII・パスワード）出力
```

詳細は [security-checklist.md](references/security-checklist.md)（OWASP Top 10 対応）参照。

**チェックリスト**:
- [ ] ユーザー入力がクエリ/コマンド/HTML に渡る箇所を確認した
- [ ] 認証・認可ミドルウェアの適用漏れを確認した
- [ ] ハードコードされた認証情報を確認した
- [ ] ログ出力に機密情報が含まれないか確認した
- [ ] [security-checklist.md](references/security-checklist.md) の OWASP Top 10 全項目を確認した

### 📋 Review Gate 6: セキュリティ欠陥の証拠・OWASP 網羅性レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Step 7 に進む。**

このゲートは **Critical バグが最も集中するフェーズ** であり、最も厳密なレビューが求められる。

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| OWASP 網羅性 | A-1（要件カバレッジ） | [security-checklist.md](references/security-checklist.md) の OWASP Top 10 全項目を確認したか。スキップした項目の理由が明記されているか |
| 証拠の十分性 | B-1（Semantic Drift） | 各セキュリティ候補に「攻撃可能なコードパス」「入力値の例」が具体的に記録されているか |
| 機密情報の保護 | B-4（プライバシー） | スキャン結果レポートに API キー・パスワード・PII がそのまま記録されていないか（マスク処理済みか） |
| 依存パッケージの確認 | B-5（Performance & Scalability） | package.json / requirements.txt の既知脆弱性を確認したか |

**通過条件**: B-4（機密情報保護）は必須通過。A-1 の OWASP 未確認項目がある場合は Major 扱い。

**不合格時**:
- 証拠不足 → Step 6a / 6b に戻り追加調査
- 機密情報漏洩 → レポートから即座に除去・マスク処理してから再レビュー

## Step 7: 発見結果の分類・優先度付け・レポート出力

検出したバグを整理し、**何から対応すべきか**が一目でわかるレポートを出力する。

### 7a. 重大度の判定

| 重大度 | 基準 | 対応期限 |
|:---|:---|:---|
| **Critical** | データ損失・認証突破・リモートコード実行・本番停止につながる | 即座（当日） |
| **High** | セキュリティリスク・主要機能の破綻・データ汚染 | 今スプリント中 |
| **Medium** | 特定条件下での障害・パフォーマンス劣化・エラーの握りつぶし | 次スプリント |
| **Low** | 潜在的な問題・デッドコード・型の不整合（動作はする） | バックログ |

詳細な判定マトリクスは [severity-matrix.md](references/severity-matrix.md) 参照。

### 7b. レポートの構成と同一パターンのグルーピング

```markdown
## バグ発見レポート — スキャンサマリー
- 対象: <パス> / 言語: <言語> / スキャン日時: YYYY-MM-DD

| 重大度 | 件数 |
| Critical | N |
| High | N |
| Medium | N |
| Low | N |

### Critical バグ
#### BUG-001: <タイトル>
- ファイル: `src/xxx.ts:42`
- カテゴリ: SQL インジェクション
- 発現条件: <どの入力値のときに発現するか>
- 証拠: `const q = "SELECT * WHERE id=" + req.params.id`
- 修正方向: Prepared Statement に変更
- 引き継ぎ: bug-triage-fix で根本調査・修正を実施

### 推奨アクション
1. Critical バグを即座に bug-triage-fix で対応
2. High バグを今スプリントのバックログに追加
```

同一パターンが複数箇所で見つかった場合はグルーピングして報告する（例: 「Null ガード欠如（8 箇所）— src/users.ts L12, L45 ...」）。

**チェックリスト**:
- [ ] 発見したすべてのバグに重大度を付与した
- [ ] バグをカテゴリ別・重大度別に整理した
- [ ] 同一パターンのバグをグルーピングした
- [ ] 各バグにファイル名と行番号を記載した
- [ ] bug-triage-fix への引き継ぎ対象を明示した
- [ ] レポートに機密情報（認証情報・PII）が含まれていないか確認した

### 📋 Review Gate 7: 最終レポートの総合品質レビュー

**review スキルに以下の観点で最終レビューを依頼し、通過してからレポートを納品する。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| レポートの完全性 | A-1（要件カバレッジ） | スキャン対象の全ファイルが確認済みか。スキップしたファイルの理由が記録されているか |
| 章間の整合性 | A-2（章間整合性） | 重大度判定がStep 3〜6の発見根拠と一貫しているか。根拠なく重大度が変わっていないか |
| 数値・判定の妥当性 | A-3（数値妥当性） | 重大度の判定基準（影響範囲・発現確率）が適切か。過剰に高い/低い評価をしていないか |
| 可読性と実用性 | A-4（可読性と説得力） | ファイル名・行番号・コードスニペット・発現条件が揃っており、開発者が即座に対応できる情報か |
| PII 保護 | B-4（プライバシー） | 全発見エントリに機密情報（APIキー・パスワード・PII）が含まれていないか |

**通過条件**: ドキュメント基準 A-1〜A-4 の全チェックリストをパス。B-4 は必須通過。Critical / Major 指摘がゼロ。

**不合格時**: 指摘内容に応じて該当 Step に戻り修正。B-4 不合格（機密情報漏洩）は最優先で対処。

## Troubleshooting

| 問題 | 原因 | 解決策 |
|:---|:---|:---|
| Review Gate で「証拠が不十分」と繰り返し指摘される | 発現条件を曖昧に記録している | 「どのファイル:行番号で、どの入力値のとき、何が起きるか」を必ず記録してから Gate に進む |
| リポジトリが大きすぎてスキャンが進まない | ファイル数が多い | Step 1 で git diff を使い変更差分のみを優先対象にする |
| セキュリティバグが見つからない | Step 6 の観点が不足 | [security-checklist.md](references/security-checklist.md) の OWASP Top 10 を参照し全項目を確認する |
| 同じ候補が Gate 3〜6 で偽陽性として除外される | パターンスキャンの網が広すぎる | 除外した根拠を明記して累積し、Step 7 の「スキャン精度」として報告に含める |
| 競合状態かどうか判断できない | 非同期の実行フローが複雑 | 「複数の実行コンテキストが共有変数にアクセスする経路があるか」を一点確認し、あれば候補として記録 |
| Gate 6 で PII 漏洩を指摘されたが何が PII か判断できない | PII の定義が不明確 | 氏名・メールアドレス・電話番号・APIキー・パスワード・トークン文字列をすべて PII とみなしてマスクする |
| 発見バグ数が多すぎてレポートが読みにくい | 重大度判定が甘い | [severity-matrix.md](references/severity-matrix.md) の基準を再適用。Medium/Low は推奨対応セクションにまとめる |
| テストコードにも多数バグが見つかる | デフォルト除外に含まれていない | Step 1c のデフォルト除外を確認。ユーザーが「テストも含めて」と指示した場合のみ対象にする |
| 生成コード（OpenAPI 等）のバグが大量に出る | 自動生成コードは意図的な実装と異なる | Step 1c で生成コードを除外対象に追加し、人手コードのみをスキャンする |
| bug-triage-fix との連携タイミングが不明 | スキル境界が曖昧 | bug-finder は「発見・リスト化」まで。個別バグの「再現・修正」は bug-triage-fix に委譲する |
| Gate 通過後に新たなバグが見つかった場合の扱い | 後続 Step のスキャン中に前 Step の対象が広がる | 新発見は現在の Step の候補リストに追加し、現在の Gate でまとめてレビューする |

## Related Skills

| スキル | 関係 | 説明 |
|:---|:---|:---|
| **bug-triage-fix** | 後工程（委譲先） | bug-finder で発見した Critical/High バグを bug-triage-fix に引き継ぎ、再現確認 → 仮説ツリー → 最小変更修正 → 回帰テスト追加まで対応する。bug-finder の Step 7 出力が bug-triage-fix の Step 3 入力となる |
| **review** | 各フェーズのゲートキーパー | 全 7 Step の完了時に Review Gate として起動し、スコープ・証拠・整合性・PII 保護を検証する。Gate 1〜2: A-1〜A-3、Gate 3〜5: A-2〜A-3 + B-3/B-5、Gate 6: A-1 + B-1/B-4、Gate 7: A-1〜A-4 + B-4 |
| **test** | 協調 | bug-finder でバグを発見した後、再発防止テストを書く場合は test スキルを活用する。特に Gate 3〜5 で発見した境界値バグは Khorikov の 4 本柱に基づくテストケース化が有効 |
| **implementation-flow** | 上流（品質ゲート） | implementation-flow の実装フェーズ完了後に bug-finder を起動し、リリース前の最終品質ゲートとして潜在バグを先行検出する。「実装が終わったらバグスキャンして」という発話でシームレスに連携できる |
