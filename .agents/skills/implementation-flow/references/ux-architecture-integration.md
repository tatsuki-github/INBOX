## Laws of UX 適用マトリクス

Phase 2 で適用する UX 法則をコンポーネント単位で対応付ける。機能に関連する 2-4 法則を選択し、設計判断に紐付ける。

### 法則 → UI コンポーネント対応表

| 法則 | 概要 | 適用場面 | UI への反映 |
|:-----|:-----|:---------|:-----------|
| **Jakob's Law** | ユーザーは大半の時間を他サイトで過ごす | ナビゲーション、フォーム、検索 | 業界標準の UI パターンに準拠する |
| **Fitts's Law** | ターゲットまでの時間は距離とサイズに依存 | CTA ボタン、タッチ操作 | 重要なボタンは大きく近くに配置（44px 以上） |
| **Hick's Law** | 選択肢が増えると決定時間が増加 | メニュー、フィルタ、設定 | 選択肢を 5-7 個以内に制限、段階的開示 |
| **Miller's Law** | 短期記憶は 7±2 チャンク | フォーム、データ表示 | 情報を 5-9 のグループにチャンキング |
| **Postel's Law** | 出力は厳密に、入力は寛容に | フォームバリデーション | 柔軟な入力受付 + 明確なエラー表示 |
| **Peak-End Rule** | 体験はピークと終了時の印象で記憶される | タスク完了、オンボーディング | 成功時の演出、完了画面の品質向上 |
| **Von Restorff** | 異質なものが記憶に残る | 通知、バッジ、CTA | 重要要素を視覚的に際立たせる |
| **Tesler's Law** | どのシステムにも削減不能な複雑さがある | ウィザード、設定 | 複雑さをシステム側で引き受ける |
| **Doherty Threshold** | 応答 400ms 以内で生産性が向上 | 全インタラクション | 高速応答 + 遅延時のフィードバック |
| **Aesthetic-Usability** | 美しいデザインはより使いやすいと知覚される | 全体の視覚品質 | 視覚的洗練度を高める |

### 機能タイプ別の法則選択ガイド

| 機能タイプ | 推奨する法則（2-4 個） | 理由 |
|:-----------|:-----------------------|:-----|
| **データ表示系**（ダッシュボード、一覧） | Miller's Law, Von Restorff, Doherty | 情報量の最適化と重要指標の強調 |
| **フォーム入力系**（登録、編集） | Postel's Law, Miller's Law, Peak-End | 入力の柔軟性と完了時の満足感 |
| **検索・フィルタ系** | Hick's Law, Jakob's Law, Doherty | 選択肢の最適化と標準 UI パターン |
| **通知・フィードバック系** | Von Restorff, Doherty, Peak-End | 注意喚起と応答性 |
| **ナビゲーション系** | Jakob's Law, Fitts's Law, Hick's Law | 標準パターン + 操作効率 |
| **ウィザード・ステップ系** | Tesler's Law, Miller's Law, Peak-End | 複雑さの吸収とステップ分割 |

## 感情設計テンプレート

Phase 2b で使用する。ユーザーフローの各ステップに感情スコア（-3 ～ +3）を付与し、
Peak-End Rule に基づいてポジティブピークとネガティブピーク軽減を設計する。

| ステップ | 操作 | 感情スコア | 設計意図 |
|:---------|:-----|:-----------|:---------|
| 1. エントリー | [操作] | 0（ニュートラル） | 低摩擦で開始 |
| 2. メイン操作 | [操作] | -1 ～ +1 | コア機能の使用感 |
| 3. ポジティブピーク | [操作] | **+2 ～ +3** | **意図的な演出（アニメーション、成功表示）** |
| 4. 完了 | [確認] | **+1 ～ +2** | **End を良い印象で終える** |
| E. エラー発生 | [エラー] | -2 | **軽減策**: 明確なメッセージ + 復旧パス |

## アーキテクチャ特性導出マトリクス

Phase 3a で使用する。Phase 1-2 の成果から、必要なアーキテクチャ特性を導出する。

### UX 要件 → アーキテクチャ特性

| UX 要件（Phase 2 由来） | 導出されるアーキテクチャ特性 | 判定基準 |
|:-------------------------|:---------------------------|:---------|
| Doherty Threshold 準拠（< 400ms） | **応答性（Responsiveness）** | API レスポンス + レンダリング合計 < 400ms |
| エラーリカバリパス | **耐障害性（Fault Tolerance）** | エラー時にアプリが停止しない |
| リアルタイムデータ表示 | **弾力性（Elasticity）** | 同時アクセス変動への対応 |
| オフライン対応 | **可用性（Availability）** | ネットワーク断でも基本操作可能 |
| 個人情報の取り扱い | **セキュリティ（Security）** | 暗号化、アクセス制御、監査ログ |
| 将来の機能拡張 | **拡張性（Extensibility）** | Open-Closed 原則準拠の設計 |
| 複数チームでの開発 | **モジュール性（Modularity）** | Bounded Context による分離 |

### 機能要件 → アーキテクチャ特性

| 機能要件（Phase 1 由来） | 導出されるアーキテクチャ特性 | 優先度の目安 |
|:-------------------------|:---------------------------|:-------------|
| CRUD 操作 | **保守性（Maintainability）** | Must |
| データ集計・レポート | **パフォーマンス（Performance）** | Should |
| ファイルアップロード | **信頼性（Reliability）** | Must |
| 外部 API 連携 | **相互運用性（Interoperability）** | Must |
| 多言語対応 | **国際化（Internationalization）** | Should |

### 特性の優先順位付け

抽出した特性を 7 個以内に絞り、Must / Should / Could で優先順位を付ける。

```
「全てはトレードオフ」— 特性の追加はコストを伴う。
7 個を超えたら、下位の特性を意識的に切り捨て、ADR で理由を記録する。
```

## コンポーネント設計テンプレート（3 層構造）

Phase 3b で使用する。機能を 3 層に分離し、各層の責務を明確にする。

```
[機能名]/
├── UI Layer（表示専任）
│   ├── [機能名]Page.tsx        ← ルーティング + レイアウト
│   ├── [機能名]Container.tsx   ← 状態管理接続 + 条件分岐
│   └── [要素名].tsx            ← Pure Presentational（Props のみ）
│
├── Business Logic（処理専任）
│   ├── types.ts                 ← ドメイン型（タグ付きユニオン）
│   ├── use[機能名].ts           ← カスタムフック（状態 + 副作用）
│   ├── [機能名]Validator.ts     ← バリデーションロジック
│   └── [機能名]Transformer.ts   ← DTO → ドメインモデル変換
│
├── Data Access（通信専任）
│   ├── [機能名]Service.ts       ← API クライアント
│   └── [機能名]Cache.ts         ← キャッシュ戦略（SWR / React Query）
│
└── Shared（共有）
    ├── constants.ts              ← マジックナンバー排除
    └── utils.ts                  ← 純粋関数ユーティリティ
```

**依存方向ルール**: UI → Business Logic → Data Access（逆方向の依存禁止）

## ADR 作成ガイドライン

Phase 3c で作成する ADR の品質基準。

| 要素 | 品質基準 | NG 例 |
|:-----|:---------|:------|
| **タイトル** | 判断内容が一目でわかる | 「設計について」（抽象的すぎ） |
| **コンテキスト** | 判断が必要になった具体的な状況 | 背景説明なしで突然選択肢 |
| **選択肢** | 最低 2 つ、それぞれメリ・デメを列挙 | 採用案のメリットしか書かない |
| **判断理由** | 「なぜ A を選んだか」だけでなく「なぜ B を選ばなかったか」 | 「A が良さそうだから」 |
| **影響** | この判断による制約・後続の設計影響 | 影響記述なし |
