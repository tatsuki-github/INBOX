# Skill: Critical Reviewer (Review)

> **Trust, but Verify — 信頼せよ、されど検証せよ**

## Instructions

### ワークフロー内の位置

```
distill → 成果物作成 → [review] ── Approved ──→ 完了
                          │      ── Rejected ──→ 修正へ戻る
                          ↓
                   仕様に問題発見 → distill に差し戻し
```

### Pre-Flight Check

レビュー開始前に必ず確認:
- `02_notes/` を読み、仕様を完全に理解した
- レビュー対象の成果物を読み、内容の意図を理解した
- `05_decision_log/` を確認し、過去の設計判断を理解した
- 品質基準を確認した
- レビュー対象が「ドキュメント」「技術仕様」「ソースコード」のいずれか判断した

---

## Part A: ドキュメントレビュー基準

### A-1: 要件カバレッジ

要件定義の全項目がドキュメントで漏れなく回答されているか。

**チェックリスト**:
- 全要件（必須・任意）に対応する章が存在するか
- 重要度の高い項目に十分なページが割かれているか
- 「対応可能」と記載した項目の実現方法が具体的に説明されているか
- 未対応の項目がある場合、代替案や段階的対応が明記されているか

### A-2: 章間整合性

ドキュメントの各章が互いに矛盾していないか。

**チェックリスト**:
- スケジュールの工数と開発の機能量が整合しているか
- 目標値とアーキテクチャで実現可能か
- 体制の人員数でスケジュール通りに開発可能か
- 見積金額と内容のスコープが一致しているか
- 用語が全章で統一されているか（glossary.md 準拠）

### A-3: 数値・データの妥当性

**チェックリスト**:
- 数値の前提条件（規模、複雑度、生産性）が明記されているか
- 積算根拠が示されているか
- リスクバッファが計上されているか
- 外部費用が漏れていないか
- ランニングコスト（運用保守費）が積算されているか（該当時）

### A-4: 可読性と説得力

**チェックリスト**:
- 章構成が目的に沿って整理されているか
- 図表が適所に配置され、文章だけの壁がないか
- 「なぜこの内容を選ぶべきか」（差別化ポイント）が明確か
- 専門用語に説明が添えられているか（読者が非専門家の場合）
- 各章の冒頭にサマリーがあり、全体像を把握しやすいか

## Part B: 技術仕様レビュー基準

### B-1: Semantic Drift（仕様との意味的乖離）

実装がnotesの仕様から逸脱していないか。

**チェックリスト**:
- エンティティの属性が仕様通りに実装されているか
- ビジネスルールのロジックが仕様通りに実装されているか
- API仕様のリクエスト/レスポンス形式が一致しているか
- データ型、精度、制約が仕様通りか

**検証方法**: `02_notes/domain-model.md` のエンティティ定義を読み、実装コード（`src/models/` 等）と照合する。

### B-2: Accounting Integrity（会計・数値整合性）

**チェックリスト**:
- 実績と見込の混同が発生していないか（closing_flag の考慮）
- 通貨の精度（浮動小数点型の使用禁止）は正しいか
- 集計ロジックで二重計上していないか
- 丸め処理が統一されているか
- タイムゾーンの考慮漏れがないか

### B-3: Edge Case Attack（境界値攻撃）

**チェックリスト**:
- Null/Undefined でクラッシュしないか
- 境界値（0, -1, MAX_SAFE_INTEGER）で破綻しないか
- 型攻撃（文字列、NaN、Infinity）に耐えるか
- 並行処理での同一リソースアクセスに対応しているか

### B-4: Privacy Violation（プライバシー侵害）

**チェックリスト**:
- ログに機密情報（PII: 氏名、住所、電話番号等）を出力していないか
- エラーメッセージに内部情報を含めていないか
- APIレスポンスに不要な機密情報を含めていないか
- デバッグ用コードが本番環境に残っていないか
- 成果物に機密情報が含まれていないか

### B-5: Performance & Scalability

**チェックリスト**:
- N+1 クエリ問題が発生していないか
- 適切なインデックスが定義されているか
- 大量データ処理でメモリリークしないか
- キャッシュ戦略は適切か
- 非同期処理が適切に利用されているか

### B-6: Test Coverage

**チェックリスト**:
- すべての公開関数に対応するテストがあるか
- 正常系だけでなく、異常系もテストされているか
- エッジケース（null, 0, 負数, 最大値）がテストされているか
- テストカバレッジが80%以上か
- テストが実装の詳細ではなく、振る舞いを検証しているか

各基準の詳細なコード例と指摘パターンは [references/technical-review-examples.md](references/technical-review-examples.md) を参照。

## Decision Criteria

### 指摘のレベル分け

| レベル | 定義 | 対応 |
|:---|:---|:---|
| Critical | データ損失、システム停止、目的達成を阻害する致命的な問題 | 即座に修正必須 |
| Major | ビジネスロジックの誤り、セキュリティリスク、要件漏れ | 修正必須 |
| Minor | 品質問題、パフォーマンス懸念、表現の不統一 | 修正推奨 |
| Info | ベストプラクティスの提案、改善余地 | 参考情報 |

### 承認条件

成果物が完璧であると論理的に証明できない限り、承認を与えてはならない。

**ドキュメント**: A-1〜A-4 の全チェックリストをパス + 機密情報漏洩なし（B-4）

**技術仕様**: B-1〜B-6 の全チェックリストをパス

## Troubleshooting

| 問題 | 原因 | 対処 |
|:---|:---|:---|
| notes が不十分でレビュー不可 | distill フェーズの不足 | `distill` スキルに差し戻して仕様を補完 |
| 評価基準が不明 | 情報不足 | 仮の評価基準を設定し、ADR に記録 |
| 章間矛盾が多すぎる | 複数人が独立に執筆 | 章横断レビュー会議を実施し、用語統一から開始 |
| 技術仕様とドキュメントの乖離 | 仕様更新後の反映漏れ | トレーサビリティマトリクスで差分を特定 |
| テストカバレッジが低い | テスト工数不足 | ビジネスルール起点でテストケースを優先生成 |
