# Skill: Distill（知識蒸留 & 構造化）

> **混沌を秩序に変え、暗黙知を形式知に鋳造する**

## Instructions

### ワークフロー内の位置

```
pdf-convert → [distill] → 成果物作成 → review
                 ↑                           ↓
            01_inbox/ の生データ          05_decision_log/ に記録
```

### 入力

| ソース | パス |
|:---|:---|
| ソース資料（生データ） | `01_inbox/` |
| ドキュメントテンプレート | `shared/schemas/` |
| 品質ゲート | `shared/quality-gates/QUALITY_GATES.md` |
| 既存仕様（更新時） | `02_notes/` |

### 出力

| 成果物 | パス |
|:---|:---|
| 用語集 | `02_notes/glossary.md` |

## Step 1: ソース資料の収集と分析

`01_inbox/` の全資料を精読し、対象ドメインの課題・制約条件・評価基準を抽出する。

**チェックリスト**:
- inbox の全資料を読み込んだか
- 対象ドメインの根本的な課題（Why）を理解できているか
- 評価基準・優先度を把握しているか
- 制約条件（期間、予算、技術要件、法規制）を特定しているか
- 不明点・矛盾点のリストを作成したか

---

## Step 2: 用語集（Glossary）の策定

ソース資料に出現する専門用語を体系化する。`shared/schemas/TEMPLATE-glossary.md` をテンプレートとして使用。

**チェックリスト**:
- ドメイン固有の用語が網羅されているか
- 略語の正式名称が定義されているか
- 同義語・類義語が統一されているか
- 和英対訳が必要な場合、対応が記載されているか
- 技術用語と業務用語の区別が明確か

---

## Step 3: ドメインモデルの構造化

ビジネスドメインを構造化し、主要エンティティを特定する。`shared/schemas/DOMAIN_MODEL_TEMPLATE.md` をテンプレートとして使用。

**チェックリスト**:
- 主要エンティティが特定されているか
- エンティティの属性と制約が明確か
- エンティティ間の関係（1:1, 1:N, N:M）は定義されているか
- 主キー・外部キー・一意制約が定義されているか
- データ型と精度（文字列長、数値精度）が明記されているか
- 法規制に基づく保存期間・削除要件があるか
- 後続の成果物で参照可能な形式になっているか

---

## Step 4: ビジネスルールの抽出

ソース資料からビジネスルール・制約を体系的に抽出する。`shared/schemas/BUSINESS_RULES_TEMPLATE.md` をテンプレートとして使用。

**チェックリスト**:
- すべてのビジネスルールに一意IDが付与されているか
- 各ルールの根拠（ソース資料の該当箇所）が明記されているか
- 例外ケースは記述されているか
- 検証ロジックが擬似コード or 数式で記述されているか
- ルール間の依存関係が明確か
- 後続の成果物で参照可能な形式になっているか

---

## Step 5: 技術仕様の策定（該当案件のみ）

非機能要件、API 仕様、データモデル、技術選定根拠を定義する。

**チェックリスト**:
- パフォーマンス要件（応答時間、スループット、同時接続数）が定義されているか
- セキュリティ要件（認証方式、暗号化、監査ログ）が定義されているか
- 可用性要件（SLA、RPO/RTO、DR 構成）が定義されているか
- API 仕様が OpenAPI 形式またはそれに準ずる形式で記述されているか
- データモデルのパーティション・クラスタリング戦略が定義されているか
- 技術選定の根拠が論理的に説明されているか

---

## Step 6: 仕様の妥当性確認

inbox の原本と notes の蒸留結果を照合し、情報の欠落や誤解がないか検証する。

**チェックリスト**:
- inbox の全要件が notes に反映されているか
- 蒸留過程で情報が失われていないか
- notes 内で矛盾する記述がないか
- 用語集の用語が notes 全体で統一的に使用されているか
- ビジネスルール間に論理的矛盾がないか
- 技術仕様が非機能要件と整合しているか
- 後続の成果物作成に十分な情報量があるか

最終成果物として、**トレーサビリティマトリクス**（要件 → 仕様の追跡表）を作成する。テンプレートは [references/output-examples.md](references/output-examples.md) を参照。

---

## Quality Gates

以下のすべてを満たした場合のみ、distill フェーズを完了とする:

**基本ゲート**:
- すべての inbox 資料が分析済み
- 用語集が作成され、全用語に ID が付与済み
- ドメインモデルが対象ドメインの業務を正確に表現
- ビジネスルールが網羅的に抽出済み（全ルールに ID、出典、検証ロジック）
- notes の各ドキュメントが相互参照可能
- トレーサビリティマトリクスで全要件の追跡が可能

**技術仕様ゲート（該当案件のみ）**:
- 非機能要件が定量的に定義済み
- API 仕様が入出力含め定義済み（該当時）
- データモデルが正規化・パーティション戦略含め設計済み（該当時）
- 技術選定根拠が論理的に文書化済み（該当時）

## Troubleshooting

| 問題 | 原因 | 対処 |
|:---|:---|:---|
| inbox の資料が不十分 | 情報不足 | 質問リストを作成し、追加情報の収集を依頼 |
| 用語が業界固有で理解困難 | ドメイン知識の不足 | 業界標準文書、規格、ガイドラインを参照 |
| 要件間の矛盾を発見 | ソース資料内の不整合 | 矛盾を明示し、確認を依頼。ADR に仮定を記録 |
| 技術選定で迷う | 複数の有力候補 | 評価マトリクスを作成し、ADR に判断根拠を記録 |
| 既存仕様の更新時に diff が不明 | 差分管理の不備 | `04_snapshots/` に変更前の状態を保存してから更新 |
