# Skill: Refactor（コードリファクタリング — 振る舞いを変えずに構造を変える）

> **動くコードを正しいコードに鍛え直せ — 振る舞いを変えずに構造を変えよ**

## Instructions

### ワークフロー内の位置

```
コードベース（リポジトリ/ディレクトリ/ファイル）
  ↓
[refactor]
  ├─ Step 1: 対象の特定とスコープ確定
  │   └─ 📋 Review Gate 1（スコープ妥当性レビュー）
  ├─ Step 2: コードスメル・技術的負債スキャン
  │   └─ 📋 Review Gate 2（スキャン結果の網羅性レビュー）
  ├─ Step 3: リファクタリング優先度の決定
  │   └─ 📋 Review Gate 3（優先度判断の整合性レビュー）
  ├─ Step 4: 安全網の確認（テスト・バックアップ）
  │   └─ 📋 Review Gate 4（安全網の十分性レビュー）
  ├─ Step 5: リファクタリング計画の立案（Fowler パターン選定）
  │   └─ 📋 Review Gate 5（計画の実現可能性レビュー）
  ├─ Step 6: リファクタリングの実施（段階的変更）
  │   └─ 📋 Review Gate 6（変更コードの品質レビュー）
  ├─ Step 7: 動作検証とリグレッションテスト
  │   └─ 📋 Review Gate 7（振る舞い保証レビュー）
  └─ Step 8: 成果物サマリーと引き渡し
  ↓
リファクタリング済みコード + 変更レポート + 技術的負債解消量
  ↓
bug-finder（潜在バグの後続スキャン）または review（成果物の品質検証）
```

### 入力

| 入力 | 説明 | 例 |
|:---|:---|:---|
| 対象パス | リポジトリルート、ディレクトリ、またはファイルパス | `./src/`, `./api/users.ts`, リポジトリ全体 |
| リファクタリング目標（任意） | 何を改善したいか | `DRY 化`, `God Class 分割`, `依存関係整理` |
| 優先スメル（任意） | 特定のコードスメルに絞る場合 | `Long Method`, `Duplicate Code`, `Feature Envy` |
| 除外パス（任意） | スキャン対象外のパス | `node_modules/`, `*.generated.ts` |

### 出力

| 出力 | 形式 | 説明 |
|:---|:---|:---|
| リファクタリング済みコード | コード差分 | 最小変更で構造を改善したコード |
| 変更レポート | Markdown | 適用したパターン・変更箇所・改善指標のサマリー |
| 技術的負債解消レポート | テーブル | Before/After の負債指標（LOC/複雑度/重複率） |

## Step 1: 対象の特定とスコープ確定

リファクタリングの範囲を明確にし、「何を改善するか」と「何を変えないか」を確定する。スコープが曖昧なままでは振る舞いの保証ができない。

### 1a. 対象パスの特定と規模把握

| 確認項目 | 判断基準 |
|:---|:---|
| 対象タイプ | ファイル / ディレクトリ / リポジトリルートでアプローチを変える |
| 言語の特定 | 拡張子・設定ファイルで言語を確定（複数言語の場合はすべて列挙） |
| ファイル規模 | 20 ファイル以下: 全件精査 / 20〜100: 高複雑度優先 / 100 超: 最高優先度箇所に絞る |
| テスト状況の確認 | テストファイルの存在 / テストカバレッジの推定 |

### 1b. リファクタリング目標の確定

| 目標カテゴリ | 代表的なゴール | 主要適用パターン |
|:---|:---|:---|
| **可読性向上** | 関数・変数名の明確化、コードの簡潔化 | Rename, Extract Function, Inline Temp |
| **重複排除（DRY）** | 同一ロジックの一元化 | Extract Function, Pull Up Method, Form Template Method |
| **責務分割（SRP）** | 巨大クラス/関数の分割 | Extract Class, Extract Method, Move Method |
| **依存関係整理** | 疎結合化、DIP の適用 | Replace Inheritance with Delegation, Introduce Parameter Object |
| **技術的負債解消** | 古い実装のモダナイズ | Substitute Algorithm, Replace Conditional with Polymorphism |

### 1c. 除外スコープの設定

以下はデフォルトで除外（ユーザー指定で変更可）:

```
デフォルト除外:
- node_modules/, vendor/, .venv/, __pycache__/
- *.test.ts, *.spec.py, *_test.go（テストコード — Step 7 で別途確認）
- *.generated.ts, *.pb.go（自動生成コード）
- dist/, build/, .next/（ビルド成果物）
```

**チェックリスト**:
- [ ] 対象パスの存在を確認した
- [ ] 言語を特定した（複数言語は全列挙）
- [ ] ファイル数・規模からアプローチ戦略を決定した
- [ ] リファクタリングの目標カテゴリを 1-3 個に絞った
- [ ] 「変えてはいけない振る舞い」を明確にした（= 外部 API・インターフェース・副作用）
- [ ] テスト状況（有無・カバレッジ推定）を確認した

### 📋 Review Gate 1: スコープ妥当性レビュー

review スキルの A-1（要件カバレッジ）と A-3（数値妥当性）の観点でレビューする。

| レビュー観点 | 確認内容 |
|:---|:---|
| スコープの完全性 | リファクタリング目標が対象パスの実態と一致しているか |
| 「変えてはいけない振る舞い」の明確さ | 外部インターフェース・副作用が明確に定義されているか |
| 規模見積もりの妥当性 | ファイル数とアプローチ戦略が適合しているか |

**通過条件**: Critical / Major 指摘がゼロ。

---

## Step 2: コードスメル・技術的負債スキャン

Fowler の 22 コードスメルカテゴリ（[code-smells-catalog.md](references/code-smells-catalog.md)）を使って問題箇所を体系的に洗い出す。スメルは「変えるべき理由」であり、「何を直すか」の根拠となる。

### 2a. 関数・メソッドレベルのスメル

| スメル | 検出シグネチャ | 判断閾値 |
|:---|:---|:---|
| **Long Method** | 関数の行数が多い | 20 行超（言語・文脈による） |
| **Long Parameter List** | 引数の数が多い | 4 個超 |
| **Duplicate Code** | 同一 or 類似コードが複数箇所に存在 | 3 行以上の重複 |
| **Dead Code** | 呼び出されない関数・未使用変数 | grep で呼び出し元なし |
| **Speculative Generality** | 「将来必要かも」で作られた未使用の汎化 | abstract class で実装が 1 つだけ |

### 2b. クラス・モジュールレベルのスメル

| スメル | 検出シグネチャ | 典型症状 |
|:---|:---|:---|
| **Large Class (God Class)** | 1 クラスが多数の責務を持つ | 500 行超・10 フィールド超 |
| **Feature Envy** | メソッドが他クラスのデータを大量に参照 | `other.fieldA`, `other.fieldB`, `other.fieldC` |
| **Data Clumps** | 常に一緒に渡されるデータグループ | 3 個以上の変数が常にペアで出現 |
| **Divergent Change** | 1 クラスに複数の変更理由がある | SRP 違反の指標 |
| **Shotgun Surgery** | 1 つの変更で多数のクラスを修正が必要 | 変更影響が広範 |

### 2c. アーキテクチャレベルの負債

| 負債パターン | 検出方法 | 影響 |
|:---|:---|:---|
| **循環依存** | モジュール間の依存グラフで閉路を確認 | テスト困難・変更困難 |
| **レイヤー違反** | UI→DB への直接アクセス等 | 責務境界の崩壊 |
| **マジックナンバー / ハードコード** | `42`, `"prod"` 等の文字列リテラル直書き | 変更容易性の低下 |

詳細スキャンシグネチャは [code-smells-catalog.md](references/code-smells-catalog.md) 参照。

**チェックリスト**:
- [ ] 関数・メソッドレベルの全 5 スメルカテゴリを確認した
- [ ] クラス・モジュールレベルの全 5 スメルカテゴリを確認した
- [ ] アーキテクチャレベルの 3 パターンを確認した
- [ ] 各スメルにファイル名・行番号・コード証拠を記録した
- [ ] 同一パターンの複数出現はグルーピングした（例: 「Long Method（7 箇所）」）

### 📋 Review Gate 2: スキャン結果の網羅性レビュー

review スキルの A-1（要件カバレッジ）と B-3（境界値攻撃）の観点でレビューする。

| レビュー観点 | 確認内容 |
|:---|:---|
| スメル証拠の十分性 | 各スメルに「どのコードの、どの行で発現するか」の具体的証拠があるか |
| 偽陽性の除外 | 意図的な長い関数（アルゴリズムの可読性のため）が誤ってスメルに含まれていないか |
| 網羅性 | 高リスクファイル（God Class 候補・変更頻度が高いファイル）が漏れていないか |

**通過条件**: Critical / Major 指摘がゼロ。「証拠なしのスメル列挙」は Major 扱い。

## Step 3: リファクタリング優先度の決定

すべてのスメルをリファクタリングする必要はない。**影響 × コスト × リスク**で優先度を決定し、最大効果を得る変更に集中する。

### 3a. 優先度マトリクスの作成

[tech-debt-matrix.md](references/tech-debt-matrix.md) の評価基準に従い、各スメルを評価する:

| 評価軸 | 高（3点） | 中（2点） | 低（1点） |
|:---|:---|:---|:---|
| **影響（なぜ直すか）** | 多くのコードが依存 / 変更頻度が高い / 読解困難 | 一部依存・中程度の頻度 | ほぼ参照されない |
| **コスト（どれくらい変更か）** | 1-3 ファイルの小さな変更 | 5 ファイル以下の変更 | 10 ファイル超の広範変更 |
| **リスク（何が壊れうるか）** | テスト完備・影響範囲が小さい | テスト部分的・影響中程度 | テストなし・影響広範 |

> **コスト・リスクは「低いほど優先度が高い」** — スコアが高いほど「対応しやすい」

### 3b. 優先度分類

| 分類 | スコア基準 | 対応方針 |
|:---|:---|:---|
| **P1: 今すぐ実施** | 影響高 + コスト低 + リスク低 | このセッションで完了する |
| **P2: 計画的に実施** | 影響高 + コスト中 or リスク中 | 今セッションの後半または次回 |
| **P3: 技術的負債として記録** | 影響低 or コスト高 | TODO コメント / Issue で記録 |
| **P4: 対応しない** | 削除予定コード / 外部依存が強すぎる | 記録して終了 |

**チェックリスト**:
- [ ] Step 2 の全スメルに優先度スコアを付与した
- [ ] P1 の対象を最大 5 項目に絞り込んだ（一度にやりすぎない）
- [ ] P3/P4 の判断根拠を記録した
- [ ] 今セッションのスコープ（P1 のみ / P1+P2 の一部）を決定した

### 📋 Review Gate 3: 優先度判断の整合性レビュー

review スキルの A-2（章間整合性）と A-3（数値妥当性）の観点でレビューする。

| レビュー観点 | 確認内容 |
|:---|:---|
| スコア判断の一貫性 | 同様のスメルで優先度が矛盾していないか（影響度の評価基準が統一されているか） |
| P1 の適切な絞り込み | P1 が多すぎないか（5 項目超は過負荷リスク）/ 少なすぎないか（1 項目は機会損失） |
| スコープの現実性 | 今セッションのスコープがファイル規模・テスト状況に対して現実的か |

**通過条件**: Critical / Major 指摘がゼロ。

## Step 4: 安全網の確認（テスト・バックアップ）

リファクタリングの鉄則: **テストがなければリファクタリングは賭けになる**。変更前に安全網を整備し、「振る舞いを変えていない」ことを証明できる状態にする。

### 4a. テストカバレッジの評価

| カバレッジ状況 | 判断 | 対応 |
|:---|:---|:---|
| テスト完備（80%+） | ✅ 安全にリファクタリング可 | Step 5 へ |
| テスト部分的（40-80%） | ⚠️ リファクタリング対象箇所のテストを追加 | test スキルで追加後に Step 5 へ |
| テスト極少（< 40%） | ❗ 特性化テスト（Characterization Test）を先に書く | 安全網構築を先行させる |
| テストなし | 🛑 特性化テスト必須 または スコープを極小に絞る | test スキルに委譲または Step 6 をマイクロステップで |

### 4b. 特性化テスト（Characterization Test）の作成

テストが存在しない場合、現在の振る舞いを記録するテストを書く。これは「正しい振る舞いを証明する」テストではなく、「現在の振る舞いを固定する」テスト。

```
特性化テストの考え方:
1. 対象コードを実行する
2. 実際に返ってくる値を観察する
3. その値を期待値としてテストに書く（正しいかどうかは問わない）
4. これにより「リファクタリングで振る舞いが変わった」ことを検知できる
```

### 4c. バックアップとブランチ戦略

```
推奨手順:
1. git commit で現在の状態を保存
2. リファクタリング専用ブランチを作成: git checkout -b refactor/<scope>
3. 各ステップ後に atomic commit（1 パターン = 1 コミット）
4. ロールバックが必要な場合: git revert または git reset --hard <checkpoint>
```

詳細は [safety-first-guide.md](references/safety-first-guide.md) 参照。

**チェックリスト**:
- [ ] テストカバレッジを評価し、対応方針を決定した
- [ ] テストが不足する場合、特性化テストを追加した or test スキルに委譲した
- [ ] git でチェックポイントを作成した（または作成を確認した）
- [ ] リファクタリング専用ブランチを作成した
- [ ] 対象コードの公開インターフェース（API シグネチャ）を記録した（変更禁止リスト）

### 📋 Review Gate 4: 安全網の十分性レビュー

review スキルの A-1（要件カバレッジ）と B-6（テストカバレッジ）の観点でレビューする。

| レビュー観点 | 確認内容 |
|:---|:---|
| テスト網羅性 | P1 対象の全コードにテストカバレッジがあるか。テストがない箇所をリファクタリングする場合、特性化テストが追加されているか |
| 変更禁止リストの完全性 | 外部から参照される全 API・インターフェースが「変更禁止」として記録されているか |
| ロールバック可能性 | git でロールバックできる状態になっているか |

**通過条件**: B-6（テストカバレッジ）が通過。特性化テストなしで「テストがない箇所」をリファクタリングしようとしている場合は Critical。

**不合格時**: test スキルに委譲してテストを追加し、Gate 4 を再通過する。

## Step 5: リファクタリング計画の立案（Fowler パターン選定）

P1 の各スメルに対して、適用する Fowler パターンと実施順序を決定する。パターン選定の根拠を記録し、実施前にユーザーに確認する。

### 5a. スメル → パターンのマッピング

[refactoring-patterns.md](references/refactoring-patterns.md) の選定マトリクスに従い、各スメルに対応するパターンを選択する:

| コードスメル | 第一候補パターン | 代替パターン |
|:---|:---|:---|
| Long Method | Extract Function | Replace Temp with Query |
| Duplicate Code | Extract Function → Pull Up Method | Form Template Method |
| Large Class | Extract Class | Move Method + Move Field |
| Long Parameter List | Introduce Parameter Object | Preserve Whole Object |
| Feature Envy | Move Method | Extract Function + Move |
| Data Clumps | Introduce Parameter Object | Extract Class |
| Dead Code | Remove Dead Code | — |
| Divergent Change | Extract Class（責務ごとに分離） | Move Method |
| Speculative Generality | Inline Class / Collapse Hierarchy | Remove Middle Man |

### 5b. 実施順序の決定原則

```
順序の原則:
1. 依存関係の末端から始める（依存される側を先にリファクタリング）
2. 小さい変更を先に行い、大きい変更への道を開く
3. テスト通過を確認しながら進める（Green → Refactor → Green）
4. 1 つのパターンを完全に適用してからコミット、次に進む
```

### 5c. 計画書の作成

```markdown
## リファクタリング計画

### スコープ: <対象パス>
### 目標: <改善ゴール>

| 優先度 | 対象 | スメル | 適用パターン | 影響ファイル | 推定工数 |
|:---|:---|:---|:---|:---|:---|
| P1-1 | UserService.ts L45-120 | Long Method | Extract Function（3関数に分割） | UserService.ts | 30分 |
| P1-2 | utils/helpers.ts, api/handler.ts | Duplicate Code | Extract Function（共通関数化） | 3ファイル | 20分 |
...
```

**チェックリスト**:
- [ ] P1 の全スメルに対応パターンを選定した
- [ ] 実施順序を依存関係と変更規模で決定した
- [ ] 計画書に対象・スメル・パターン・影響ファイルを記載した
- [ ] 1 コミット = 1 パターン適用 の方針を決定した
- [ ] ユーザーに計画を提示し、承認を得た

### 📋 Review Gate 5: 計画の実現可能性レビュー

review スキルの A-2（章間整合性）と B-1（Semantic Drift）の観点でレビューする。

| レビュー観点 | 確認内容 |
|:---|:---|
| パターンとスメルの整合性 | 選択したパターンが対象スメルを実際に解消できるか |
| 実施順序の論理性 | 依存関係を無視した順序になっていないか（依存先を先に変えようとしていないか） |
| スコープの適切さ | 計画のスコープが Step 1 で確定したスコープを逸脱していないか |

**通過条件**: Critical / Major 指摘がゼロ。

---

## Step 6: リファクタリングの実施（段階的変更）

計画に従いコードを変更する。**振る舞いを変えない**が絶対原則。各パターンの適用後にテストを実行し、Green を確認してから次に進む。

### 6a. スモールステップの原則

```
実施サイクル（パターン 1 つ = 1 サイクル）:
1. 変更前のテストがすべて Green であることを確認
2. 1 つのリファクタリングパターンを適用
3. テストを実行 → Green であることを確認
4. git commit（コミットメッセージ: "refactor: Extract Function - extractUserValidation"）
5. 次のパターンへ
```

> **Red になったら即座にロールバック（git stash or git checkout）。推測で続けない。**

### 6b. パターン別実施ガイド

| パターン | 実施手順 | よくある失敗 |
|:---|:---|:---|
| **Extract Function** | 1. 新関数を作る 2. 元のコードを新関数の呼び出しに置き換える 3. テスト | 変数のスコープを忘れて参照エラー |
| **Move Method** | 1. 移動先クラスに新メソッドを作る 2. 元のメソッドを委譲に変える 3. 参照を更新 4. 元を削除 | 参照の更新漏れ |
| **Extract Class** | 1. 新クラスを作る 2. フィールドを移動 3. メソッドを移動 4. 元クラスから委譲 | 双方向参照が生じて循環依存 |
| **Rename** | 1. IDE のリネーム機能を使う（全参照一括更新） 2. テスト | 文字列マッチングでの見落とし |
| **Introduce Parameter Object** | 1. 新しいデータクラスを作る 2. 引数をオブジェクトに変換 3. 呼び出し箇所を更新 | デフォルト値の設定漏れ |

詳細は [refactoring-patterns.md](references/refactoring-patterns.md) 参照。

### 6c. 振る舞いを変えない境界の管理

```
変更禁止リスト（Step 4c で記録したもの）:
- public API のシグネチャ（引数の型・順序・戻り値型）
- 外部から参照されるクラス名・モジュール名
- 副作用（ファイル書き込み・DB 更新・ログ出力）の有無とタイミング
- エラー時の挙動（スローする例外の種類）
```

**チェックリスト**:
- [ ] 各パターン適用前後でテストが Green であることを確認した
- [ ] 1 パターン = 1 コミット を守った
- [ ] 変更禁止リストの項目を変更していない
- [ ] Red になった場合は即座にロールバックし、原因を特定してから再試行した
- [ ] リファクタリング中にバグを発見した場合は bug-triage-fix に委譲した（混在させない）

### 📋 Review Gate 6: 変更コードの品質レビュー

review スキルの B-1〜B-6 の技術仕様レビュー基準でレビューする。

| レビュー観点 | 確認内容 |
|:---|:---|
| 仕様との整合性（B-1） | リファクタリング後のコードが元の仕様（振る舞い）と一致しているか |
| 境界値の堅牢性（B-3） | 抽出した関数がエッジケース（null・空配列・境界値）を同様に処理するか |
| パフォーマンス（B-5） | Extract Function による不要なループや N+1 が発生していないか |
| テストカバレッジ（B-6） | 変更箇所のテストが維持・追加されているか |

**通過条件**: B-1（仕様整合性）は必須通過。Critical / Major 指摘がゼロ。

## Step 7: 動作検証とリグレッションテスト

リファクタリングが完了したコードの振る舞いを最終検証する。「何も壊れていない」ことを証明する段階。

### 7a. テストスイートの実行

| テスト種別 | 目的 | 期待結果 |
|:---|:---|:---|
| **ユニットテスト** | 変更した関数・クラスの直接検証 | 全件 Green |
| **統合テスト** | モジュール間の連携が維持されているか | 全件 Green |
| **特性化テスト** | Step 4 で追加した振る舞い固定テスト | 全件 Green |
| **既存のエンドツーエンドテスト** | 上位レベルの振る舞いが維持されているか | 全件 Green |

### 7b. 手動チェック項目

自動テストで検証しにくい観点を手動で確認する:

| チェック項目 | 確認方法 |
|:---|:---|
| エラーメッセージの内容 | リファクタリング後も同じエラーメッセージが出るか |
| ログ出力 | 副作用（ログ・ファイル書き込み）のタイミングが変わっていないか |
| パフォーマンス | 極端な速度低下がないか（大規模ループを変更した場合） |
| エッジケース | null・空配列・境界値での動作が変わっていないか |

### 7c. リグレッションテストの追加

リファクタリングのプロセスで発見したエッジケースを新規テストとして追加する:

```
追加テストの命名規則:
[対象機能] - [リファクタリングで変更した点] - [期待する振る舞い]

例:
- "UserService.validateUser - 抽出した validateEmail - nullを渡した時にエラーを返す"
- "PaymentHandler - Extract Class 後 - 同一の支払いロジックが実行される"
```

**チェックリスト**:
- [ ] ユニットテスト・統合テスト・特性化テストが全件 Green
- [ ] 手動チェック（エラーメッセージ・ログ・パフォーマンス）を実施した
- [ ] リファクタリング中に発見したエッジケースをテストに追加した
- [ ] テスト追加後も全件 Green を確認した

### 📋 Review Gate 7: 振る舞い保証レビュー

review スキルの A-1（要件カバレッジ）と B-6（テストカバレッジ）の観点でレビューする。

| レビュー観点 | 確認内容 |
|:---|:---|
| テスト網羅性 | リファクタリングした全コードパスにテストがあるか |
| 振る舞いの一致 | Step 4c で記録した変更禁止リストの項目が変更されていないか |
| 新規テストの品質 | 追加したテストが振る舞いを検証しているか（実装の詳細ではなく） |

**通過条件**: 全テスト Green。B-6 の全チェックリストをパス。Critical / Major 指摘がゼロ。

## Troubleshooting

| 問題 | 原因 | 解決策 |
|:---|:---|:---|
| テストが Red になった | リファクタリングで振る舞いが変わった | 即座に git stash で元に戻す。変更内容を見直してスモールステップで再実施 |
| テストがなくてリファクタリングできない | 特性化テストの未作成 | Step 4 に戻り特性化テストを作成する。または test スキルに「現在の振る舞いを記録するテストを書いて」と委譲する |
| Extract Class 後に循環依存が発生 | 双方向参照が生じた | 依存の向きを整理する（インターフェース導入またはイベントドリブンへ変更） |
| リファクタリング中にバグを発見 | コードスメルと本物のバグが混在 | バグは bug-triage-fix に委譲し、リファクタリングは中断してコミット。バグ修正後に再開 |
| God Class の分割で何から始めるか分からない | 責務の境界が不明確 | メソッドをリスト化し、「このメソッドが変わる理由は何か？」で分類する。同じ理由で変わるものが同じクラス |
| Extract Function 後に変数スコープエラー | ローカル変数の参照範囲ミス | 抽出した関数に必要な変数を引数として明示的に渡す |
| Rename 後にビルドエラーが多発 | 文字列テンプレートや設定ファイルに旧名が残っている | IDE のリネーム機能と grep を組み合わせて全参照を確認する |
| リファクタリングのスコープが広がりすぎる | 「ついでに」の改善が連鎖する | Scout Rule（通りすがりに直す）ではなく、スコープを固守する。追加発見は P3 リストに記録する |
| パフォーマンスが劣化した | Extract Function で不要なオブジェクト生成やループが増えた | プロファイラで測定。性能要件がある箇所はリファクタリングを限定的にする |
| Introduce Parameter Object 後に呼び出し元が多すぎて更新できない | 影響範囲が広すぎるパターンを選んだ | まず新しい引数形式の関数を追加し、古い関数から委譲。段階的に移行する（Strangler Fig パターン） |
| 既存テストが実装の詳細をテストしていて Green にならない | テストがホワイトボックステストで内部構造に依存 | Step 4b で特性化テストを追加し、既存の壊れやすいテストは振る舞いベースに書き直す |
| TypeScript の any 除去で実行時エラーが増えた | 型エラーを抑制していた箇所でバグが顕在化した | バグが顕在化したとみなし bug-triage-fix に委譲。any の除去はリファクタリングだが、型エラーの発見はバグ修正が必要なことを示す |
