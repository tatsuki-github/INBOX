# 技術的負債評価マトリクス

> 影響 × コスト × リスクで技術的負債の優先度を決定する。
> 「何をいつ直すか」の判断を客観化するためのフレームワーク。

---

## 1. 優先度スコアリング基準

### 影響スコア（なぜ直すか — 高いほど優先度が上がる）

| スコア | 基準 | 指標例 |
|:---|:---|:---|
| **3（高影響）** | 多くのコードが依存 / 変更頻度が高い / 読解困難で onboarding コスト大 | 他の 10 以上のファイルから import / 直近 1 ヶ月に 5 回以上変更 |
| **2（中影響）** | 一部依存・中程度の変更頻度 | 3-9 ファイルから参照 / 月 2-4 回の変更 |
| **1（低影響）** | ほぼ参照されない / 変更頻度が低い | 1-2 ファイルから参照 / 年に 1-2 回の変更 |

### コストスコア（どれくらい変更するか — 低いほど優先度が上がる）

| スコア | 基準 | 変更規模 |
|:---|:---|:---|
| **3（低コスト）** | 1-3 ファイルの小さな変更 | 変更行数 50 行以下、影響ファイル 3 以下 |
| **2（中コスト）** | 5 ファイル以下の変更 | 変更行数 50-200 行、影響ファイル 5 以下 |
| **1（高コスト）** | 10 ファイル超の広範変更 | 変更行数 200 行超、影響ファイル 10 超 |

### リスクスコア（何が壊れうるか — 低いほど優先度が上がる）

| スコア | 基準 | 安全網の状況 |
|:---|:---|:---|
| **3（低リスク）** | テスト完備（80%+）・影響範囲が明確 | 単体テスト + 統合テスト完備 |
| **2（中リスク）** | テスト部分的（40-80%）・影響中程度 | 一部テストあり、手動確認が必要 |
| **1（高リスク）** | テストなし / 影響範囲が不明 | テストなし、変更影響が広範 |

---

## 2. 優先度判定テーブル

優先度スコア = 影響スコア + コストスコア + リスクスコア（最大 9 点）

| 総スコア | 優先度分類 | 対応方針 |
|:---|:---|:---|
| **8-9 点** | **P1: 今すぐ実施** | このセッションで完了する。ROI が最大 |
| **6-7 点** | **P2: 計画的に実施** | 今セッションの後半または次回のスプリント |
| **4-5 点** | **P3: 技術的負債として記録** | TODO コメント / Issue で追跡 |
| **3 点** | **P4: 対応しない** | コスト対効果が低い。削除予定なら記録のみ |

## 4. 技術的負債計測指標（Before/After）

リファクタリング前後の改善を定量化するための指標。

### コード品質指標

| 指標 | 計測方法 | 改善方向 |
|:---|:---|:---|
| **最大関数行数** | `wc -l` / IDE 表示 | 小さいほど良い（目標 20 行以下） |
| **最大クラス行数** | `wc -l` | 小さいほど良い（目標 200 行以下） |
| **循環複雑度** | `eslint complexity` / `radon cc` | 低いほど良い（目標 10 以下/関数） |
| **重複コード率** | `jscpd` / `pylint duplicate-code` | 低いほど良い（目標 5% 以下） |
| **テストカバレッジ** | `nyc` / `pytest-cov` | 高いほど良い（目標 80%+） |

### ファイルレベル指標

| 指標 | 計測コマンド例 | 意味 |
|:---|:---|:---|
| LOC (Lines of Code) | `wc -l src/**/*.ts` | 変更量の粗い指標 |
| 関数数/ファイル | `grep -c "function\|=>" src/*.ts` | 責務の分散度 |
| import 数/ファイル | `grep -c "import" src/*.ts` | 依存の複雑さ |

## 5. 技術的負債の分類（Ward Cunningham の定義に基づく）

| 種類 | 定義 | 対処方針 |
|:---|:---|:---|
| **意図的・慎重な負債** | 「今は急ぐが後で直す」と決めた負債 | P2 で計画的に対処 |
| **意図的・無謀な負債** | 設計を無視して速度優先で書いた | P1 で対処（リスクが高い） |
| **偶発的・慎重な負債** | 後から「もっと良い設計がわかった」 | P2-P3 で計画的に |
| **偶発的・無謀な負債** | 「DRY って何？」状態で書かれたコード | 教育 + P1-P2 で対処 |

> **重要**: 技術的負債は「悪いもの」ではない。戦略的に借りて、計画的に返すもの。返済計画なき借入が問題。
