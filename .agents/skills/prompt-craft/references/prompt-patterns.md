# プロンプトパターン 8 種の詳細定義

> プロンプト設計で使用する 8 つの基本パターン。選定フロー・組み合わせガイド付き。

---

## パターン一覧

### P1: Zero-shot

| 項目 | 内容 |
|:---|:---|
| **定義** | 例を一切与えず、指示文のみでタスクを実行させる |
| **適用場面** | 単純な翻訳、要約、感情分析、一般知識 QA |
| **利点** | トークン効率が最高。プロンプトが短い |
| **欠点** | 出力形式が安定しない。ドメイン固有タスクに弱い |
| **成功条件** | モデルの事前学習で十分対応できるタスク |

```
あなたは翻訳者です。以下の日本語を英語に翻訳してください。

入力: {{text}}
```

---

### P2: Few-shot

| 項目 | 内容 |
|:---|:---|
| **定義** | 入出力の例を 2-6 個提示し、パターンを学習させる |
| **適用場面** | 分類、フォーマット変換、ドメイン固有の用語対応 |
| **利点** | 出力形式が安定する。ドメイン適応が容易 |
| **欠点** | トークン消費が増加。例の品質に依存する |
| **成功条件** | 「良い例」が 2-6 個用意できる |

**例の設計指針**:
- 正常系 2-3 例 + 境界ケース 1-2 例 + 異常系 1 例
- 出力フォーマットを全例で完全統一
- 例の順序: 簡単 → 難しい

---

### P3: Chain-of-Thought (CoT)

| 項目 | 内容 |
|:---|:---|
| **定義** | 思考過程を段階的に出力させてから最終回答を導く |
| **適用場面** | 数学的推論、論理判断、多段階の意思決定 |
| **利点** | 推論精度が大幅に向上。判断根拠が透明化 |
| **欠点** | 出力が長くなる。レイテンシ増。トークンコスト増 |
| **成功条件** | 「考えれば正解にたどり着く」タスク |

**実装バリエーション**:

| バリエーション | 指示例 |
|:---|:---|
| **明示的 CoT** | 「ステップバイステップで考えてください」 |
| **構造化 CoT** | 「以下の 3 ステップで推論せよ: 1) 前提の確認 2) 条件の評価 3) 結論」 |
| **CoT + 最終回答分離** | 思考は `<thinking>` タグ内、回答は `<answer>` タグ内 |

---

### P4: Role-play（ペルソナ設定）

| 項目 | 内容 |
|:---|:---|
| **定義** | LLM に特定の役割・専門家としての視点を付与 |
| **適用場面** | コードレビュー、医療相談、法務チェック |
| **利点** | ドメイン知識の活用度が上がる。回答のトーンが安定 |
| **欠点** | 過度な役割設定は hallucination リスク |
| **成功条件** | 専門家の視点やトーンが出力品質を明確に向上させる |

**効果的なペルソナの 4 要素**:
1. 役職・経験年数
2. 専門領域（具体的に）
3. 行動原則（判断基準の優先順位）
4. 制限事項（やらないこと）

---

### P5: Structured Output（構造化出力）

| 項目 | 内容 |
|:---|:---|
| **定義** | JSON / XML / CSV 等の機械可読フォーマットで出力を強制 |
| **適用場面** | API 連携、データパイプライン、自動後処理 |
| **利点** | パース可能な安定出力。後続処理との統合が容易 |
| **欠点** | 自然な文章生成には不向き |
| **成功条件** | 出力を機械的に処理する必要がある |

**強制テクニック**:

| モデル | テクニック |
|:---|:---|
| Claude | XML タグ指定 + Prefix 強制 |
| GPT-4o | `response_format: { type: "json_schema" }` |
| Gemini | MIME type 指定 |
| 汎用 | Few-shot で形式を明示 + 「この形式以外での回答は禁止」 |

---

### P6: Self-consistency（自己整合性）

| 項目 | 内容 |
|:---|:---|
| **定義** | 同一入力で複数回生成し、多数決で最終回答を選択 |
| **適用場面** | 診断、分類、リスク評価など高精度が必要なタスク |
| **利点** | 単発の推論誤りを統計的に補正 |
| **欠点** | コスト N 倍。レイテンシ N 倍。パイプライン実装が必要 |
| **成功条件** | 精度 > コスト/速度の優先順位 |

**推奨実行回数**: 3-5 回（奇数推奨）

---

### P7: ReAct（Reasoning + Acting）

| 項目 | 内容 |
|:---|:---|
| **定義** | 思考（Thought）→ 行動（Action）→ 観察（Observation）のループ |
| **適用場面** | ツール呼び出し、検索結合、エージェント的動作 |
| **利点** | 外部情報を動的に取得して推論に反映 |
| **欠点** | ループ制御が複雑。無限ループリスク |
| **成功条件** | 外部ツール/API との統合が必要なタスク |

---

### P8: Meta-prompting

| 項目 | 内容 |
|:---|:---|
| **定義** | LLM 自身にプロンプトの評価・改善を行わせる |
| **適用場面** | プロンプト最適化、A/B テスト設計、品質評価 |
| **利点** | 人手のプロンプト改善を補助 |
| **欠点** | 改善が表面的になりやすい |
| **成功条件** | 人間のレビューと組み合わせて使用する |

```
以下のプロンプトを評価し、改善提案を 3 つ挙げてください。
評価基準: 明瞭性、具体性、出力安定性

プロンプト:
{{prompt_text}}
```

## パターン選定フローチャート

```
1. 出力を機械的にパースする必要があるか？
   → Yes: P5 (Structured Output) を必ず含める
   → No: 次へ

2. 外部ツール/API と連携するか？
   → Yes: P7 (ReAct)
   → No: 次へ

3. 高精度が絶対条件か（コスト/速度より精度優先）？
   → Yes: P6 (Self-consistency) を検討
   → No: 次へ

4. 推論・分析・多段階判断が必要か？
   → Yes: P3 (CoT) → 専門家視点が有効なら P3 + P4
   → No: 次へ

5. ドメイン固有の出力パターンがあるか？
   → Yes: P2 (Few-shot) → 専門家トーンも必要なら P2 + P4
   → No: P1 (Zero-shot) + P4 (Role-play)
```

---

## 組み合わせマトリクス

| 組み合わせ | 適用場面 | 効果 |
|:---|:---|:---|
| P2 + P5 | API 連携のデータ変換 | 安定 JSON + ドメイン適応 |
| P3 + P4 | 専門家の分析レポート | 根拠付き推論 + 専門視点 |
| P3 + P6 | 高精度な診断・判定 | CoT の推論 × 多数決の安定性 |
| P2 + P4 + P5 | カスタマーサポート Bot | ペルソナ + 例示 + 構造化応答 |
| P3 + P4 + P5 | 業務判断の自動化 | 専門家思考 + 透明な推論 + パース可能出力 |
