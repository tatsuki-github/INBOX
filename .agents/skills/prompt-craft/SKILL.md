# Skill: Prompt Craft（AI プロンプトの設計・鋳造）

> **曖昧な願望を精密な指令に鍛え上げよ — LLM は「読心術師」ではなく「忠実な実行者」だ**

## Instructions

### ワークフロー内の位置

```
ユーザーの意図・課題
  ↓
[prompt-craft]
  ├─ Step 1: 目的・制約ヒアリング
  ├─ Step 2: ペルソナ・トーン設計
  ├─ Step 3: 構造設計とパターン選定
  ├─ Step 4: プロンプト本文の執筆
  ├─ Step 5: Few-shot 例・出力制御の設計
  ├─ Step 6: テスト・反復改善
  └─ Step 7: 品質検証・文書化・引き渡し
  ↓
完成プロンプト（System / User / テンプレート）
  ↓
実運用 or agent-craft / skill-forge への入力
```

### 入力

| 入力 | 説明 | 例 |
|:---|:---|:---|
| タスク概要 | プロンプトで達成したいこと | 「顧客問い合わせの自動分類」 |
| 対象モデル（任意） | 使用する LLM | Claude 3.5 Sonnet, GPT-4o, Gemini |
| 既存プロンプト（任意） | 改善対象の現行プロンプト | 「以下の文章を要約して…」 |
| 期待出力例（任意） | 理想的な出力サンプル | JSON 形式の分類結果 |
| 制約条件（任意） | トークン上限、レイテンシ、コスト | 「入力 2000 トークン以内」 |
| 運用環境（任意） | API / Chat UI / エージェント内 | 「Slack Bot 経由で呼び出す」 |

### 出力

| 出力 | 形式 | 説明 |
|:---|:---|:---|
| プロンプト本文 | Markdown / テキスト | System Prompt + User Prompt テンプレート |
| 設計メモ | Markdown | 設計判断の根拠・パターン選定理由 |
| テスト結果 | テーブル | テストケースと実行結果の記録 |
| Few-shot 例セット | Markdown | プロンプトに組み込む入出力例 |

## Step 1: 目的・制約ヒアリング

プロンプトの「何を・誰が・なぜ・どこで」を明確にする。曖昧なまま書き始めると、後工程で全面書き直しになる。

### 1a. タスク分解（WHAT / WHY / WHO）

| 軸 | 質問 | 記入例 |
|:---|:---|:---|
| **WHAT** | LLM に何をさせたいか？ | 顧客メールを 5 カテゴリに分類する |
| **WHY** | なぜ LLM が必要か？（人手では何が問題か） | 1 日 500 件の手動分類が限界 |
| **WHO** | プロンプトの利用者は誰か？ | CS チームの非エンジニアメンバー |
| **INPUT** | LLM に渡す入力の形式・長さ・品質は？ | 日本語メール本文、平均 300 文字 |
| **OUTPUT** | 期待する出力の形式・構造は？ | JSON: `{"category": "...", "confidence": 0.95}` |
| **EDGE** | 想定される厄介な入力は？ | 複数カテゴリにまたがるメール、英語混じり |

### 1b. 制約条件の洗い出し

| 制約カテゴリ | チェック項目 | 例 |
|:---|:---|:---|
| **モデル制約** | トークン上限、コンテキストウィンドウ | Claude: 200K、GPT-4o: 128K |
| **コスト制約** | 1 リクエストあたりの許容コスト | 「$0.01 / リクエスト以下」 |
| **レイテンシ制約** | 応答時間の要件 | 「3 秒以内に返す」 |
| **安全性制約** | PII 処理、ガードレール要件 | 「個人名をマスクしてから渡す」 |
| **運用制約** | バッチ / リアルタイム、頻度 | 「リアルタイム、ピーク時 100 req/min」 |
| **出力制約** | フォーマット厳密性、言語 | 「必ず JSON で返す。日本語」 |

### 1c. 成功基準の定義

曖昧な「良いプロンプト」ではなく、検証可能な基準を設定する。

| 基準種別 | 指標 | 例 |
|:---|:---|:---|
| **精度** | 正解率、F1 スコア | 「分類精度 90% 以上」 |
| **一貫性** | 同一入力での出力安定性 | 「10 回実行で 9 回同じ結果」 |
| **フォーマット遵守** | 出力形式の遵守率 | 「JSON パースエラー 0%」 |
| **安全性** | ガードレール突破率 | 「プロンプトインジェクション耐性」 |

**チェックリスト**:
- [ ] タスクの WHAT / WHY / WHO を言語化した
- [ ] 入力の形式・長さ・品質を把握した
- [ ] 期待出力の形式と構造を具体的に定義した
- [ ] エッジケース（厄介な入力パターン）を 3 つ以上洗い出した
- [ ] 成功基準を検証可能な指標で定義した
- [ ] 制約条件（コスト / レイテンシ / 安全性）を確認した

## Step 2: ペルソナ・トーン設計

LLM に「誰として振る舞うか」を定義する。ペルソナの精度がプロンプト全体の品質を左右する。

### 2a. ペルソナ定義

| 要素 | 説明 | 良い例 | 悪い例 |
|:---|:---|:---|:---|
| **役割** | 専門分野と職責 | 「10 年経験の SRE エンジニア」 | 「賢い AI」 |
| **専門性** | 具体的な知識領域 | 「Kubernetes と Prometheus に精通」 | 「IT に詳しい」 |
| **行動原則** | 判断基準・優先順位 | 「可用性 > パフォーマンス > コスト」 | 「最善を尽くす」 |
| **制限事項** | やってはいけないこと | 「推測で設定値を提案しない」 | （記載なし） |

### 2b. トーン・スタイル選定

| トーン | 適用場面 | 具体的な指示例 |
|:---|:---|:---|
| **フォーマル** | ビジネス文書、レポート | 「です・ます調。専門用語は定義を添える」 |
| **カジュアル** | チャットボット、社内ツール | 「簡潔に。箇条書き優先。絵文字は不使用」 |
| **教育的** | チュートリアル、解説 | 「初心者にもわかるよう段階的に説明。比喩を活用」 |
| **技術的** | API ドキュメント、仕様記述 | 「正確さ優先。コード例を必ず含める」 |
| **創造的** | ブレスト、アイデア出し | 「常識にとらわれず、意外な組み合わせを提案」 |

### 2c. ペルソナの「しないこと」リスト

ペルソナの境界を明確にすることで、出力のブレを抑制する。

```
あなたは以下を **絶対にしない**:
- 確信がないことを断定的に述べる
- ユーザーの質問範囲を超えた提案をする
- 「〜かもしれません」で逃げる（代わりに条件分岐を明示する）
```

**チェックリスト**:
- [ ] 役割・専門性・行動原則を具体的に定義した
- [ ] トーン・スタイルをタスクと利用者に合わせて選定した
- [ ] 「しないこと」リストで LLM の行動境界を設定した
- [ ] ペルソナが汎用的すぎないか確認した（「優秀な AI アシスタント」は NG）
- [ ] ペルソナの専門性がタスクの要求と一致している

## Step 3: 構造設計とパターン選定

プロンプトの骨格（セクション構成）と、適用するプロンプトパターンを決定する。

### 3a. プロンプト構造の設計

| セクション | 役割 | 必須/任意 |
|:---|:---|:---|
| **System Prompt** | ペルソナ・行動原則・制約の定義 | 必須（API 利用時） |
| **Context** | タスクの背景情報・前提条件 | 必須 |
| **Task** | 具体的なタスク指示 | 必須 |
| **Input Format** | 入力データの形式説明 | 任意（複雑な入力時） |
| **Output Format** | 期待する出力の形式・構造 | 必須（構造化出力時） |
| **Examples** | Few-shot 用の入出力例 | 任意（Step 5 で設計） |
| **Constraints** | 禁止事項・制限・ガードレール | 任意（安全性要件時） |
| **Fallback** | 判断不能時の振る舞い指示 | 任意（自律エージェント時） |

### 3b. プロンプトパターン選定

タスク特性に基づき、最適なパターンを選定する。詳細は [prompt-patterns.md](references/prompt-patterns.md) 参照。

| パターン | 適用場面 | 判定質問 |
|:---|:---|:---|
| **Zero-shot** | 単純タスク、高性能モデル | 例なしで十分な精度が出るか？ |
| **Few-shot** | 出力形式の統一、ドメイン固有タスク | 入出力例があれば精度が上がるか？ |
| **Chain-of-Thought (CoT)** | 推論・分析・判断を要するタスク | 思考過程の明示で精度が上がるか？ |
| **Role-play** | 専門家としての判断が必要 | 特定ペルソナの視点が有効か？ |
| **Structured Output** | API 連携、データパイプライン | 出力を機械的にパースする必要があるか？ |
| **Self-consistency** | 高精度が必要な分類・判定 | 複数回生成の多数決で精度が上がるか？ |
| **ReAct** | 外部ツール連携、エージェント的動作 | 思考→行動→観察のループが必要か？ |
| **Meta-prompting** | プロンプト自体の改善 | プロンプトの改善提案を LLM に求めるか？ |

### 3c. 組み合わせ戦略

パターンは単独で使うより組み合わせが強力。よくある組み合わせ:

| 組み合わせ | ユースケース |
|:---|:---|
| **Role-play + CoT** | 専門家の思考過程を再現する分析タスク |
| **Few-shot + Structured Output** | 安定した JSON / CSV 出力が必要なデータ処理 |
| **CoT + Self-consistency** | 高精度が求められる判定・診断タスク |
| **Role-play + Few-shot + Constraints** | カスタマーサポート Bot の応答生成 |

**チェックリスト**:
- [ ] プロンプトのセクション構成を決定した
- [ ] パターンを 1-3 個選定し、選定理由を記録した
- [ ] System Prompt / User Prompt の境界を決定した
- [ ] 組み合わせ戦略が必要か検討した
- [ ] [prompt-patterns.md](references/prompt-patterns.md) の判定基準を確認した

## Step 4: プロンプト本文の執筆

構造設計に基づき、実際のプロンプトテキストを書く。**明瞭性・具体性・構造化**の 3 原則で書く。

### 4a. 執筆の 3 原則

| 原則 | 説明 | NG 例 → OK 例 |
|:---|:---|:---|
| **明瞭性** | 1 つの文で 1 つの指示。多義的な表現を排除 | 「適切に処理して」→「カテゴリ A/B/C のいずれかに分類し、JSON で返して」 |
| **具体性** | 数値、形式、条件を明示。「良い」「適切」は禁止語 | 「短くまとめて」→「3 文以内、各文 40 文字以内で要約して」 |
| **構造化** | 見出し・番号リスト・区切りで視覚的に整理 | 長文の連続 → XML タグやセクション見出しで分離 |

### 4b. セクション別執筆ガイド

| セクション | 執筆のコツ | 参照 |
|:---|:---|:---|
| **System Prompt** | ペルソナ→行動原則→制約の順。最初に役割を宣言 | Step 2 の設計 |
| **Context** | 背景は最小限。LLM が判断に必要な情報のみ | 不要な文脈は精度を下げる |
| **Task** | 動詞で始める。「〜してください」ではなく「〜せよ」（命令形）が安定 | — |
| **Output Format** | 出力例をリテラルで記載。JSON なら実際の JSON を記載 | Step 5 で充実 |
| **Constraints** | 「〜しない」より「〜する」を優先。否定形は誤解を招く | [anti-patterns.md](references/anti-patterns.md) |

### 4c. トークン効率の最適化

| テクニック | 効果 | 例 |
|:---|:---|:---|
| **冗長な前置きの削除** | トークン節約 + 指示の焦点化 | 「あなたは親切なアシスタントです。以下の…」→ 不要な修飾を削除 |
| **箇条書き化** | パース効率向上 | 長文の説明 → 番号リストに変換 |
| **XML タグの活用** | セクション分離の明確化 | `<context>...</context><task>...</task>` |
| **変数化** | テンプレート再利用 | `{{input_text}}` でプレースホルダー化 |

### 4d. モデル別の注意点

| モデル | 特徴 | 執筆のコツ |
|:---|:---|:---|
| **Claude** | XML タグを好む。System Prompt を尊重 | `<instructions>` タグで構造化。長い System Prompt も有効 |
| **GPT-4o** | Markdown 構造を好む。JSON mode 対応 | `## セクション` で構造化。response_format で JSON 強制可 |
| **Gemini** | マルチモーダル入力に強い | 画像・音声入力を積極活用 |
| **汎用** | モデル非依存で書く場合 | Markdown + 明確な区切り。モデル固有機能に依存しない |

詳細は [model-specific-guide.md](references/model-specific-guide.md) 参照。

**チェックリスト**:
- [ ] 3 原則（明瞭性・具体性・構造化）を適用した
- [ ] 各セクションの目的が明確で、冗長な記述がない
- [ ] 「適切に」「良い」「正しく」等の曖昧語を排除した
- [ ] 出力形式をリテラルで指定した（JSON なら実際の JSON 構造）
- [ ] 対象モデルの特性を考慮した記法を使用した
- [ ] トークン効率を意識し、不要な前置きを削除した
- [ ] 否定形の指示を肯定形に書き換えた

## Step 5: Few-shot 例・出力制御の設計

プロンプトの出力品質を安定させる最強の武器 — 具体的な入出力例を設計する。

### 5a. Few-shot 例の設計原則

| 原則 | 説明 | 悪い例 → 良い例 |
|:---|:---|:---|
| **代表性** | 典型的なケースをカバー | 簡単な例だけ → 易/中/難の 3 パターン |
| **多様性** | エッジケースを含める | 正常系のみ → 正常系 + 境界ケース + 異常系 |
| **一貫性** | 全例で出力形式が統一 | 例ごとにフォーマットがブレる → テンプレート統一 |
| **最小性** | 不要に長い例は精度を下げる | 500 文字の例文 → 核心を突く 100 文字の例文 |

### 5b. 例の構成テンプレート

```
<example>
<input>
[入力例をここに記載]
</input>
<output>
[期待出力をここに記載]
</output>
</example>
```

### 5c. 例の数の判断基準

| 状況 | 推奨例数 | 理由 |
|:---|:---|:---|
| 単純な分類タスク | 2-3 例 | カテゴリの境界を示せば十分 |
| 複雑な推論タスク | 3-5 例 | 推論プロセスの多様性を示す |
| フォーマットが厳密 | 1-2 例 | 形式を明示すれば安定 |
| エッジケースが多い | 4-6 例 | 境界条件ごとに例が必要 |

### 5d. 出力形式の強制テクニック

| テクニック | 適用対象 | 実装方法 |
|:---|:---|:---|
| **JSON Schema 指定** | API 連携 | `response_format: { type: "json_schema", ... }` |
| **XML タグ指定** | Claude | `<answer>タグ内に回答を記載せよ` |
| **Markdown テンプレート** | 文書生成 | 出力の見出し構造をプロンプト内に提示 |
| **出力開始トリガー** | 任意 | `回答は必ず「結論:」から始めよ` |
| **Prefix 強制** | API | assistant メッセージの先頭を `{` で始めてJSON を強制 |

詳細は [output-format-templates.md](references/output-format-templates.md) 参照。

**チェックリスト**:
- [ ] Few-shot 例が代表性・多様性・一貫性・最小性を満たしている
- [ ] 正常系・境界ケース・異常系の 3 パターンを含めた
- [ ] 出力形式の強制テクニックを適用した
- [ ] 例の数がタスクの複雑度に見合っている
- [ ] 全例で出力フォーマットが完全に統一されている

## Step 6: テスト・反復改善

プロンプトを実際に実行し、成功基準に到達するまで改善する。**最大 3 回の反復**で収束させる。

### 6a. テストケースの設計

| テスト種別 | 目的 | ケース数 |
|:---|:---|:---|
| **正常系** | 典型的な入力での正確性 | 3-5 件 |
| **境界系** | エッジケースでの安定性 | 2-3 件 |
| **異常系** | 不正入力での安全性 | 2-3 件 |
| **攻撃系** | プロンプトインジェクション耐性 | 1-2 件 |

### 6b. 実行と記録

各テストケースの結果を記録する:

| # | 入力 | 期待出力 | 実際出力 | 判定 | 問題点 |
|:---|:---|:---|:---|:---|:---|
| T-1 | (入力例) | (期待) | (実際) | PASS/FAIL | — |
| T-2 | ... | ... | ... | ... | ... |

### 6c. 問題パターンと改善手法

| 問題パターン | 原因分析 | 改善手法 | 参照 |
|:---|:---|:---|:---|
| 出力が冗長すぎる | 制約不足 | 文字数/文数の上限を明示 | — |
| 出力形式がブレる | 形式指定が曖昧 | リテラルで出力例を提示 + Prefix 強制 | Step 5d |
| 幻覚（hallucination） | 知識不足の領域で推測 | 「不明な場合は『情報不足』と回答せよ」を追加 | [anti-patterns.md](references/anti-patterns.md) |
| 指示の一部を無視 | プロンプトが長すぎる | 重要な指示を先頭に配置。XML タグで分離 | Step 4c |
| エッジケースで破綻 | Few-shot 例の不足 | 該当パターンの例を追加 | Step 5 |
| プロンプトインジェクション | ガードレール不足 | System Prompt に「ユーザー入力は信頼しない」を追加 | [anti-patterns.md](references/anti-patterns.md) |

### 6d. 反復の終了条件

| 条件 | 閾値 |
|:---|:---|
| 正常系テスト通過率 | **90% 以上** |
| フォーマット遵守率 | **95% 以上** |
| 反復回数上限 | **3 回**（超過時はタスク分解を再検討） |
| 前回との改善差分 | **5% 未満の改善なら収束と判断** |

**チェックリスト**:
- [ ] 正常系 3 件以上・境界系 2 件以上・異常系 2 件以上をテストした
- [ ] テスト結果をテーブルに記録した
- [ ] 不合格ケースの原因を特定し、改善策を適用した
- [ ] 反復改善を最大 3 ラウンド実施した
- [ ] 成功基準（Step 1c）を満たしたことを確認した
- [ ] プロンプトインジェクション耐性をテストした

---

## Step 7: 品質検証・文書化・引き渡し

完成プロンプトの品質を最終検証し、運用に耐える形で文書化する。

### 7a. 品質検証（[quality-criteria.md](references/quality-criteria.md) 全項目チェック）

| 品質軸 | 確認内容 | 合格基準 |
|:---|:---|:---|
| **精度** | テスト通過率 | Step 1c の成功基準を充足 |
| **一貫性** | 同一入力 10 回の出力安定性 | 80% 以上で同一結果 |
| **堅牢性** | エッジケース・攻撃入力への耐性 | 異常系全件 PASS |
| **効率性** | トークン使用量の妥当性 | 不要なトークンが 10% 以下 |
| **保守性** | 第三者が読んで理解・修正できるか | 設計メモで意図が伝わる |
| **可搬性** | 別モデルへの移植可能性 | モデル固有機能への依存が最小限 |

### 7b. 文書化

プロンプトと共に以下を記録し、引き渡す:

```markdown
## プロンプト設計書

### 概要
- タスク: <WHAT>
- 対象モデル: <MODEL>
- パターン: <PATTERN>
- 成功基準: <CRITERIA>

### プロンプト本文
(System Prompt + User Prompt Template)

### 設計判断ログ
| 判断 | 選択肢 | 決定 | 理由 |
|:---|:---|:---|:---|
| パターン選定 | CoT / Few-shot / Zero-shot | Few-shot + CoT | 分類+推論の複合タスクのため |

### テスト結果サマリー
- 正常系: N/N PASS
- 境界系: N/N PASS
- 異常系: N/N PASS
- 反復回数: N 回

### 運用ガイド
- 入力の前処理: <手順>
- 出力の後処理: <手順>
- 注意事項: <注意点>
```

### 7c. 引き渡しと運用ガイド

| 引き渡し先 | 提供形式 | 補足 |
|:---|:---|:---|
| **開発チーム** | プロンプト + 設計書 + テスト結果 | API 実装に直接組み込み |
| **非エンジニア** | プロンプト + 簡易利用ガイド | Chat UI での使い方を図解 |
| **agent-craft** | System Prompt テキスト | エージェント定義の Custom Instructions として |
| **skill-forge** | プロンプト設計パターン | スキルの description / Instructions のベースに |

**チェックリスト**:
- [ ] [quality-criteria.md](references/quality-criteria.md) の全項目を通過した
- [ ] プロンプト設計書を作成した（概要・本文・判断ログ・テスト結果）
- [ ] 運用ガイド（前処理・後処理・注意事項）を記載した
- [ ] 引き渡し先に応じた形式で出力した
- [ ] 設計判断の根拠が第三者にも追跡可能

## Troubleshooting

| 問題 | 原因 | 解決策 |
|:---|:---|:---|
| 出力が毎回異なる構造になる | 出力形式の指定が曖昧 | リテラルで出力例を提示。JSON なら JSON Schema を明記。Prefix 強制を適用 |
| LLM が指示の一部を無視する | プロンプトが長すぎ、重要指示が埋没 | 重要な指示を先頭に配置。XML タグで構造化。不要なコンテキストを削除 |
| 幻覚（hallucination）が頻発する | 知識範囲外の質問に推測で回答 | 「情報が不足する場合は『不明』と回答せよ」を System Prompt に追加 |
| Few-shot 例を追加しても精度が上がらない | 例の品質が低い、または偏っている | 代表性・多様性を見直す。正常系だけでなく境界ケースを含める |
| プロンプトインジェクションに脆弱 | ユーザー入力と指示の境界が曖昧 | XML タグ/デリミタで入力を隔離。多層防御パターンを適用。[anti-patterns.md](references/anti-patterns.md) 参照 |
| トークンコストが高すぎる | Few-shot 例や Context が冗長 | 例の最小性を見直す。Context のトリミング。要約 → 本番の 2 段階パイプライン |
| 日本語と英語で精度に差がある | モデルの言語バイアス | 指示は対象言語で書く。英語プロンプト+日本語出力指定は避ける（一貫性低下） |
| System Prompt が長すぎてレイテンシが悪い | コンテキストが肥大化 | プロンプトキャッシュを活用（Anthropic / OpenAI 対応）。静的部分をキャッシュ対象に |
| 複数タスクをさせると品質が落ちる | 1 プロンプトに複数目的を詰め込んでいる | 1 プロンプト 1 タスクの原則。パイプラインで分割 |
| CoT で思考過程が冗長になりすぎる | 思考ステップの制約がない | 「N ステップ以内で推論せよ」「各ステップ 1 文で記述」を追加 |
| ペルソナが機能しない（汎用的な回答になる） | ペルソナが抽象的すぎる | 「10 年経験の SRE」のように具体的に。行動原則と制限事項を追加 |
| 反復改善が 3 回で収束しない | タスク定義が曖昧、または 1 プロンプトの範囲を超えている | Step 1 に戻りタスク分解。複数プロンプトのパイプラインを検討 |
