# Skill: Data Validation

> **Garbage In, Garbage Out を防ぐ最後の砦**

CRITICAL: 本スキル実行時は、対象案件の `projects/<案件名>/` を明示すること。

## Instructions

### ワークフロー内の位置

```
pdf-convert → [data-validation] → distill → review
                    ↑ ↓
              01_inbox/ or 02_notes/ or 03_spec/ のデータ検証
```

### 入力

| ソース | パス | 検証対象 |
|:---|:---|:---|
| inbox のテーブルデータ | `projects/<案件名>/01_inbox/*.md` | PDF 変換された Markdown テーブル |
| notes のスキーマ定義 | `projects/<案件名>/02_notes/domain-model.md` | エンティティ定義の論理的整合性 |
| notes のビジネスルール | `projects/<案件名>/02_notes/business-rules.md` | ルール間の矛盾・欠落 |
| spec の見積・数値 | `projects/<案件名>/03_spec/*.md` | 工数、金額、SLA の整合性 |
| CSV データ | 任意のパス | 生データの品質チェック |

### 出力

- **検証レポート**: 検出された問題の一覧（Markdown 形式）
- **修正済みデータ（オプション）**: 自動修正可能な問題の修正版

---

## Step 1: 検証対象の特定

検証すべきデータの種類と場所を特定し、検証の厳密度（strict / lenient）を決定する。

```
検証対象は？
  ├── PDF 変換後のテーブル → Step 2a: テーブル構造検証
  ├── CSV / Excel データ  → Step 2b: データ品質検証
  ├── ドメインモデル定義   → Step 2c: スキーマ整合性検証
  ├── ビジネスルール       → Step 2d: ルール整合性検証
  └── 提案書内の数値       → Step 2e: 数値整合性検証
```

---

## Step 2a: テーブル構造検証（PDF 変換後）

`pdf-convert` で生成された Markdown テーブルの品質を確認する。

**チェックリスト**:
- テーブルのヘッダー行が正しく認識されているか
- 列数が全行で一致しているか
- セル結合が崩れて空セルになっていないか
- 数値データの桁区切り・小数点が正しいか
- 日付データのフォーマットが統一されているか
- 元の PDF と Markdown テーブルの値が一致するか（サンプリング検証）

---

## Step 2b: データ品質検証（CSV / Excel）

**チェックリスト**:
- 全行でカラム数が一致しているか
- 必須フィールドに NULL / 空文字がないか
- データ型が期待通りか（数値フィールドに文字列が混入していないか）
- 数値の範囲は妥当か（負のage、未来の日付等がないか）
- 一意制約を満たしているか（ID の重複がないか）
- 文字コードは統一されているか（UTF-8 推奨）
- 欠損値のパターンに規則性はあるか（特定列に集中等）

---

## Step 2c: スキーマ整合性検証（ドメインモデル）

`02_notes/domain-model.md` のエンティティ定義を論理的に検証する。

**チェックリスト**:
- すべてのエンティティに主キー（PK）が定義されているか
- 外部キー（FK）の参照先エンティティが存在するか
- データ型がドメインに適切か（例: 金額に INTEGER ではなく DECIMAL）
- NOT NULL / UNIQUE 制約が適切に設定されているか
- エンティティ間の関係（1:1, 1:N, N:M）が論理的に正しいか
- 循環参照が発生していないか
- 正規化のレベルは適切か

---

## Step 2d: ルール整合性検証（ビジネスルール）

`02_notes/business-rules.md` のルール間の論理的整合性を検証する。

**チェックリスト**:
- すべてのルールに一意 ID が付与されているか
- ルール間に矛盾がないか（例: BR-001「必須」vs BR-005「任意」）
- ルールが参照するエンティティ・属性が domain-model.md に存在するか
- 出典（RFP の該当箇所）が明記されているか
- 例外ケースが網羅されているか
- ルールの優先順位が定義されているか（矛盾時の解決策）

---

## Step 2e: 数値整合性検証（提案書内）

`03_spec/` 内の数値（工数、金額、SLA 目標値等）が整合しているか検証する。

**チェックリスト**:
- 工数の合計が各章で一致しているか
- 金額の積算根拠と合計が一致しているか
- SLA 目標値が技術章のアーキテクチャで実現可能か
- スケジュールの工程間に論理的な依存関係が成立しているか
- 人員計画 x 単価 x 期間 = 見積金額が成立しているか
- 消費税・諸経費の計算が正しいか

---

## Step 3: 検証結果のレポート

レポートは以下の構造で出力する。詳細なテンプレートと指摘例は [references/report-templates.md](references/report-templates.md) を参照。

**レポート構造**:
1. **メタ情報**: 案件名、検証対象、検証種別、検証日
2. **結果サマリー**: 総合判定（Valid / Conditional / Invalid）、深刻度別件数
3. **検出された問題**: 問題の一覧（深刻度、箇所、影響、修正案）
4. **推奨アクション**: Critical → 即修正、Major → 修正後再検証、Minor → 修正推奨

**深刻度レベル**:

| レベル | 定義 | 対応 |
|:---|:---|:---|
| Critical | データ損失・誤計算リスク | 即座に修正必須 |
| Major | 論理的矛盾 | 修正後に再検証 |
| Minor | 品質改善 | 修正推奨 |
| Info | 推奨事項 | 参考情報 |

## Troubleshooting

| 問題 | 原因 | 対処 |
|:---|:---|:---|
| CSV の文字化け | 文字コード不一致（Shift_JIS vs UTF-8） | UTF-8 に変換してから検証 |
| テーブルの列数が動的 | セル結合の PDF 変換崩れ | 元 PDF を参照して手動修正後に再検証 |
| スキーマの循環参照 | 設計ミス | 関係を見直し、中間エンティティで解決 |
| ルール間矛盾が解決不能 | RFP 自体に矛盾 | 顧客に確認し、ADR に仮定を記録 |
| 大量データで検証が遅い | データ量過多 | サンプリング検証に切り替え |
