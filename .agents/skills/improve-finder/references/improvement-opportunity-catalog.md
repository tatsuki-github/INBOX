# improvement-opportunity-catalog.md

> 7 次元別の改善機会検出シグネチャ集。improve-finder Phase 3〜5 の実行リファレンス。
> 各シグネチャは「検出方法」と「改善方向」がセットで記録されている。

---

## 次元 1: コード可読性・保守性

> **原則**: コードは書く時間より読む時間の方が長い。未来の自分が即座に意図を理解できるか？

| # | 改善パターン | 検出シグネチャ | 改善方向 |
|:---|:---|:---|:---|
| R-01 | 意味不明な命名 | 変数名が 1〜2 文字、略語（`tmp`, `val`, `res`）、非ドメイン語（`data`, `item`） | ドメイン語で命名（`orderItem`, `currentUser`）|
| R-02 | DRY 違反（重複ロジック） | 同一・類似ロジックが 2 箇所以上に分散 | 共通関数・フック・ユーティリティに抽出 |
| R-03 | マジックナンバー・文字列 | `if (status === 2)`, `timeout: 30000` 等の説明なしリテラル | 定数・enum ライクなリテラルユニオンで命名 |
| R-04 | 長すぎる関数 | 30 行超の関数、複数の `return` や副作用が混在 | 単一責務原則（SRP）に従い分割・抽出 |
| R-05 | 深すぎるネスト | インデントが 4 段以上 | ガード節（早期 return）・プロミスチェーン・flatMap で平坦化 |
| R-06 | コメントアウトされたコード | `// const oldFn = ...` が残存 | 削除（git で復元可能）|
| R-07 | 不要なコメント | 「インクリメントする」等のコードの繰り返し | why（なぜ）を説明するコメントに変更 |
| R-08 | 不整合な命名規則 | `getUserData` と `fetch_order` が混在（camelCase と snake_case）| プロジェクト規約に統一 |

## 次元 2: アーキテクチャ

> **原則**: 変更容易性こそがアーキテクチャの本質。「1 箇所変えたら 10 箇所壊れる」は設計の失敗。

| # | 改善パターン | 検出シグネチャ | 改善方向 |
|:---|:---|:---|:---|
| A-01 | 責務過多コンポーネント | 1 ファイルに UI 描画・ビジネスロジック・API 呼び出し・状態管理が混在 | レイヤー分離（UI / ロジック / データ層）|
| A-02 | 循環依存 | モジュール A → B → A の依存サイクル（`import` を追跡） | 依存関係の整理・抽象インターフェースの導入 |
| A-03 | 高結合 | 1 ファイルが 10 ファイル以上を直接 import している | 依存性逆転・ファサードパターンの導入 |
| A-04 | デッドコード | 参照ゼロの関数・クラス・変数・export（IDE の参照検索で確認）| 削除（保守コストの軽減）|
| A-05 | 過度な抽象化 | 1 度しか使わない抽象層・インターフェース | YAGNI 原則に従い削除・直接実装に戻す |
| A-06 | God Object / 巨大クラス | 500 行超のクラス、10 を超えるパブリックメソッド | 責務単位でクラス分割 |
| A-07 | 設定のハードコード | API URL・タイムアウト値・エンドポイントが直書き | 環境変数・設定ファイルに移動 |
| A-08 | 依存の方向の誤り | 下位レイヤー（DB 層）が上位レイヤー（API 層）に依存 | クリーンアーキテクチャの依存方向に修正 |

## 次元 3: 型安全性

> **原則**: 有効な状態のみ表現できる型を設計すれば、バグが生まれる余地が消える。

### TypeScript

| # | 改善パターン | 検出シグネチャ | 改善方向 |
|:---|:---|:---|:---|
| T-01 | `any` の使用 | `any` 型が変数・引数・戻り値に使われている | `unknown` + 型ガード、または具体型に置換 |
| T-02 | `enum` の使用 | `enum OrderStatus { ... }` | リテラルユニオン型 `type OrderStatus = 'pending' \| 'shipped'` |
| T-03 | boolean フラグ地獄 | `isLoading: boolean; isError: boolean; isSuccess: boolean` の複数フラグ | タグ付きユニオン型 `type State = { status: 'loading' } \| { status: 'error'; error: Error } \| { status: 'success'; data: T }` |
| T-04 | 型アサーションの乱用 | `as SomeType` が頻出、特に `as any` | 型ガード関数 `isSomeType(x): x is SomeType` に変換 |
| T-05 | 戻り値型の未明示 | パブリック API の関数に戻り値型アノテーションがない | `: ReturnType` を明示（Effective TypeScript Item 19）|
| T-06 | never 型チェック欠如 | switch 文の default に `never` 型チェックがない | `const _exhaustive: never = value` パターンで網羅性保証 |
| T-07 | optional chaining の欠落 | `obj.a.b.c` のような深いアクセスに null チェックがない | `obj?.a?.b?.c` + nullish coalescing `??` |
| T-08 | Index Signature の乱用 | `[key: string]: any` がオブジェクト型に使われている | `Record<K, V>` または具体的なキー型に変換 |

### Python

| # | 改善パターン | 検出シグネチャ | 改善方向 |
|:---|:---|:---|:---|
| P-01 | 型ヒントの欠如 | 関数引数・戻り値に型ヒントがない | `def process(user: User) -> OrderResult:` を追加 |
| P-02 | `Optional` の未使用 | `None` を返す可能性があるが戻り値型に `Optional[T]` がない | `Optional[str]` または `str \| None`（3.10+）を追加 |
| P-03 | 型の `Any` 依存 | `from typing import Any` が多用されている | 具体的な TypeVar・Protocol・dataclass に移行 |
| P-04 | Union 型の未活用 | 複数の型を受け取る関数に型ヒントがない | `Union[int, str]` または `int \| str`（3.10+）を追加 |

## 次元 4: パフォーマンス

> **原則**: 遅い箇所を計測してから最適化せよ。推測ではなく計測が最適化の起点。

| # | 改善パターン | 検出シグネチャ | 改善方向 |
|:---|:---|:---|:---|
| P-01 | N+1 問題（DB） | ループ内の DB クエリ（`for user in users: db.query(...)`)| バッチ取得 / Eager Loading / `SELECT IN` |
| P-02 | N+1 問題（API） | ループ内の外部 API 呼び出し | `Promise.all()` でバッチ並列実行 |
| P-03 | メモ化欠如（React） | 重い計算が毎レンダリング実行、親の re-render で子が再描画 | `useMemo` / `useCallback` / `React.memo` |
| P-04 | 同期ブロッキング | 重い同期処理（ファイル IO・画像処理）がメインスレッドをブロック | 非同期 / Web Worker / バックグラウンドタスク |
| P-05 | バンドル肥大 | 巨大ライブラリの全量 import（`import * as _`） | Named import / Dynamic import / 軽量代替ライブラリ |
| P-06 | 不必要なデータ取得 | 全フィールドを SELECT しているが使うのは 2-3 フィールドのみ | SELECT の絞り込み / GraphQL フラグメント |
| P-07 | キャッシュの欠如 | 同じ重いクエリ・計算が毎リクエスト実行される | メモ化 / Redis / HTTP キャッシュヘッダー |
| P-08 | 不要な再レンダリング | Context の更新で無関係なコンポーネントが再描画 | Context の分割 / Zustand / Jotai 等へ移行検討 |

## 次元 5: UX/UI

> **原則**: ユーザーはデザインを見ない。問題が起きたときだけデザインに気づく。

### Laws of UX 違反パターン

| # | 法則 | 改善パターン | 症状 |
|:---|:---|:---|:---|
| U-01 | Miller's Law | 情報過密 | 1 画面の選択肢・項目が 7 個以上 |
| U-02 | Hick's Law | 意思決定の遅延 | ドロップダウンの選択肢が 10 個以上でグルーピングなし |
| U-03 | Fitts's Law | タップミスの多発 | インタラクティブ要素が 44px 未満 |
| U-04 | Jakob's Law | 学習コストの高さ | 業界標準とは異なる独自の操作フロー |
| U-05 | Peak-End Rule | 達成感の欠如 | フォーム完了・注文完了後の演出がない |
| U-06 | Doherty Threshold | ユーザー離脱 | 操作への応答が 400ms を超える（ローディング状態なし）|

### アクセシビリティ / WCAG AA

| # | 基準 | 改善パターン | 症状 |
|:---|:---|:---|:---|
| W-01 | WCAG 1.4.3 | コントラスト比不足 | 通常テキストのコントラスト比が 4.5:1 未満 |
| W-02 | WCAG 4.1.2 | aria-label 欠如 | ボタン・リンクに説明ラベルがない |
| W-03 | WCAG 2.1.1 | キーボード操作不可 | マウスがないと操作できない UI |
| W-04 | WCAG 2.4.7 | フォーカス表示なし | focus-visible スタイルがない |
| W-05 | WCAG 1.4.11 | 非テキストコントラスト不足 | アイコン・フォームの境界線が 3:1 未満 |

### デザイントークン / 一貫性

| # | 改善パターン | 検出シグネチャ | 改善方向 |
|:---|:---|:---|:---|
| D-01 | ハードコード色値 | `color: #1a1a2e` 等が CSS に直書き | CSS カスタムプロパティ（変数）に移行 |
| D-02 | スペーシング不統一 | `padding: 13px`, `margin: 7px` 等の任意値 | 4px ベースのスケール（4, 8, 12, 16, 24, 32...）に統一 |
| D-03 | 複数の同目的コンポーネント | ボタンが `Button`, `ActionButton`, `CTAButton` と複数存在 | 統一コンポーネントに集約 |

## 次元 6: テストカバレッジ

> **原則**: テストのないコードは、「動いている」ではなく「まだ壊れたと気づいていない」。

| # | 改善パターン | 検出シグネチャ | 改善方向 |
|:---|:---|:---|:---|
| E-01 | テスト不在のビジネスロジック | 重要なサービス・ユースケース関数にテストファイルなし | ユニットテストを優先追加 |
| E-02 | ハッピーパスのみ | テストが正常系 1 ケースのみ | 異常系・境界値（null/0/MAX）テストを追加 |
| E-03 | 統合テストの欠如 | UI → API → DB の結合フローがテストされていない | 統合テスト・E2E テストを追加 |
| E-04 | 意図不明なテスト名 | `it('works')`, `test('test1')` 等 | BDD: `it('should return error when email is invalid')` に改名 |
| E-05 | 実装詳細への依存 | `wrapper.instance().privateMethod()` のような内部へのアクセス | 振る舞いベースのテストに書き直し |
| E-06 | スナップショットのみ | Jest スナップショットテストだけで動作を検証していない | 意味のある assertion を追加 |

## 次元 7: 観測可能性・ドキュメント

> **原則**: 本番で障害が起きたとき、ログがなければ「何が起きたか」を知る術がない。

| # | 改善パターン | 検出シグネチャ | 改善方向 |
|:---|:---|:---|:---|
| O-01 | 非構造化ログ | `console.log('error:', e)` のみ、JSON 形式でない | 構造化ログ（`logger.error({ userId, error: e.message })`）|
| O-02 | メトリクスの欠如 | 重要な処理（決済・認証・バッチ）にメトリクスがない | `recordMetric('payment.processed', duration)` を追加 |
| O-03 | 不明瞭なエラーメッセージ | `throw new Error('something went wrong')` | `throw new Error(\`Payment failed for orderId: ${orderId}\`)` |
| O-04 | JSDoc の欠如 | 複雑な公開関数に説明・型・引数ドキュメントがない | JSDoc / Docstring を追加 |
| O-05 | README の陳腐化 | README が現在の実装と異なる | README を実装に合わせて更新 |
| O-06 | 型定義のドキュメント欠如 | 複雑な型定義（Union・Intersection）に説明コメントがない | `/** @description ... */` でドキュメントを追加 |
