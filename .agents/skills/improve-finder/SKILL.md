# Skill: Improve Finder（コード能動スキャン → 改善機会発見）

> **壊れていなくても磨ける — 改善機会は黙って待ち続けている**

## Instructions

### ワークフロー内の位置

各 Phase の完了時に **review スキル** による Review Gate を通過してから次の Phase に進む。
Gate を通過できなかった場合は、該当 Phase に戻って修正する。
これにより、**偽陽性・証拠不足・優先付けの歪みを発見途中で排除**し、最終レポートの信頼性を担保する。

```
リポジトリ / ディレクトリ / ファイル（コードパス指定）
  ↓
[improve-finder]
  ├─ Phase 1: スキャン対象の定義とスコープ確定
  │   └─ 📋 Review Gate 1（スコープ定義の完全性・改善観点の適切性レビュー）
  ├─ Phase 2: コードベース構造把握と改善機会ゾーン特定
  │   └─ 📋 Review Gate 2（構造把握の網羅性・改善ゾーン優先順位の妥当性レビュー）
  ├─ Phase 3: コード品質・アーキテクチャ改善機会スキャン
  │   │         [software-architecture + deep-research 委譲]
  │   └─ 📋 Review Gate 3（改善機会候補の証拠・具体性・偽陽性除外レビュー）
  ├─ Phase 4: 型安全性・パフォーマンス改善機会スキャン
  │   │         [effective-typescript + robust-python 委譲]
  │   └─ 📋 Review Gate 4（型強化・最適化候補の実現可能性・優先性レビュー）
  ├─ Phase 5: UX/UI・テスト・観測可能性改善機会スキャン
  │   │         [ux-psychology + ui-design + test 委譲]
  │   └─ 📋 Review Gate 5（UX/UI・テスト改善候補の証拠・影響範囲レビュー）
  └─ Phase 6: 改善機会の分類・優先度付け・レポート出力
              [decision-framework 委譲]
      └─ 📋 Review Gate 6（最終レポートの総合品質・優先付けの合理性レビュー）
  ↓
改善機会レポート（優先度別 / 7次元別 / ファイル:行番号付き）
  ↓
improve-flow（改善の設計・実装ワークフローに引き継ぎ）
```

### 入力

| 入力 | 説明 | 例 |
|:---|:---|:---|
| スキャン対象パス | リポジトリルート、ディレクトリ、またはファイルパス | `./src/`, `./components/`, リポジトリ全体 |
| フォーカス次元（任意） | 特定の改善次元を優先する | `architecture`, `type-safety`, `ux`, `test-coverage` |
| 除外パス（任意） | スキャン対象から除外するパス | `node_modules/`, `*.test.ts`, `dist/` |
| 言語（任意） | 対象言語が明示される場合 | `TypeScript`, `Python`, `Go` |
| 技術スタック（任意） | フレームワーク・ライブラリ情報 | `Next.js + React`, `FastAPI`, `Go + Gin` |

### 出力

| 出力 | 形式 | 説明 |
|:---|:---|:---|
| 改善機会レポート | Markdown | 優先度別・7次元別の改善機会一覧（ファイル:行番号付き）|
| スキャンサマリー | テーブル | High/Medium/Low の件数と優先対応推奨 |
| 改善優先度マップ | 箇条書き | Impact × Effort マトリクスによる推奨実施順序 |
| improve-flow 引き継ぎパック | 箇条書き | improve-flow の Phase 0 に渡すスコープ・成功基準・課題リスト |

## Phase 1: スキャン対象の定義とスコープ確定

スキャン範囲を明確にし、「改善」の観点で対象を適切に絞る。**スコープが曖昧なまま進むと、改善機会が偽陽性や見落としで信頼性を失う**。

### 1a. 対象パスの特定と言語検出

| 確認項目 | 判断基準 |
|:---|:---|
| パスの存在確認 | 存在しない場合はユーザーに再確認 |
| 対象タイプ判定 | ファイル / ディレクトリ / リポジトリルートでスキャン戦略を変える |
| 言語・技術スタック自動検出 | 拡張子・設定ファイル（package.json, pyproject.toml 等）で特定 |
| ファイル数・規模 | 50 以下: 全件精査 / 50〜100: 高改善余地優先 / 100 超: コア + 直近変更に絞る |

### 1b. 改善スキャンの 7 次元とフォーカス設定

| 次元 | スキャン内容 | 委譲スキル |
|:---|:---|:---|
| **1. コード可読性・保守性** | 命名・DRY 違反・コードの匂い・重複 | software-architecture |
| **2. アーキテクチャ** | 責務分離・結合度・循環依存・モジュール境界 | software-architecture |
| **3. 型安全性** | any/enum 除去機会・タグ付きユニオン導入余地 | effective-typescript |
| **4. パフォーマンス** | N+1・メモ化機会・不要な再レンダリング・クエリ最適化 | effective-typescript + deep-research |
| **5. UX/UI** | Laws of UX 準拠・アクセシビリティ・デザイントークン統一 | ux-psychology + ui-design |
| **6. テストカバレッジ** | テストが薄い箇所・テスト不在のビジネスロジック | test |
| **7. 観測可能性・ドキュメント** | ログ・メトリクス・ドキュメント不足・エラーメッセージ品質 | deep-research |

### 1c. 除外スコープの設定

以下のパスは原則スキャン対象外（ユーザー指定で変更可）:

```
デフォルト除外:
- node_modules/, vendor/, .venv/, __pycache__/
- *.test.ts, *.spec.py, *_test.go（改善スキャンの対象は本番コード）
- *.generated.ts, *.pb.go（生成コード）
- dist/, build/, .next/（ビルド成果物）
```

**チェックリスト**:
- [ ] スキャン対象パスを特定し、存在を確認した
- [ ] 言語・技術スタックを特定した
- [ ] ファイル数・規模を把握し、スキャン戦略を決定した
- [ ] フォーカス次元（指定がない場合は全 7 次元）を設定した
- [ ] 除外スコープを設定した

### 📋 Review Gate 1: スコープ定義の完全性・改善観点の適切性レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Phase 2 に進む。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| スコープの網羅性 | A-1（要件カバレッジ） | ユーザー指定の対象が漏れなくスキャン対象に含まれているか |
| 7 次元の適切性 | A-2（章間整合性） | 技術スタックに対して不適切な次元が含まれていないか |
| 機密ファイルの配慮 | B-4（プライバシー） | `.env`・シークレットファイルをスキャンする場合、機密情報をレポートに含めない方針が確認されているか |

**通過条件**: Critical / Major 指摘がゼロ。Minor 指摘は記録して続行可。

**不合格時**: 指摘に基づきスコープを修正し、Phase 1a から再確認する。

## Phase 2: コードベース構造把握と改善機会ゾーン特定

コードの全体像を把握し、**改善余地が大きい箇所**（技術的負債・複雑度・テスト薄・型不安全）を優先スキャン対象として特定する。

### 2a. ファイル構造の探索

| 確認対象 | 目的 |
|:---|:---|
| コアビジネスロジック集中箇所 | 改善の影響が最大（services/, domain/, handlers/ 等）|
| 最近変更された箇所 | git log で直近 2 週間以内の変更ファイルを特定 |
| 大規模コンポーネント・モジュール | 500 行超のファイル（責務分離の機会） |
| データアクセス層 | N+1・クエリ最適化の主戦場 |
| UI コンポーネント | デザイントークン統一・アクセシビリティ改善の機会 |

### 2b. 改善余地指標による優先ファイル特定

| 改善余地指標 | 判断基準 |
|:---|:---|
| LOC が多い | 500 行超のファイル（責務分離の機会） |
| 関数の複雑度が高い | 深いネスト・多数の条件分岐 |
| `any` / 型アサーションが多い | 型安全性改善の機会 |
| テストがない / カバレッジが低い | テスト強化の機会 |
| `TODO / FIXME` コメントが多い | 既知の改善課題の集積 |
| コメント・JSDoc が少ない | ドキュメント充実の機会 |

**チェックリスト**:
- [ ] ファイル構造を把握し、コアビジネスロジックを特定した
- [ ] 改善余地が高いファイル（LOC・複雑度・型不安全）を特定した
- [ ] `TODO / FIXME` コメントの箇所をリストアップした
- [ ] スキャン優先順位を決定した（改善余地の高い順に並べた）

### 📋 Review Gate 2: 構造把握の網羅性・改善ゾーン優先順位の妥当性レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Phase 3 に進む。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| 高改善余地ゾーンの網羅性 | A-1（要件カバレッジ） | コアビジネスロジック・型不安全箇所・テスト薄い箇所が改善ゾーンリストに含まれているか |
| 優先順位の整合性 | A-2（章間整合性） | 高改善余地と判断した根拠（LOC・複雑度・型安全性）がスキャン優先順位と一致しているか |
| TODO/FIXME の網羅 | A-3（数値妥当性） | 既知の改善課題（TODO/FIXME）がリストに含まれているか |

**通過条件**: Critical / Major 指摘がゼロ。

**不合格時**: 指摘に基づき改善ゾーンリストを補完し、Phase 2a から再確認する。

## Phase 3: コード品質・アーキテクチャ改善機会スキャン

**software-architecture + deep-research に委譲**

「動いているが設計上の改善余地がある」箇所を発見する。

### 3a. コード可読性・保守性の改善機会

| 改善パターン | 検出方法 |
|:---|:---|
| **命名が不明確** | 1 文字変数・略語・非ドメイン語（`tmp`, `data`, `item` 等） |
| **DRY 違反** | 同一ロジックの複数箇所への分散（コピペされたバリデーション等） |
| **マジックナンバー** | 説明なしの数値リテラル（`if (status === 2)` 等） |
| **長すぎる関数** | 30 行超・複数の責務を持つ関数 |
| **深すぎるネスト** | 4 段以上のインデント（ガード節・早期リターンへの変換機会）|

詳細な検出シグネチャは [improvement-opportunity-catalog.md](references/improvement-opportunity-catalog.md) の「コード可読性」セクション参照。

### 3b. アーキテクチャ改善機会（software-architecture に委譲）

| 改善パターン | 検出方法 | 改善方向 |
|:---|:---|:---|
| **責務過多コンポーネント** | 1 ファイルに UI・ビジネスロジック・API 呼び出しが混在 | レイヤー分離 |
| **循環依存** | モジュール A → B → A の依存サイクル | 依存関係の整理 |
| **高結合** | 多数のファイルを直接 import する | インターフェース抽象化 |
| **デッドコード** | 参照されていない関数・クラス・変数 | 削除による保守性向上 |
| **過度な抽象化** | 1 度しか使わない抽象層 | 単純化の機会 |

### 3c. ベストプラクティスとのギャップ調査（deep-research に委譲）

特定した改善機会に対して、業界標準の解決パターンを「標準」レベルで調査する。

**チェックリスト**:
- [ ] 命名・DRY・マジックナンバーの改善機会を特定した
- [ ] アーキテクチャの問題（責務過多・循環依存・高結合）を特定した
- [ ] デッドコードを特定した
- [ ] 各改善機会にファイル:行番号の証拠を付けた
- [ ] ベストプラクティスとのギャップを調査した（必要な場合）

### 📋 Review Gate 3: 改善機会候補の証拠・具体性・偽陽性除外レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Phase 4 に進む。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| 候補の証拠の具体性 | A-3（数値妥当性） | 各候補に「どのファイル:行番号で、何が問題か」が記録されているか |
| 偽陽性の除外 | A-2（章間整合性） | 「意図的な設計（許容されたトレードオフ）」が誤って改善候補に含まれていないか |
| 影響の評価 | B-5（Performance & Scalability） | 各改善機会の改善後の影響（保守性・可読性向上度）が評価されているか |

**通過条件**: Critical / Major 指摘がゼロ。「証拠なし」は Major 扱い。

**不合格時**: 証拠不足の候補を再調査するか偽陽性として除外し、Phase 3a から再スキャンする。

## Phase 4: 型安全性・パフォーマンス改善機会スキャン

**effective-typescript + robust-python に委譲**

### 4a. 型安全性の改善機会（effective-typescript に委譲）

| 改善パターン | 検出方法 | 改善方向 |
|:---|:---|:---|
| **`any` の使用** | `any` 型が使われている箇所 | `unknown` + 型ガード、または具体型に置換 |
| **`enum` の使用** | TypeScript `enum` | リテラルユニオン型に変換 |
| **boolean フラグ地獄** | `isLoading + isError + isSuccess` の複数フラグ | タグ付きユニオン型に変換 |
| **型アサーションの乱用** | `as SomeType` が多い | 型ガード関数に変換 |
| **戻り値型の未明示** | パブリック API に戻り値型がない | 明示的な戻り値型を追加 |
| **never 型チェック欠如** | switch 文に網羅性チェックがない | `never` 型で網羅性を保証 |

Python の場合は robust-python に委譲し、型ヒント（`Optional`, `Union`, `TypeVar` 等）の追加機会を検出する。

### 4b. パフォーマンス改善機会

| 改善パターン | 検出方法 | 改善方向 |
|:---|:---|:---|
| **N+1 問題** | ループ内の DB クエリ・API 呼び出し | バッチ取得・Eager Loading |
| **メモ化欠如** | 重い計算が毎回実行される | `useMemo` / `useCallback` / `React.memo` |
| **不要な再レンダリング** | 親の再レンダリングで子が毎回再描画 | メモ化・コンポーネント分割 |
| **同期ブロック** | 重い同期処理がメインスレッドをブロック | 非同期・Worker への移行 |
| **バンドルサイズの膨張** | 未使用 import・大きなライブラリの全量読み込み | Tree Shaking・Dynamic Import |

詳細な検出パターンは [improvement-opportunity-catalog.md](references/improvement-opportunity-catalog.md) の「型安全性」「パフォーマンス」セクション参照。

**チェックリスト**:
- [ ] `any` / `enum` の使用箇所を特定した
- [ ] boolean フラグ地獄の箇所を特定した
- [ ] N+1 問題の可能性がある箇所を特定した
- [ ] メモ化・再レンダリング最適化の機会を特定した
- [ ] 各候補にファイル:行番号の証拠を付けた

### 📋 Review Gate 4: 型強化・最適化候補の実現可能性・優先性レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Phase 5 に進む。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| 型改善の実現可能性 | A-3（数値妥当性） | 型強化の提案が現在の技術スタック・TypeScript バージョンで実現可能か |
| パフォーマンス改善の効果推定 | B-5（Performance & Scalability） | 改善後の効果（レンダリング回数削減・クエリ数削減等）が具体的に推定されているか |
| 改善コストの適切性 | A-2（章間整合性） | 改善効果に対して実装コストが見合っているか評価されているか |

**通過条件**: Critical / Major 指摘がゼロ。

**不合格時**: 実現不可能または効果不明な候補を除外し、Phase 4a または 4b に戻る。

## Phase 5: UX/UI・テスト・観測可能性改善機会スキャン

**ux-psychology + ui-design + test に委譲**

### 5a. UX/UI 改善機会（ux-psychology + ui-design に委譲）

| 改善カテゴリ | Laws of UX / 基準 | 症状例 |
|:---|:---|:---|
| **認知負荷** | Miller's Law, Hick's Law | 選択肢が多すぎる・情報密度が高すぎる |
| **インタラクション** | Fitts's Law | タッチターゲットが 44px 未満 |
| **視覚的階層** | Visual Hierarchy | Primary/Secondary の区別がない |
| **アクセシビリティ** | WCAG AA | コントラスト比 4.5:1 未満・aria-label 欠如 |
| **デザイントークン** | 一貫性 | ハードコード色値・スペーシング不統一 |
| **感情設計** | Peak-End Rule | 完了時の達成感演出がない |

フロントエンドのないバックエンドプロジェクトでは、API 設計の一貫性・エラーレスポンスの品質を対象とする。

### 5b. テストカバレッジの改善機会（test に委譲）

| 改善カテゴリ | 検出方法 | 改善方向 |
|:---|:---|:---|
| **テスト不在のビジネスロジック** | 重要な関数・サービスにテストがない | ユニットテスト追加 |
| **ハッピーパスのみのテスト** | 正常系しかテストがない | 異常系・境界値テスト追加 |
| **統合テストの欠如** | コンポーネント間の連携がテストされていない | 統合テスト追加 |
| **テストの可読性** | テスト名が `test1`, `it('works')` 等 | BDD スタイルの命名へ改善 |

### 5c. 観測可能性・ドキュメントの改善機会

| 改善カテゴリ | 検出方法 | 改善方向 |
|:---|:---|:---|
| **エラーログの品質** | `console.error(e)` のみで構造なし | 構造化ログへ移行 |
| **メトリクスの欠如** | 重要な処理にメトリクスがない | メトリクス追加 |
| **JSDoc / コメントの欠如** | 複雑な関数に説明がない | ドキュメント追加 |
| **エラーメッセージの不明瞭さ** | `Error: something went wrong` | コンテキスト付きエラーメッセージへ |

**チェックリスト**:
- [ ] UX/UI 改善機会を Laws of UX / WCAG 観点で特定した
- [ ] テストが薄い箇所・テスト不在のビジネスロジックを特定した
- [ ] ログ・メトリクス・ドキュメントの改善機会を特定した
- [ ] 各候補に証拠（ファイル:行番号または操作手順）を付けた
- [ ] フロントエンドのないプロジェクトでは次元 5 を API 設計観点に切り替えた

### 📋 Review Gate 5: UX/UI・テスト改善候補の証拠・影響範囲レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Phase 6 に進む。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| UX 改善の法則根拠 | A-2（章間整合性） | 各 UX 改善候補に適用した Laws of UX が一貫して記述されているか |
| テストギャップの重大性評価 | B-6（Test Coverage） | テスト不在のビジネスロジックが重大度で評価されているか |
| 観測可能性改善の優先度 | B-5（Performance & Scalability） | ログ・メトリクス改善の事業影響度が評価されているか |

**通過条件**: Critical / Major 指摘がゼロ。

**不合格時**: 根拠不明確な候補を再調査し、Phase 5a〜5c に戻る。

## Phase 6: 改善機会の分類・優先度付け・レポート出力

**decision-framework に委譲**

### 6a. Impact × Effort マトリクスによる優先付け

詳細な判定基準は [opportunity-priority-matrix.md](references/opportunity-priority-matrix.md) 参照。

| 優先度 | Impact | Effort | アクション |
|:---|:---|:---|:---|
| **P1（今すぐ）** | High | Low | improve-flow に最優先で引き継ぎ |
| **P2（次に）** | High | High | improve-flow の次サイクルでの計画実施 |
| **P3（余力で）** | Low | Low | バックログに追加、スプリント後半で対応 |
| **P4（保留）** | Low | High | このサイクルでは扱わない |

### 6b. 改善機会レポートの構成

レポートテンプレートの詳細は [scan-output-templates.md](references/scan-output-templates.md) 参照。

```markdown
## 改善機会レポート — スキャンサマリー
- 対象: <パス> / 言語: <言語> / スキャン日時: YYYY-MM-DD

| 優先度 | 件数 |
| P1（今すぐ） | N |
| P2（次に） | N |
| P3（余力で） | N |

### P1 改善機会
#### IMP-001: <タイトル>
- ファイル: `src/xxx.ts:42`
- 次元: アーキテクチャ（責務過多）
- 現状: <どのような状態か>
- 改善方向: <どう改善するか>
- 期待効果: <改善後に何が良くなるか>
- 引き継ぎ: improve-flow Phase 0 スコープに追加

### improve-flow 引き継ぎパック
- 改善スコープ: <対象ファイル・機能>
- 成功基準: <Before/After で比較できる定量基準>
- P1 課題リスト: <IMP-001, IMP-002 ...>
```

**チェックリスト**:
- [ ] 全改善機会に Impact × Effort の評価を付与した
- [ ] P1-P3 を整理し、P4 を明示的に除外した
- [ ] 各改善機会にファイル名と行番号を記載した
- [ ] improve-flow への引き継ぎパックを作成した
- [ ] レポートに機密情報（APIキー・PII）が含まれていないか確認した
- [ ] 同一パターンの改善機会をグルーピングした（例: `any 使用（12箇所）`）

### 📋 Review Gate 6: 最終レポートの総合品質・優先付けの合理性レビュー

**review スキルに以下の観点で最終レビューを依頼し、通過してからレポートを納品する。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| 優先付けの合理性 | A-1（要件カバレッジ） | Impact × Effort の判定がビジネス価値・技術的影響を適切に反映しているか |
| レポートの完全性 | A-4（可読性と説得力） | ファイル名・行番号・現状・改善方向・期待効果が揃い、実行可能な情報か |
| PII 保護 | B-4（プライバシー） | レポートに機密情報が含まれていないか |
| 整合性 | A-2（章間整合性） | Phase 1〜5 の発見と最終レポートの内容が一貫しているか |

**通過条件**: A-1〜A-4 の全チェックリストをパス。B-4 は必須通過。Critical / Major 指摘がゼロ。

**不合格時**: 指摘内容に応じて該当 Phase に戻り修正。B-4 不合格（機密情報漏洩）は最優先で対処。

## Troubleshooting

| 問題 | 原因 | 解決策 |
|:---|:---|:---|
| bug-finder と重複した候補が出る | 改善機会とバグの境界が曖昧 | 「動作に影響する欠陥」は bug-finder へ委譲し、「品質・保守性・体験の向上機会」のみを残す |
| 改善候補が多すぎてレポートが読みにくい | 全てを列挙している | Phase 6 の Impact × Effort で P4 を積極的に除外。P1-P2 のみを詳述し、P3 は箇条書きにまとめる |
| 意図的な設計決定を誤って候補に含める | アーキテクチャの背景を知らずにスキャン | ADR・コメント・PR 説明を確認し、意図的なトレードオフは「既知の決定」として別記 |
| UX 改善機会の定量化が難しい | UX は主観的に見える | Laws of UX 違反件数・WCAG 基準違反件数など客観指標に変換する |
| TypeScript の `any` が多すぎてスキャンが終わらない | コードベース全体が型不安全 | Phase 1 でフォーカス次元を絞るか、ファイル単位で優先順位を付ける |
| テストカバレッジの計測ができない | カバレッジツールが未設定 | ファイル単位の目視確認（関数ごとにテストファイルを確認）で代替。「カバレッジ計測ツールの導入」も改善機会として記録 |
| パフォーマンス改善候補の効果が不明 | 現状のメトリクスがない | 改善方向と期待効果の定性的な説明を記録し、「計測設定の導入」も改善機会として Phase 6 に含める |
| improve-flow への引き継ぎスコープが大きすぎる | 改善候補を絞れていない | P1 候補のみを improve-flow の 1 サイクル分として抽出。P2 以降は次サイクルへ |
| Gate で「証拠が不十分」と繰り返し指摘される | ファイル名・行番号なしに候補を記録している | 「どのファイル:行番号で、現状は何で、どう改善できるか」を必ず記録してから Gate に進む |
| デッドコードかどうか判断できない | 動的な参照・リフレクションの可能性 | IDE の参照検索や grep で確認。不明な場合は「要確認」フラグを付けて候補に残す |
| フロントエンドのないバックエンドで次元 5（UX/UI）をスキャンしようとする | フォーカス次元の設定ミス | Phase 1 でプロジェクト種別に応じて次元 5 を「API 設計・エラーレスポンス品質」に切り替える |
| 改善候補と `TODO` コメントの重複 | TODO をそのまま候補に挙げている | TODO は「既知の改善機会」として別セクションに整理し、新規発見候補と明確に区別する |
