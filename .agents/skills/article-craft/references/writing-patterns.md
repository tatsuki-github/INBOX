# ライティングパターン集

> 記事執筆で使える文章構成パターン、リード文の型、展開テクニック、締めのパターン。
> SKILL.md の Step 4（本文執筆）で参照する。

---

## 1. リード文パターン

記事の冒頭 2〜3 文で読者をフックする型。

### パターン一覧

| # | パターン名 | 効果 | 適する記事タイプ |
|:---:|:---|:---|:---|
| 1 | 課題共感型 | 読者の痛みに寄り添い、共感を得る | ハウツー、解説 |
| 2 | 意外な事実型 | 驚きで注意を引く | オピニオン、解説 |
| 3 | 結果先行型 | 成果を先に見せて興味を引く | ケーススタディ、ハウツー |
| 4 | 問いかけ型 | 読者に考えさせて引き込む | オピニオン、解説 |
| 5 | ストーリー型 | 物語で感情的につなげる | ケーススタディ、インタビュー |
| 6 | データ提示型 | 数値で説得力を示す | 比較、リスト |

### 各パターンの例

#### 1. 課題共感型

```
「リモートワークで集中できない」——そんな悩みを抱えていませんか？
自宅には誘惑が多く、オフィスのような緊張感もない。
この記事では、在宅でも集中力を維持する 5 つの具体的な方法を紹介します。
```

**構造**: 読者の課題を代弁 → 課題の背景を補足 → 記事の価値を宣言

#### 2. 意外な事実型

```
マルチタスクは生産性を 40% 低下させる——スタンフォード大学の研究が明らかにしました。
にもかかわらず、多くの人が複数の作業を同時にこなそうとしています。
本記事では、シングルタスクに切り替えるための実践的な方法を解説します。
```

**構造**: 意外な事実・データ → 現状とのギャップ → 記事で得られる解決策

#### 3. 結果先行型

```
チームの開発速度が 2 倍になりました。
きっかけは、たった 1 つのプロセス改善——CI/CD パイプラインの導入です。
この記事では、導入の背景から具体的な手順、得られた成果までを共有します。
```

**構造**: 成果を提示 → 要因を簡潔に → 記事の内容を予告

#### 4. 問いかけ型

```
あなたのチームでは、コードレビューにどれくらい時間をかけていますか？
「レビューが形骸化している」と感じたことはないでしょうか。
この記事では、実効性のあるコードレビュー文化をつくる 3 つの原則を提案します。
```

**構造**: 問いかけ → 読者の潜在的な不満に触れる → 解決策の予告

#### 5. ストーリー型

```
昨年の夏、私たちのプロジェクトは危機に瀕していました。
リリースは 2 週間後に迫り、主要機能にクリティカルバグが 3 件。
チームが取った行動と、そこから得た教訓をお話しします。
```

**構造**: 状況の描写 → 緊張感の提示 → 記事の内容を予告

#### 6. データ提示型

```
2024 年、日本の SaaS 市場は前年比 25% 成長し、1.2 兆円規模に到達しました。
この成長を支える技術トレンドとは何か？
本記事では、注目すべき 5 つのトレンドをデータとともに解説します。
```

**構造**: データを提示 → 問いを立てる → 記事の内容を予告

## 2. 展開パターン

本論で論点を展開する際の構成テクニック。

### PREP 法（基本）

| ステップ | 説明 | 文例 |
|:---|:---|:---|
| **P**oint（結論） | 最初に結論を述べる | 「コードレビューは 30 分以内に完了すべきです」 |
| **R**eason（理由） | 結論の根拠を説明 | 「なぜなら、時間が経つほどコンテキストが失われるからです」 |
| **E**xample（具体例） | 具体例・データで裏付け | 「実際に、Google のチームでは〜」 |
| **P**oint（再結論） | 結論を再確認 | 「したがって、レビュー依頼から 30 分以内の対応をルール化しましょう」 |

### SDS 法（簡潔な説明向け）

| ステップ | 説明 |
|:---|:---|
| **S**ummary（要約） | 伝えたいことを一言で |
| **D**etails（詳細） | 補足情報・具体例 |
| **S**ummary（再要約） | 要点の再確認 |

### 問題解決型

| ステップ | 説明 |
|:---|:---|
| **Problem**（問題） | 読者が直面している問題 |
| **Agitation**（深刻化） | 問題を放置した場合のリスク |
| **Solution**（解決策） | 具体的な解決方法 |

### 比較対照型

| ステップ | 説明 |
|:---|:---|
| **Before**（改善前） | 現状の問題点 |
| **After**（改善後） | 改善後の理想状態 |
| **Bridge**（橋渡し） | Before → After に到達する方法 |

## 3. 段落構成のテクニック

| テクニック | 説明 | 例 |
|:---|:---|:---|
| **トピックセンテンス** | 段落の冒頭で主旨を述べる | 「テストの自動化には 3 つの利点があります。」 |
| **具体と抽象の往復** | 抽象的な主張と具体例を交互に | 主張 → 事例 → 主張の一般化 |
| **数字の活用** | 定量的な情報で説得力を高める | 「50% 削減」「3 つのポイント」 |
| **比喩の活用** | 馴染みのない概念を身近なものに例える | 「API は"レストランの注文"のようなもの」 |
| **接続詞の変化** | 同じ接続詞の連続を避ける | しかし→一方で→とはいえ |

## 4. 締めのパターン

### パターン一覧

| # | パターン名 | 効果 | 適する記事タイプ |
|:---:|:---|:---|:---|
| 1 | 要点再確認型 | 学びを定着させる | 全タイプ |
| 2 | アクション喚起型 | 具体的な行動を促す | ハウツー、解説 |
| 3 | 問いかけ型 | 読者の思考を促す | オピニオン |
| 4 | 展望型 | 未来への期待を示す | ケーススタディ、解説 |
| 5 | 余韻型 | 感情的な余韻を残す | インタビュー、エッセイ |

### 各パターンの例

#### 1. 要点再確認型

```
本記事のポイントをまとめます。

1. ○○は△△である
2. □□する際は◇◇に注意する
3. 最も重要なのは▽▽である

この 3 点を押さえれば、○○で失敗するリスクを大幅に減らせます。
```

#### 2. アクション喚起型

```
まずは今日から、1 つだけ試してみてください。

おすすめは「ステップ 2」で紹介した○○です。
5 分もあれば始められます。小さな一歩が大きな変化につながります。
```

#### 3. 問いかけ型

```
最後に、読者のみなさんに問いかけます。

あなたのチームでは、○○にどう向き合っていますか？
正解は 1 つではありません。この記事が、考えるきっかけになれば幸いです。
```

## 5. 冗長表現の書き換え辞書

| ❌ 冗長な表現 | ✅ 簡潔な表現 | 備考 |
|:---|:---|:---|
| 「〜することができる」 | 「〜できる」 | 能力表現の簡略化 |
| 「〜ということです」 | 「〜です」 | 回りくどい終助詞の削除 |
| 「〜というものです」 | 「〜です」 | 同上 |
| 「〜を行う」 | 「〜する」 | 冗長な動詞の簡略化 |
| 「〜において」 | 「〜で」 | 助詞の簡略化 |
| 「〜に関して」 | 「〜について」 or 「〜の」 | より自然な助詞に |
| 「〜の方が」（比較でない） | 削除 | 不要な「方」 |
| 「基本的には」 | 削除、または条件を明示 | 曖昧回避 |
| 「いわゆる」 | 削除、または正式名称を使用 | 曖昧回避 |
| 「さまざまな」 | 具体的に列挙 | 抽象表現の排除 |

## 6. 見出し設計のテクニック

### 良い見出しの条件

| 条件 | 説明 | 例 |
|:---|:---|:---|
| **自己完結** | 見出しだけで内容が推測できる | ✅「CI/CD で開発速度が 2 倍になった理由」 ❌「理由について」 |
| **並列性** | 同階層の見出しが同じ文法構造 | ✅「選ぶ / 設定する / 検証する」 ❌「選び方 / 設定 / 検証について」 |
| **適切な粒度** | 長すぎず短すぎない（10〜25 文字） | ✅「集中力を高める 3 つの習慣」 ❌「習慣」 |
| **キーワード含有** | 検索されやすい語を含む | SEO を意識する場合に有効 |

### 見出しの階層ルール

| ルール | 説明 |
|:---|:---|
| H2 は記事の大きな区切り | 本の「章」に相当 |
| H3 は H2 の内訳 | 本の「節」に相当 |
| H4 以降は使用を最小限に | 階層が深いと読みにくくなる |
| H2 の数は 3〜7 個が目安 | 多すぎると散漫、少なすぎると浅い |
