# Skill: Article Craft（記事の企画・執筆）

> **良い記事は「読者の問い」に答える — テーマではなく読者の課題から始めよ**

## Instructions

### ワークフロー内の位置

```
知識ソース → [article-craft] → 記事成果物
  (notes,       ↓                ├── 記事本文（Markdown）
   spec,     テーマ分析           ├── メタ情報（タイトル, 概要, タグ）
   経験)     ・読者定義           └── (OGP / サムネイル指示)
             ・構成設計                    ↓
             ・執筆              review スキルで品質検証
             ・品質検証
```

### 入力

| 入力 | 説明 | 例 |
|:---|:---|:---|
| テーマ / トピック | 記事で扱う主題 | 「リモートワークの生産性」 |
| 知識ソース | 参考にする情報源 | notes/ の蒸留済み資料、書籍、実体験 |
| 対象読者（任意） | 想定する読者層 | 「エンジニア初心者」「経営層」 |
| 記事タイプ（任意） | 希望する記事形式 | 「ハウツー」「オピニオン」 |
| 公開媒体（任意） | 掲載先のプラットフォーム | Zenn、note、社内ブログ、Qiita |
| 文字数目安（任意） | 希望する記事の長さ | 「3000 文字程度」「短め」 |

### 出力

| 出力 | 形式 | 説明 |
|:---|:---|:---|
| 記事本文 | Markdown | 見出し・本文・コードブロック（該当時）を含む完成原稿 |
| メタ情報 | YAML / テーブル | タイトル、概要（description）、タグ、カテゴリ |
| アウトライン | Markdown リスト | 執筆前の構成案（ユーザー確認用） |

## Step 1: テーマ分析と読者定義

記事のテーマを分析し、読者像を明確にする。

### 1a. テーマの 5W1H 分解

| 軸 | 質問 | 記入例 |
|:---|:---|:---|
| **What** | 何について書くか？ | リモートワークでの集中力維持法 |
| **Who** | 誰に向けて書くか？ | 在宅勤務を始めたばかりの社会人 |
| **Why** | 読者はなぜこの記事を読むか？ | 集中できず生産性が落ちている |
| **When** | いつ読まれるか？（旬・文脈） | リモートワーク普及後 |
| **Where** | どこに掲載するか？ | note |
| **How** | どの深さ・切り口で書くか？ | 実践的なテクニック中心 |

### 1b. 読者ペルソナの定義

| 項目 | 内容 |
|:---|:---|
| 読者層 | 職種・経験レベル・年齢層 |
| 前提知識 | 読者が既に知っていること |
| 課題・痛み | 読者が抱えている具体的な問題 |
| 期待する成果 | 記事を読んだ後に得たいもの |
| 読了後のアクション | 記事を読んだ後にとる行動 |

### 1c. 記事のゴール設定

| ゴール種別 | 説明 | 例 |
|:---|:---|:---|
| **情報提供** | 読者に新しい知識を届ける | 「○○の仕組みがわかる」 |
| **行動促進** | 読者に具体的な行動を起こさせる | 「ツールを導入する」 |
| **意見形成** | 読者の考え方に影響を与える | 「○○について再考する」 |
| **共感獲得** | 読者と経験・感情を共有する | 「同じ悩みを持つ仲間がいると知る」 |

**チェックリスト**:
- [ ] テーマの 5W1H を分解した
- [ ] 読者ペルソナを定義した（前提知識・課題・期待成果）
- [ ] 記事のゴール（情報提供 / 行動促進 / 意見形成 / 共感獲得）を決定した
- [ ] 読者の前提知識レベルに合った深さを設定した

## Step 2: 記事タイプの決定

テーマと読者に最適な記事タイプを選定する。

### 2a. 記事タイプ一覧

| タイプ | 目的 | 構成の特徴 | 適するケース |
|:---|:---|:---|:---|
| **ハウツー** | 手順を教える | 問題提起→手順→結果 | 具体的なやり方を伝えたい |
| **解説・入門** | 概念を説明する | 概要→詳細→まとめ | 新しい概念・技術を紹介したい |
| **オピニオン** | 主張を伝える | 主張→根拠→反論への応答→結論 | 自分の見解を発信したい |
| **ケーススタディ** | 事例を共有する | 背景→課題→施策→結果→学び | 実体験から学びを届けたい |
| **リスト記事** | 複数項目を列挙する | 導入→項目 1〜N→まとめ | 網羅的に情報を整理したい |
| **比較記事** | 選択肢を比較する | 評価軸→候補比較→推奨 | 意思決定を支援したい |
| **インタビュー** | 対話形式で伝える | 導入→Q&A→まとめ | 人の経験・視点を届けたい |
| **レビュー** | 評価を共有する | 概要→評価軸別レビュー→総評 | 製品・書籍・サービスの評価 |
| **まとめ・振り返り** | 期間の成果を整理する | 背景→成果→課題→次のアクション | 週報・月報・年次振り返り |

### 2b. タイプ選定の決定木

```
読者に手順を教えたいか？
├─ Yes → ハウツー
└─ No → 概念や仕組みを説明したいか？
         ├─ Yes → 解説・入門
         └─ No → 自分の意見・主張を伝えたいか？
                  ├─ Yes → オピニオン
                  └─ No → 実体験・事例を共有したいか？
                           ├─ Yes → ケーススタディ
                           └─ No → 複数の項目を列挙・比較したいか？
                                    ├─ Yes（列挙）→ リスト記事
                                    ├─ Yes（比較）→ 比較記事
                                    └─ No → インタビュー / レビュー / まとめ
```

詳細は [article-types-guide.md](references/article-types-guide.md) を参照。

**チェックリスト**:
- [ ] 記事タイプを決定した
- [ ] 決定木に沿って選定理由を確認した
- [ ] 選定したタイプの構成パターンを把握した

## Step 3: アウトライン作成

記事全体の構成を設計し、ユーザーに確認を取る。

### 3a. アウトラインの構成要素

| 要素 | 説明 | 必須 |
|:---|:---|:---:|
| タイトル案 | 読者の関心を引く記事タイトル（2〜3 候補） | ✅ |
| リード文の方向性 | 冒頭 2〜3 文で伝えること | ✅ |
| 見出し構造 | H2 / H3 の階層と各セクションの要点 | ✅ |
| 各セクションのキーメッセージ | そのセクションで伝える核心（1 文） | ✅ |
| 想定文字数配分 | セクションごとの文字数目安 | ⭐推奨 |
| CTA（行動喚起） | 記事末尾で読者に促すアクション | ⭐推奨 |

### 3b. タイトル設計の原則

| 原則 | 説明 | 例 |
|:---|:---|:---|
| **具体性** | 抽象的でなく具体的なベネフィットを示す | ❌「生産性の話」→ ✅「集中力を 2 倍にする 5 つの習慣」 |
| **数字の活用** | 定量的な情報で注目を集める | 「3 つのステップ」「10 分で」 |
| **読者の課題起点** | 読者の悩みに直接応える | 「○○で困っていませんか？」 |
| **適切な長さ** | 30〜40 文字（日本語） | 長すぎると切れる、短すぎると情報不足 |

### 3c. アウトライン出力フォーマット

```markdown
## アウトライン

**タイトル案**:
1. <候補 1>
2. <候補 2>
3. <候補 3>

**リード文の方向性**: <読者の課題に触れ、記事で得られる価値を示す>

**構成**:
1. H2: <見出し>（約 ○○ 文字）
   - キーメッセージ: <1 文>
   - H3: <小見出し>
   - H3: <小見出し>
2. H2: <見出し>（約 ○○ 文字）
   - キーメッセージ: <1 文>
   ...
N. H2: まとめ（約 ○○ 文字）
   - CTA: <読了後に促すアクション>

**想定総文字数**: 約 ○○ 文字
```

**CRITICAL**: アウトラインを出力した後、ユーザーの承認を得てから Step 4 に進むこと。

**チェックリスト**:
- [ ] タイトル案を 2〜3 候補作成した
- [ ] リード文の方向性を決定した
- [ ] H2 / H3 の見出し構造を設計した
- [ ] 各セクションにキーメッセージを設定した
- [ ] 文字数配分が偏りすぎていない
- [ ] ユーザーにアウトライン承認を依頼した

## Step 4: 本文執筆

承認済みアウトラインに基づき、記事本文を執筆する。

### 4a. 執筆の基本原則

| 原則 | 説明 |
|:---|:---|
| **PREP 法** | Point（結論）→ Reason（理由）→ Example（具体例）→ Point（再結論） |
| **一文一義** | 1 つの文に 1 つのメッセージだけを入れる |
| **読者目線** | 「筆者が言いたいこと」ではなく「読者が知りたいこと」を優先 |
| **具体と抽象の往復** | 抽象的な主張には具体例を、具体例には抽象的な学びを添える |
| **冗長排除** | 「という」「こと」「もの」「ような」の連続使用を避ける |

### 4b. セクション別の執筆ガイド

| セクション | 書き方のポイント | 目安文字数比率 |
|:---|:---|:---:|
| **リード文** | 読者の課題に共感 → 記事の価値を宣言 → 読了メリット提示 | 5〜10% |
| **導入** | 背景・文脈を簡潔に共有し、本題への橋渡しをする | 10〜15% |
| **本論（各セクション）** | PREP 法で展開。見出しだけで内容が推測できるようにする | 60〜70% |
| **まとめ** | 記事全体のキーポイントを再確認 → CTA で行動を促す | 10〜15% |

### 4c. 文体の一貫性

| 項目 | 選択肢 | 判断基準 |
|:---|:---|:---|
| 敬体 / 常体 | です・ます / だ・である | 媒体の慣習 + 読者との距離感 |
| 人称 | 一人称（私）/ 非人称 | オピニオン系は一人称、解説系は非人称 |
| 専門用語 | 初出時に説明する / 前提知識として扱う | 読者ペルソナの前提知識に準拠 |

詳細は [writing-patterns.md](references/writing-patterns.md) を参照。

**チェックリスト**:
- [ ] アウトラインに沿って全セクションを執筆した
- [ ] リード文が読者の課題に触れ、読了メリットを示している
- [ ] 各セクションが PREP 法（結論→理由→具体例→結論）で展開されている
- [ ] 一文一義を遵守している（1 文 60 文字以内目安）
- [ ] 敬体 / 常体が記事全体で統一されている
- [ ] 専門用語は初出時に説明している（読者ペルソナ準拠）

## Step 5: 品質検証とリファインメント

執筆した記事の品質を検証し、必要に応じて修正する。

### 5a. 構造チェック

| チェック項目 | 基準 |
|:---|:---|
| タイトルと内容の一致 | タイトルが約束する内容が本文でカバーされている |
| 見出しの論理構造 | H2 → H3 の階層が論理的に整合している |
| セクション間の流れ | 前のセクションが次のセクションへの橋渡しになっている |
| 冒頭と結末の対応 | リード文で提起した課題がまとめで回収されている |

### 5b. 文章品質チェック

| チェック項目 | 基準 |
|:---|:---|
| 冗長な表現 | 「〜ということ」「〜することができる」→ 簡潔に書き直す |
| 曖昧な表現 | 「いろいろ」「さまざまな」→ 具体的に列挙する |
| 受動態の多用 | 能動態に書き直せる箇所は書き直す |
| 接続詞の重複 | 「しかし」「また」の連続使用を避ける |
| 誤字脱字 | 固有名詞・技術用語のスペルを確認する |

### 5c. 読者体験チェック

| チェック項目 | 基準 |
|:---|:---|
| 最初の 3 行で読む価値が伝わるか | リード文のフック力 |
| スキャン可読性 | 見出しだけ読んで概要がわかるか |
| 視覚的なリズム | テキストの壁がなく、適切に段落・リスト・テーブルが使われているか |
| 読了後の満足度 | 読者がゴール（知識獲得 / 行動促進 / 共感）に到達できるか |
| CTA の明確さ | 記事末尾で次のアクションが具体的に示されているか |

詳細は [quality-checklist.md](references/quality-checklist.md) を参照。

**チェックリスト**:
- [ ] タイトルと内容が一致している
- [ ] 見出しの論理構造に矛盾がない
- [ ] セクション間の流れが自然である
- [ ] 冗長・曖昧な表現を排除した
- [ ] 文体（敬体 / 常体）が統一されている
- [ ] 最初の 3 行で読む価値が伝わる
- [ ] 見出しだけ読んで概要がわかる
- [ ] CTA が明確である

## Quality Gates

以下のすべてを満たした場合のみ、記事を完成とする:

**構造ゲート**:
- タイトル・リード文・本論・まとめの全セクションが存在する
- H2 / H3 の階層が論理的に整合している
- リード文で提起した課題がまとめで回収されている

**品質ゲート**:
- 冗長表現（「〜ということ」「〜することができる」）が 0 件
- 曖昧表現（「いろいろ」「さまざま」「など」で終わる列挙）が 0 件
- 文体（敬体 / 常体）が全文で統一されている
- 一文一義が遵守されている
- 専門用語が初出時に説明されている

**読者体験ゲート**:
- リード文が読者の課題に触れ、読了メリットを提示している
- 見出しだけ読んで記事全体の概要が把握できる
- CTA が記事末尾に存在し、具体的なアクションを示している

## Examples

### Example 1: 【基本】ハウツー記事の作成

```
「リモートワークで集中力を維持する方法について記事を書いて」

→ Step 1: テーマ = 集中力維持、読者 = 在宅勤務の社会人、ゴール = 行動促進
→ Step 2: タイプ = ハウツー（手順を教える）
→ Step 3: アウトライン作成 → タイトル 3 候補 + H2×4 セクション → ユーザー承認
→ Step 4: PREP 法で各セクション執筆、です・ます調
→ Step 5: 構造チェック + 文章品質チェック + 読者体験チェック
```

### Example 2: 【応用】オピニオン記事の作成

```
「AI がクリエイティブ業界に与える影響についてオピニオン記事を書いて」

→ Step 1: テーマ = AI × クリエイティブ、読者 = デザイナー・クリエイター、ゴール = 意見形成
→ Step 2: タイプ = オピニオン（主張 → 根拠 → 反論応答 → 結論）
→ Step 3: アウトライン作成 → 主張を明確化 + 根拠 3 点 + 想定反論 → ユーザー承認
→ Step 4: 一人称・だ/である調で執筆、反論への応答を丁寧に展開
→ Step 5: 主張と根拠の一貫性を検証、バランスチェック
```

### Example 3: 【応用】ケーススタディ記事の作成

```
「チーム開発で導入した CI/CD パイプラインの成功事例を記事にして」

→ Step 1: テーマ = CI/CD 導入事例、読者 = 開発チームリーダー、ゴール = 情報提供 + 行動促進
→ Step 2: タイプ = ケーススタディ（背景 → 課題 → 施策 → 結果 → 学び）
→ Step 3: アウトライン作成 → 数値成果を含む構成案 → ユーザー承認
→ Step 4: 背景→課題→施策→結果の流れで具体的に執筆、数値データを活用
→ Step 5: 事実と学びの区別を検証、再現可能性をチェック
```

### Example 4: 【基本】リスト記事の作成

```
「おすすめの生産性向上ツール 10 選の記事を書いて」

→ Step 1: テーマ = 生産性ツール、読者 = ビジネスパーソン全般、ゴール = 情報提供
→ Step 2: タイプ = リスト記事（導入 → 項目 1〜10 → まとめ）
→ Step 3: アウトライン作成 → ツール選定基準 + 10 項目の順序 → ユーザー承認
→ Step 4: 各項目を統一フォーマット（概要 / 特徴 / 推奨場面）で執筆
→ Step 5: 重複排除、選定基準の一貫性を検証
```

## Troubleshooting

| 問題 | 原因 | 対策 |
|:---|:---|:---|
| 記事の焦点がぼやける | テーマが広すぎる / 読者が未定義 | Step 1 に戻り、5W1H を再分解して読者ペルソナを絞る |
| 書き出しが思いつかない | リード文の型が決まっていない | [writing-patterns.md](references/writing-patterns.md) のリード文パターンから選択 |
| 記事が長くなりすぎる | スコープが広すぎる / 脱線している | 各セクションのキーメッセージに立ち返り、逸脱部分を削除 |
| 記事が短すぎる | 具体例・データが不足している | PREP 法の Example（具体例）を追加。読者の「たとえば？」に答える |
| 見出しが魅力的でない | 内容の要約になっていない | 見出しだけで読者が読みたくなるか検証。数字・ベネフィットを含める |
| 文体が途中で変わる | 敬体 / 常体の使い分けルール未設定 | Step 4c の文体テーブルで事前に決定し、執筆後に全文チェック |
| 専門用語が多すぎる | 読者ペルソナの前提知識を超えている | Step 1b の前提知識に照らし、初出時の説明を追加 |
| 結論が弱い | まとめが本論の繰り返しだけ | CTA を追加し、読者の次のアクションを具体的に提示 |
| SEO を意識したいが方法がわからない | キーワード戦略が未設定 | タイトル・H2 見出し・リード文にターゲットキーワードを自然に含める |
| 既存記事のリライトが中途半端 | 改善ポイントが不明確 | Step 5 の品質チェックを先に実施し、改善箇所を特定してから修正 |
