# Bug Report Template — バグ調査レポートテンプレート

> バグ調査・修正完了後に出力する標準レポート。調査の透明性を確保し、ナレッジを蓄積する。

---

## バグ調査レポート（標準テンプレート）

```markdown
## バグ調査レポート

### 基本情報
- **バグID**: BUG-YYYY-NNN
- **報告日**: YYYY-MM-DD
- **発見日**: YYYY-MM-DD
- **クローズ日**: YYYY-MM-DD
- **優先度**: P[1/2/3/4]
- **ステータス**: [調査中 / 修正中 / クローズ]
- **報告者**: [エンドユーザー名 / 社内報告]

### バグ概要
**ひとことサマリー**: [1文でバグを表現]

**影響範囲**:
- 対象機能: [機能名]
- 影響ユーザー: [全ユーザー / 特定条件のユーザー（詳細: XXX）]
- 影響データ: [なし / あり（詳細: XXX）]

---

### 症状（ユーザー報告）

**報告内容**:
> [ユーザーの原文を引用]

**STAR 形式整理**:
- **Situation（状況）**: [どの画面・機能で]
- **Trigger（トリガー）**: [何をしたとき]
- **Actual（実際）**: [何が起きたか]
- **Expected（期待）**: [何が起きるべきだったか]

**再現手順**:
1. [手順1]
2. [手順2]
3. [手順3 → ここで発生]

**再現率**: [常に / [条件]のとき / まれに（約N%）]

---

### 根本原因

**根本原因**:
[2-3文で根本原因を説明。技術的な正確さと非技術者への説明力を両立する]

**発生メカニズム**:
1. [ユーザーが何かをする]
2. [システムが何をする]
3. [なぜ問題が起きるか]
4. [症状として何が表れるか]

**証拠**:
- ログ: `[該当ログ行、またはログファイルのパス]`
- コード: `[ファイルパス]:L[行番号]`
- データ: `[DB クエリ結果や設定値]`

**除外した仮説**:
| 仮説 | 除外理由 |
|:---|:---|
| [仮説1] | [なぜ違うか] |
| [仮説2] | [なぜ違うか] |

---

### 修正内容

**修正アプローチ**: [選択したアプローチ名]

**変更ファイル**:
| ファイル | 行 | 変更内容 |
|:---|:---|:---|
| `src/xxx.ts` | L42 | [変更の説明] |
| `src/yyy.ts` | L88-95 | [変更の説明] |

**変更サマリー（差分）**:
```diff
- 変更前のコード
+ 変更後のコード
```

```sql
-- 影響ユーザーのデータ修正 SQL

```

### 検証結果

**バグの解消確認**:
- [ ] 最小再現手順でバグが再現しないことを確認

**回帰テスト結果**:
- [ ] 既存テストスイート: [PASS/FAIL]
- [ ] 追加したテスト: [PASS/FAIL]

**推奨事項**（オプション）:

## クローズ基準チェックリスト

以下を全て満たした場合のみクローズ可能:

| 基準 | 確認 |
|:---|:---|
| バグの症状が解消された | ✅ / ❌ |
| 根本原因が特定・記録された | ✅ / ❌ |
| 修正コードがレビューを通過した | ✅ / ❌ |
| 回帰テストが追加された | ✅ / ❌ |
| 影響ユーザーへのデータ修正が完了した（該当時） | ✅ / N/A |
| バグ調査レポートが記録された | ✅ / ❌ |
| 類似箇所の確認が完了した | ✅ / ❌ |

---

## 優先度定義

| 優先度 | 基準 | 対応期限 |
|:---|:---|:---|
| **P1: クリティカル** | データ損失・決済障害・認証突破・全体停止 | 即座（24時間以内） |
| **P2: 高** | 主要機能が使えない・全ユーザー影響 | 本日中（48時間以内） |
| **P3: 中** | 一部機能の不具合・回避策あり | 次スプリント |
| **P4: 低** | 表示崩れ・軽微な不具合 | バックログ |
