# Skill: Bug Triage Fix（バグ報告 → 原因特定 → 修正）

> **症状は嘘をつかない — ログの奥に潜む根本原因を一撃で仕留めよ**

## Instructions

### ワークフロー内の位置

各 Step の完了時に **review スキル** によるレビューゲートを通過してから次の Step に進む。
レビューで問題が検出された場合は、該当 Step に戻って修正する。
これにより、誤った前提のまま調査が進むことを防ぎ、**バグの真因を確実に特定**する。

```
エンドユーザーのバグ報告（自然言語 / ログ / スクリーンショット）
  ↓
[bug-triage-fix]
  ├─ Step 1: 報告の受領と構造化
  │   └─ 📋 Review Gate 1（報告の構造化品質レビュー）
  ├─ Step 2: 再現性の確認
  │   └─ 📋 Review Gate 2（再現条件の妥当性レビュー）
  ├─ Step 3: 原因仮説ツリーの構築
  │   └─ 📋 Review Gate 3（仮説ツリーの網羅性・論理性レビュー）
  ├─ Step 4: コードベース調査と根本原因の特定
  │   └─ 📋 Review Gate 4（根本原因の証拠・除外根拠レビュー）
  ├─ Step 5: 修正方針の決定
  │   └─ 📋 Review Gate 5（修正方針の妥当性レビュー）
  ├─ Step 6: 修正の実施
  │   └─ 📋 Review Gate 6（修正コードの品質レビュー）
  └─ Step 7: 検証・テスト追加・クローズ
      └─ 📋 Review Gate 7（最終成果物の総合レビュー）
  ↓
修正済みコード + バグ調査レポート + 回帰テスト（全ゲート通過済み）
```

### implementation-flow との使い分け

[implementation-flow](../implementation-flow/SKILL.md) Phase 0c 作業種別ルーターと連携する。

| シグナル | 正しいスキル |
|:---|:---|
| 期待動作 vs 実際の乖離、再現手順・ログあり | **bug-triage-fix**（Phase 0c Q1 → `bug-fix`） |
| 「〜機能を追加して」「〜してほしい」（新規要求） | **implementation-flow** Phase 0c へ |
| 改善のみ・新機能なし | **improve-flow**（Phase 0c Q2 → `perf-only`） |

**エスカレーション（本スキル → implementation-flow）**:

- Step 5（修正方針）で **設計変更・新規コンポーネント追加** が必要と判明
- 既存 API **契約の破壊的変更** が必要 → `modify-breaking` Lite Path
- 上記以外の機能拡張 → `extend` Lite Path
- エスカレーション時: バグ調査レポートを Phase 1 入力として引き継ぐ

**Step 7 のテスト**: [test](../test/SKILL.md) Step 1-4 で回帰テストを追加。Red ファーストで再現テストを書き、修正後 Green を確認する。

### 入力

| 入力 | 説明 | 例 |
|:---|:---|:---|
| バグ報告テキスト | エンドユーザーの自然言語による報告 | 「ログインすると画面が白くなる」 |
| エラーログ（任意） | スタックトレース、コンソールエラー | `TypeError: Cannot read properties of null` |
| 再現手順（任意） | ユーザーが操作した手順 | 「1. ログイン 2. プロフィール編集 3. 保存で発生」 |
| 環境情報（任意） | OS、ブラウザ、バージョン | Chrome 122, macOS 14.3 |
| スクリーンショット説明（任意） | 画面の状態説明 | 「エラーダイアログが表示される」 |

### 出力

| 出力 | 形式 | 説明 |
|:---|:---|:---|
| バグ調査レポート | Markdown | 報告の構造化、根本原因、修正内容のサマリー |
| 修正コード | コードブロック | 最小限の変更で根本原因を解消するコード |
| 回帰テストケース | コードブロック | 同じバグが再発しないことを検証するテスト |

## Step 1: バグ報告の受領と構造化

曖昧なユーザー報告を、調査可能な構造化情報に変換する。**報告の質が調査効率を決める**。

### 1a. 報告の構造化（STAR 形式）

受領したバグ報告を以下の形式に整理する:

| 要素 | 内容 | 記入例 |
|:---|:---|:---|
| **Situation（状況）** | どの機能・画面で発生したか | 「プロフィール編集画面で保存ボタン押下時」 |
| **Trigger（トリガー）** | 何をしたときに発生したか | 「アバター画像を変更後に保存した場合のみ」 |
| **Actual（実際の動作）** | 何が起きたか（症状） | 「500エラーが返り保存されない」 |
| **Expected（期待動作）** | 何が起きるべきだったか | 「プロフィールが更新される」 |

### 1b. 不足情報の特定と補完

構造化後に不足している情報を特定し、可能な範囲で補完・推定する。

> **PII 注意**: バグ報告にユーザー名・メールアドレス・電話番号等の個人情報が含まれる場合、
> 調査に不要な PII はマスクしてから記録・共有する（例: `user@example.com` → `user@***.***`）。

| 情報カテゴリ | チェック | 不足時の対処 |
|:---|:---|:---|
| 再現手順 | 手順が具体的か | コードから操作フローを推定する |
| エラーメッセージ | 完全なスタックトレースがあるか | ログファイルを探索する |
| 発生頻度 | 常に / 特定条件で / まれに | コードの条件分岐を確認する |
| 影響範囲 | 特定ユーザーのみ / 全ユーザー | データ依存の可能性を判断する |
| 発生日時 | いつから / デプロイとの関係 | git log でコード変更と照合する |

### 1c. バグ優先度の仮判定

| 優先度 | 基準 | 対応 |
|:---|:---|:---|
| **P1: 即座に対応** | データ損失、決済障害、認証突破 | Step 4 に直行。仮説ツリーを省略可 |
| **P2: 本日中** | 主要機能が使えない、全ユーザー影響 | Step 1〜7 を通常手順で |
| **P3: 次スプリント** | 一部機能の不具合、回避策あり | Step 3 の仮説ツリーを丁寧に |
| **P4: バックログ** | 表示崩れ、軽微な不具合 | Step 5 から開始可 |

**チェックリスト**:
- [ ] バグ報告を STAR 形式に構造化した
- [ ] 発生条件（必ず発生 / 特定条件）を特定した
- [ ] 影響範囲（特定ユーザー / 全体）を判断した
- [ ] 優先度（P1〜P4）を仮判定した
- [ ] 不足情報を特定し、補完または推定した

### 📋 Review Gate 1: 報告の構造化品質レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Step 2 に進む。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| 情報の完全性 | A-1（要件カバレッジ） | STAR 形式の全要素（Situation/Trigger/Actual/Expected）が埋まっているか |
| 整合性 | A-2（章間整合性） | 症状と発生条件の記述が矛盾していないか |
| 数値・データの妥当性 | A-3（数値妥当性） | 優先度判定の根拠が適切か。影響範囲の見積もりが過小/過大でないか |
| PII 保護 | B-4（プライバシー） | バグ報告内の個人情報が適切にマスクされているか |

**通過条件**: Critical / Major 指摘がゼロ。Minor 指摘は記録して続行可。

**不合格時**: 指摘箇所を修正し、Step 1 の該当サブステップに戻る。

## Step 2: 再現性の確認

**再現できないバグは直せない** — 再現条件を確定させることが、原因特定の最短経路。

### 2a. 再現試行

報告された手順でバグを再現する:

1. 報告の手順をそのまま実行する
2. 再現した場合 → Step 3 へ
3. 再現しない場合 → 2b の再現条件調査へ

### 2b. 再現条件の絞り込み

| 変数 | 確認内容 | コードでの確認箇所 |
|:---|:---|:---|
| **ユーザー属性** | 特定のロール / プラン / データ状態 | 認証・認可ロジック、ユーザーモデル |
| **データ状態** | 特定の値 / Null / 空文字 / 特殊文字 | バリデーション、DB クエリ |
| **タイミング** | 特定の操作順序 / 競合状態 | イベントハンドラー、非同期処理 |
| **環境** | ブラウザ / OS / 言語設定 | ユーザーエージェント判定、i18n |
| **外部依存** | API 応答 / DB 状態 / キャッシュ | 外部 API 呼び出し、キャッシュ制御 |

### 2c. 再現不可時の対処

再現できない場合でも調査を進める戦略:

| 状況 | 戦略 |
|:---|:---|
| ログに証拠がある | ログから条件を逆算して再現を試みる |
| 特定ユーザーのみ | そのユーザーのデータ状態をコピーして再現 |
| 間欠的に発生 | 競合状態・タイミング問題と仮定して調査 |
| 本番のみ発生 | 本番と開発の設定差分を確認する |

**チェックリスト**:
- [ ] 報告手順で再現を試みた（成功/失敗を記録）
- [ ] 再現条件（ユーザー属性/データ状態/タイミング）を絞り込んだ
- [ ] 最小再現手順を確定した
- [ ] 再現不可の場合は代替調査戦略を選択した

### 📋 Review Gate 2: 再現条件の妥当性レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Step 3 に進む。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| 再現手順の論理性 | A-2（章間整合性） | 再現手順が Step 1 の報告内容と整合しているか |
| 条件網羅性 | B-3（境界値攻撃） | 再現条件の変数（ユーザー属性・データ状態・タイミング・環境）を十分に検証したか |
| 再現不可時の妥当性 | A-1（要件カバレッジ） | 再現不可の場合、代替調査戦略が報告の症状を説明できる経路を持っているか |

**通過条件**: Critical / Major 指摘がゼロ。特に「再現条件の絞り込みが甘い」という Major 指摘がある場合は必ず解消する。

**不合格時**: 指摘に基づき再現条件の検証を追加し、Step 2b に戻る。

## Step 3: 原因仮説ツリーの構築

症状から根本原因への経路を **仮説ツリー** で体系化する。闇雲なコード探索を防ぐ。

### 3a. 症状カテゴリの判定

エラーの症状から、最も可能性の高い原因カテゴリを判定する:

| 症状パターン | 最有力カテゴリ | 調査優先箇所 |
|:---|:---|:---|
| `TypeError` / `AttributeError` / `null reference` | データ不整合・Null 未考慮 | バリデーション、初期化処理 |
| `401 / 403 エラー` | 認証・認可ロジック | トークン検証、権限チェック |
| `500 Internal Server Error` | サーバーサイドの例外 | バックエンドログ、DB クエリ |
| 画面が固まる / ローディング永続 | 非同期処理のデッドロック | Promise/async-await、イベントハンドラー |
| データが保存されない（エラーなし） | サイレント失敗 | try-catch、トランザクション |
| 特定のデータのみ失敗 | データ検証・型変換 | バリデーション、型変換ロジック |
| タイミング依存の失敗 | 競合状態・レースコンディション | 非同期処理、ロック機構 |

### 3b. 仮説ツリーの構築

症状カテゴリを起点に、考えられる根本原因を木構造で列挙する:

```
症状: ユーザーがプロフィール保存時に 500 エラー
│
├─ [仮説 A] バックエンドの例外
│   ├─ [A-1] DB クエリエラー（制約違反、型不一致）
│   ├─ [A-2] バリデーションロジックのバグ
│   └─ [A-3] 依存サービス（S3/外部 API）の障害
│
├─ [仮説 B] データ不整合
│   ├─ [B-1] Null/空文字の未処理
│   └─ [B-2] 特殊文字・エンコーディング問題
│
└─ [仮説 C] 権限・認可
    └─ [C-1] ユーザーに更新権限がない
```

### 3c. 仮説の優先順位付け

各仮説を以下の観点でランク付けする:

| 仮説 | 可能性 | 調査コスト | 優先度 |
|:---|:---|:---|:---|
| A-1 DB クエリエラー | 高（ログに証拠） | 低（ログ確認のみ） | **1位** |
| B-1 Null 未処理 | 中（新機能追加直後） | 中（コード確認） | **2位** |
| A-3 外部サービス障害 | 低（他機能は正常） | 低（ステータス確認） | **3位** |

**チェックリスト**:
- [ ] 症状カテゴリを判定した
- [ ] 仮説ツリーを 3 階層で構築した
- [ ] 各仮説の可能性と調査コストを評価した
- [ ] 調査順序（優先度）を決定した
- [ ] 最有力仮説 1 つと代替仮説 2 つを特定した

### 📋 Review Gate 3: 仮説ツリーの網羅性・論理性レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Step 4 に進む。**

このゲートは **真因特定の精度を左右する最重要レビュー** である。仮説の漏れが真因の見逃しに直結する。

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| 仮説の網羅性 | A-1（要件カバレッジ） | 症状カテゴリから導かれる全カテゴリの原因仮説が検討されているか。抜け漏れはないか |
| 仮説間の整合性 | A-2（章間整合性） | 仮説同士が矛盾していないか。優先順位の根拠が論理的か |
| 境界条件の考慮 | B-3（境界値攻撃） | Null/未定義・タイミング・競合状態など、見えにくい原因が仮説に含まれているか |
| 調査コスト評価の妥当性 | A-3（数値妥当性） | 各仮説の可能性・調査コストの見積もりが適切か |

**通過条件**: Critical / Major 指摘がゼロ。「仮説に重大な漏れがある」は Critical 扱い。

**不合格時**: 指摘された仮説の漏れを追加し、仮説ツリーを再構築して再レビュー。

## Step 4: コードベース調査と根本原因の特定

仮説ツリーの優先順位に従い、コードを調査して根本原因を確定する。

### 4a. 調査戦略の選択

| 調査アプローチ | 適用場面 | 手法 |
|:---|:---|:---|
| **ログ逆引き** | エラーログがある | スタックトレースから呼び出し元を追う |
| **データフロー追跡** | データ不整合が疑われる | 入力→変換→保存の各ポイントを確認 |
| **差分調査** | 最近のデプロイ後に発生 | `git log --since` で変更箇所を特定 |
| **コード検索** | キーワードが特定できる | エラーメッセージで Grep 検索 |
| **テスト実行** | テストが存在する | 既存テストを実行して失敗箇所を確認 |

### 4b. 根本原因の確定条件

根本原因として確定するには、以下の 3 条件をすべて満たすこと:

| 条件 | 確認方法 |
|:---|:---|
| **再現性**: その箇所が原因で症状が発生する | コード変更 / ログで証明 |
| **一意性**: 他の箇所では説明できない | 代替仮説を除外した |
| **修正可能性**: 変更で症状が解消する | 修正案が具体的に描けている |

### 4c. 調査結果の記録

```markdown
## 根本原因調査結果

**根本原因**: [ファイル:行番号] での [具体的な問題]

**発生メカニズム**:
1. ユーザーが [操作] を実行する
2. [関数/メソッド] が [条件] のとき [問題のある処理] をする
3. [エラー/症状] が発生する

**証拠**:
- ログ: `[該当ログ行]`
- コード: `[問題箇所のコードスニペット]`

**除外した仮説**:
- [仮説 X]: [除外理由]
```

**チェックリスト**:
- [ ] 最有力仮説からコード調査を開始した
- [ ] 根本原因の 3 条件（再現性・一意性・修正可能性）を満たした
- [ ] 調査結果（根本原因・発生メカニズム・証拠）を記録した
- [ ] 除外した仮説と除外理由を明記した
- [ ] ファイルと行番号を特定した

### 📋 Review Gate 4: 根本原因の証拠・除外根拠レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Step 5 に進む。**

このゲートは **誤った原因で修正に進むことを防ぐ** 最も重要なレビューポイントである。

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| 証拠の十分性 | A-3（数値・データの妥当性） | 根本原因を裏付けるログ・コード証拠が十分か。推測だけで確定していないか |
| 仕様との整合性 | B-1（仕様との意味的乖離） | 特定された根本原因が仕様上のどのルールに違反しているか明確か |
| 除外根拠の論理性 | A-2（章間整合性） | 除外した仮説の除外理由が論理的か。証拠に基づく除外か |
| 3 条件の検証 | B-3（境界値攻撃） | 再現性・一意性・修正可能性の 3 条件それぞれが具体的な証拠で裏付けられているか |
| 発生メカニズムの完全性 | A-1（要件カバレッジ） | 発生メカニズムに飛躍や未説明のステップがないか |

**通過条件**: Critical / Major 指摘がゼロ。「証拠が不十分」「除外理由が不明」は Critical 扱い。

**不合格時**: 
- 証拠不足 → Step 4a に戻り追加調査を実施
- 除外が不適切 → Step 3 の仮説ツリーに戻り、除外した仮説を再調査

## Step 5: 修正方針の決定

根本原因を確定したうえで、**最小変更・最大安全性**の修正方針を決定する。

### 5a. 修正アプローチの選択

| アプローチ | 適用場面 | リスク |
|:---|:---|:---|
| **Null ガード追加** | Null/未定義参照エラー | 低 — 既存ロジックへの影響なし |
| **バリデーション強化** | 不正データによる障害 | 低 — 入力を早期に弾く |
| **エラーハンドリング追加** | サイレント失敗 | 低 — 例外の可視化のみ |
| **ロジック修正** | ビジネスルールの誤り | 中 — 関連コードへの影響を要確認 |
| **データ修正** | 既存データの不整合 | 高 — データマイグレーション必要 |
| **アーキテクチャ変更** | 設計レベルの問題 | 高 — 広範な変更、別 Issue を推奨 |

### 5b. 修正スコープの定義

修正前に以下を明確にする:

| 確認項目 | 内容 |
|:---|:---|
| **変更ファイル** | 修正が必要なファイルと行の一覧 |
| **影響範囲** | 修正によって変動する可能性のある機能 |
| **後退リスク** | 修正が他の機能を壊す可能性 |
| **データ移行の要否** | 既存データへの影響があるか |
| **テスト追加の要否** | 新規テストケースが必要か |

### 5c. 修正方針の文書化

```markdown
## 修正方針

**根本原因**: [一行サマリー]

**修正アプローチ**: [選択したアプローチ]

**変更ファイル**:
- `src/xxx.ts` L42: [変更内容]

**影響範囲**: [影響する機能]

**後退リスク**: [低/中/高] — [理由]

**テスト追加**: [必要/不要] — [追加するケース]
```

**チェックリスト**:
- [ ] 最小変更の原則に従い、必要最小限の修正スコープを定義した
- [ ] 修正アプローチを選択し、リスクを評価した
- [ ] 影響範囲と後退リスクを特定した
- [ ] データ移行の要否を判断した
- [ ] テスト追加の方針を決定した

### 📋 Review Gate 5: 修正方針の妥当性レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Step 6 に進む。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| 修正と原因の整合性 | B-1（仕様との意味的乖離） | 修正方針が Step 4 で特定した根本原因を正確に解消するものか |
| 影響範囲の漏れ | A-1（要件カバレッジ） | 修正による影響範囲が網羅的に特定されているか |
| リスク評価の妥当性 | A-3（数値妥当性） | 後退リスクの評価が適切か。過小評価していないか |
| セキュリティ考慮 | B-4（プライバシー） | 修正方針がセキュリティリスクを増加させないか |
| パフォーマンス影響 | B-5（Performance） | 修正がパフォーマンスに悪影響を与えないか |

**通過条件**: Critical / Major 指摘がゼロ。

**不合格時**: 指摘に基づき修正方針を見直し、Step 5a から再検討する。

## Step 6: 修正の実施

決定した修正方針に従い、コードを修正する。**一度に一箇所ずつ、確認しながら修正する**。

### 6a. 修正の実施原則

| 原則 | 説明 |
|:---|:---|
| **最小変更** | 根本原因の解消に必要な最小限のコードのみ変更する |
| **意図の明示** | 修正コードにコメントで「なぜこう直したか」を記述する |
| **既存テスト維持** | 修正後に既存テストが全て通過することを確認する |
| **副作用の排除** | バグ修正以外の変更（リファクタリング等）を混入させない |

### 6b. 修正パターン別の実装ガイド

詳細は [fix-patterns.md](references/fix-patterns.md) 参照。

| パターン | Before | After |
|:---|:---|:---|
| **Null ガード** | `user.profile.name` | `user?.profile?.name ?? 'unknown'` |
| **早期リターン** | ネストした条件分岐 | Guard clause で早期リターン |
| **例外の可視化** | 空の catch ブロック | catch でログ出力 + 適切な例外再スロー |
| **型の強制** | `parseInt(val)` | `parseInt(val, 10)` + NaN チェック |

### 6c. 修正後の自己チェック

修正コードをレビューする前に自分でチェックする:

| チェック項目 | 確認方法 |
|:---|:---|
| 根本原因が解消されているか | 手動で再現手順を実行 |
| 既存テストが全て通過するか | テストスイートを実行 |
| 他の箇所に類似の問題がないか | 同パターンを Grep 検索 |
| コードが読みやすいか | 修正理由がコメントで伝わるか |

**チェックリスト**:
- [ ] 根本原因の箇所のみを最小限に修正した
- [ ] 修正コードに「なぜ修正したか」のコメントを追加した
- [ ] 既存テストが全て通過することを確認した
- [ ] 同様のパターンが他の箇所にないか Grep で確認した
- [ ] バグ修正以外の変更が混入していないことを確認した

### 📋 Review Gate 6: 修正コードの品質レビュー

**review スキルに以下の観点でレビューを依頼し、通過してから Step 7 に進む。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| 仕様との整合性 | B-1（Semantic Drift） | 修正コードが仕様に準拠しているか。修正により新たな仕様乖離が発生していないか |
| 会計・数値整合性 | B-2（Accounting Integrity） | 修正が金額計算・集計ロジックに影響する場合、整合性が維持されているか |
| 境界値の堅牢性 | B-3（Edge Case Attack） | 修正コードが Null/未定義・境界値・型攻撃・並行処理に耐えるか |
| プライバシー保護 | B-4（Privacy Violation） | 修正がログ出力やエラーメッセージに PII を漏洩させないか |
| パフォーマンス | B-5（Performance & Scalability） | N+1 問題、メモリリーク、不要なクエリが導入されていないか |
| テストカバレッジ | B-6（Test Coverage） | 修正箇所に対応するテストが存在し、正常系・異常系をカバーしているか |

**通過条件**: B-1〜B-6 の全チェックリストをパス。Critical / Major 指摘がゼロ。

**不合格時**: 指摘に基づきコードを修正し、Step 6 の該当サブステップに戻る。

---

## Step 7: 検証・テスト追加・クローズ

修正を検証し、同じバグが再発しないようにテストを追加してクローズする。

### 7a. 修正の検証

| 検証項目 | 手順 |
|:---|:---|
| **バグが解消されたか** | Step 2 で確定した最小再現手順を実行し、症状が出ないことを確認 |
| **正常系が維持されているか** | 関連する通常の操作フローが正しく動作することを確認 |
| **回帰が発生していないか** | 影響範囲の機能を動作確認する |

### 7b. 回帰テストの追加

同じバグが将来再発しないよう、テストを追加する:

```
テストケースの設計方針:
1. バグを発生させた具体的な条件をそのままテストケースにする
2. テスト名に「バグ番号 / バグの概要」を含める
3. 正常系（修正後）と異常系（修正前の状態）の両方をカバーする
```

テスト命名規則: `[機能名] - [バグを発生させた条件] - [期待する動作]`

例:
- `プロフィール保存 - 空のアバター画像 URL - エラーなく保存される`
- `プロフィール保存 - 特殊文字を含む表示名 - 正しくサニタイズされる`

### 7c. バグ調査レポートの出力

```markdown
## バグ調査レポート

### バグ概要
- **報告日**: YYYY-MM-DD
- **優先度**: P[1-4]
- **影響**: [特定ユーザー/全ユーザー] の [機能名]

### 根本原因
[1-2文で根本原因を説明]

### 発生メカニズム
[手順で説明]

### 修正内容
| ファイル | 変更内容 |
|:---|:---|
| `src/xxx.ts` | [変更説明] |

### テスト追加
- [追加したテストケース名]

### 再発防止
[同様の問題を防ぐための推奨事項]
```

### 7d. 類似バグの確認

同じパターンの問題が他の箇所に潜んでいないか確認する:

| 確認項目 | 手順 |
|:---|:---|
| 類似コードパターン | 修正前のコードパターンを Grep で検索 |
| 関連モジュール | 同じモジュール内の類似処理を確認 |
| 同一開発者の PR | 同時期に追加されたコードを確認 |

**チェックリスト**:
- [ ] 最小再現手順でバグが解消されたことを確認した
- [ ] 関連する正常系の動作が維持されていることを確認した
- [ ] 回帰テストを追加した（テスト名にバグ概要を含む）
- [ ] バグ調査レポートを出力した
- [ ] 類似パターンを他の箇所で確認した
- [ ] バグ調査レポートに PII が含まれていないことを確認した

### 📋 Review Gate 7: 最終成果物の総合レビュー

**review スキルに以下の観点で最終レビューを依頼し、通過してからクローズする。**

| レビュー観点 | review スキル基準 | 確認内容 |
|:---|:---|:---|
| バグ調査レポートの品質 | A-1〜A-4（ドキュメントレビュー全基準） | レポートの完全性・整合性・数値妥当性・可読性 |
| 修正コードの最終確認 | B-1〜B-6（技術仕様レビュー全基準） | 修正コードとテストの総合的な品質確認 |
| プロセスの一貫性 | A-2（章間整合性） | 各 Step の出力が一貫しているか（根本原因→修正方針→修正内容の整合性） |
| PII 保護 | B-4（Privacy Violation） | 全成果物（レポート・コード・テスト）に機密情報が含まれていないか |

**通過条件**: ドキュメント基準（A-1〜A-4）および技術基準（B-1〜B-6）の全チェックリストをパス。Critical / Major 指摘がゼロ。

**不合格時**: 指摘内容に応じて該当 Step に戻り修正。

## Examples

### Example 1: 「保存ボタンを押すと画面が白くなる」

```
「プロフィール編集画面で保存ボタンを押すと画面が真っ白になる」

→ Step 1: STAR 形式に構造化。Trigger=保存ボタン押下、Actual=画面白画面、P2 判定
→ Gate 1: review → 構造化品質 OK。PII なし。通過
→ Step 2: 開発環境で再現。アバター画像変更後のみ発生と特定
→ Gate 2: review → 再現条件の網羅性 OK。通過
→ Step 3: 症状=画面白画面 → フロントエンドの未処理例外が最有力
          仮説ツリー: A) JS 例外 (A-1: null参照, A-2: 非同期エラー)
→ Gate 3: review → 仮説に CSS/レンダリング系の仮説漏れを指摘 → 追加して再通過
→ Step 4: コンソールに "Cannot read properties of null (reading 'url')" を発見
          src/components/Profile.tsx L87: `avatar.url` が null のとき例外
→ Gate 4: review → 証拠（ログ+コード）十分。3条件充足。通過
→ Step 5: Null ガード追加。変更は1箇所、後退リスク低
→ Gate 5: review → 修正方針が根本原因に対応。通過
→ Step 6: `avatar?.url ?? ''` に修正。既存テスト全通過
→ Gate 6: review → B-1〜B-6 全パス。通過
→ Step 7: 再現手順でバグ解消確認。テスト「アバターなし状態での保存」を追加
→ Gate 7: review → レポート品質・コード品質ともに OK。クローズ承認
```

### Example 2: 「支払いが二重請求された」（P1 対応）

```
「昨日の購入で同じ金額が2回引き落とされた」

→ Step 1: P1（決済障害）判定 → Step 4 に直行
→ Step 4: payments テーブルに同一 order_id で2レコード確認
          Stripe webhook が2回届き、べき等キーが機能していないと判明
          POST /webhook で冪等性チェックなしに処理していた（L234）
→ Step 5: Stripe の `stripe-signature` で重複チェックを追加
→ Step 6: webhook 受信時に processed_events テーブルで重複確認を実装
→ Step 7: 二重 webhook をシミュレートしてテスト。影響ユーザーへの返金対応を別途確認
```

### Example 3: 「再現できないが本番のみエラーになる」

```
「本番環境のみ、まれに注文確定で 500 エラーになる」

→ Step 2: 開発環境では再現不可。本番ログを調査する戦略に切り替え
→ Step 3: 間欠的エラー → 競合状態 / タイミング問題を最有力仮説に
→ Step 4: 本番ログに「DeadlockException」を発見
          在庫テーブルを複数トランザクションが同時に更新する設計が原因
→ Step 5: SELECT FOR UPDATE でロック順序を統一する方針
→ Step 6: トランザクションのロック取得順序を一元化
→ Step 7: 負荷テストで DeadlockException が解消されたことを確認
```

### Example 4: 「ログインできないユーザーがいる」

```
「特定のユーザーだけログインできないと連絡があった」

→ Step 1: 影響=特定ユーザーのみ、P2 判定
→ Step 2: 該当ユーザーの ID でログインを試みる → 403 エラー
→ Step 3: 認証・認可の問題が最有力
→ Step 4: DB でユーザーのロールを確認 → is_active=false になっている
          管理画面の「一括更新」処理のバグで誤って非アクティブ化された
→ Step 5: 一括更新の WHERE 条件の誤りを修正。影響ユーザーのデータも復旧
→ Step 6: WHERE 句のバグを修正。管理画面の一括処理にドライランモードを追加
→ Step 7: 該当ユーザーのログインが復旧。同様の被害ユーザーを全件確認
```

### Example 5: 「検索結果が出ない」（エラーなし）

```
「商品名で検索しても結果が一件も出ない。先週まで使えていた」

→ Step 1: エラーなし、サイレント失敗のパターン。先週から変化 → git log で差分確認
→ Step 2: 任意のキーワードで再現確認。全ての検索が0件返却
→ Step 3: サイレント失敗 → インデックス破損 / クエリのバグが最有力
→ Step 4: git log で Elasticsearch のインデックス設定を変更したコミットを発見
          `keyword` フィールドが `text` に変更され、完全一致検索のみになっていた
→ Step 5: インデックス設定を元に戻し、再インデックスを実施
→ Step 6: マッピング設定を修正し、インデックス再構築スクリプトを実行
→ Step 7: 各種キーワードで検索が正常動作することを確認。変更レビューフローを改善
```

### Example 6: 「ファイルアップロードが時々失敗する」

```
「CSVをアップロードすると、時々エラーになるが再試行すると成功する」

→ Step 1: 間欠的発生、P3 判定（回避策あり）
→ Step 2: 大きなファイル（5MB以上）で高確率で再現
→ Step 3: タイムアウト / メモリ制限が最有力
→ Step 4: ファイルサイズに応じてレスポンスが遅延。Nginx のタイムアウト 30 秒を超過
→ Step 5: 非同期処理（バックグラウンドジョブ）へ切り替える方針
→ Step 6: アップロード受付 → 即レスポンス → バックグラウンドで処理の非同期化を実装
→ Step 7: 10MB ファイルで安定動作を確認。進捗ポーリング用のエンドポイントも追加
```

## Troubleshooting

| 問題 | 原因 | 解決策 |
|:---|:---|:---|
| バグが再現できない | 条件が絞り込めていない | Step 2b の変数マトリクスで条件を系統的に変えながら試す |
| 仮説が多すぎて絞れない | 症状の情報が不足している | ログをより詳細なレベルに変更して追加情報を収集する |
| 根本原因がコードに見つからない | インフラ・設定・データの問題 | DB データ、設定ファイル、外部サービスの状態を確認する |
| 修正しても症状が変わらない | 本当の根本原因が別にある | 仮説ツリーに戻り、2位の仮説から調査をやり直す |
| 修正で別のバグが発生した | 影響範囲の確認が不十分 | git diff で変更範囲を確認し、影響する機能のテストを実行する |
| テストが書けない | 依存が多く単体テストが困難 | モック/スタブで依存を分離する。test スキルに委譲する |
| 本番のみ発生、開発では再現不可 | 環境差分がある | 設定値、シークレット、データ量の差分を比較する |
| 間欠的に発生し捕捉できない | 競合状態・外部依存の不安定性 | ログに相関 ID を追加して特定セッションを追跡する |
| データ修正が必要で作業が怖い | データへの影響が未知 | トランザクション内でドライラン → 確認後にコミット |
| バグレポートが曖昧すぎる | ユーザーが技術に不慣れ | スクリーンショット取得 / ブラウザコンソール確認を依頼する |
| P1 対応中に根本原因が特定できない | 時間的プレッシャー | 暫定対処（フィーチャーフラグで無効化等）で影響を止めてから調査する |
| 類似バグが多数見つかった | コードベース全体の設計問題 | 個別修正後、パターンを抽出してリファクタリング Issue を起票する |
| Review Gate で同じ指摘が繰り返される | 前 Step の出力品質が根本的に低い | 該当 Step の入力（前 Step の成果物）を見直し、必要なら前の Gate まで戻る |
| Review Gate で仮説の漏れを指摘された | 症状カテゴリの判定が狭い | Step 3a の症状パターン表を再確認し、見落としたカテゴリを網羅的に追加する |
| Gate 4 で証拠不十分と指摘された | ログ・コード証拠が不足 | Step 4a で追加の調査アプローチ（ログ逆引き、データフロー追跡等）を組み合わせる |
| P1 対応で全 Gate を通る時間がない | 緊急度と品質のトレードオフ | Gate 1〜3 は簡易通過（Major 以上のみ確認）、Gate 4〜7 は通常通り実施する |

| **implementation-flow** | リダイレクト / エスカレーション | Phase 0c Q1 で `bug-fix` と判定された要求は本スキルが正。Step 5 で設計変更必要時 → implementation-flow Lite `extend` / `modify-breaking` へエスカレーション（[work-type-routing.md](../implementation-flow/references/work-type-routing.md) 参照） |
| **distill** | 前工程 | バグ報告が大量のログや仕様書を含む場合、distill で重要な仕様・ドメインルールを蒸留してから Step 3 の仮説ツリー構築に活用する |
