# リバースエンジニアリング チェックリスト

> コードから仕様を起こす際に見落としやすいポイントを体系化したチェックリスト。各 Step の完了時に該当セクションを確認する。

---

## 全般チェック（全 Step 共通）

| # | チェック項目 | 見落としリスク |
|:---|:---|:---|
| G-1 | 【推定】マークを適切に付与しているか | コードの意図を断定し、誤った仕様書になる |
| G-2 | 【要確認】マークを適切に付与しているか | 不明点を放置し、仕様書の信頼性が低下する |
| G-3 | ファイル:行番号の参照を記載しているか | 仕様書とコードの紐付けが失われる |
| G-4 | コメントの記述を鵜呑みにしていないか | 古いコメントと実装が乖離していることが多い |
| G-5 | テストコードも解析対象に含めているか | テストは暗黙の仕様書（expect/assert が期待動作を定義） |

---

## Step 1: リポジトリ概況スキャン

| # | チェック項目 | よくある見落とし |
|:---|:---|:---|
| S1-1 | `.gitignore` で除外されるべきファイルが追跡されていないか | `.env` がコミットされている場合、シークレット漏洩 |
| S1-2 | サブモジュール（`git submodule`）の存在を確認したか | `.gitmodules` を見落とすと依存が不完全に |
| S1-3 | ビルドツール（Webpack/esbuild/SWC）の設定を確認したか | エイリアス（`@/`）がパス解決に影響 |
| S1-4 | プロジェクトの IDE 設定（`.vscode/`, `.idea/`）を確認したか | デバッグ設定からエントリーポイントが判明する |
| S1-5 | `scripts` フィールド（package.json）を確認したか | ビルド・テスト・デプロイのコマンドが定義されている |

---

## Step 2: エントリーポイント・依存関係

| # | チェック項目 | よくある見落とし |
|:---|:---|:---|
| S2-1 | `devDependencies` と `dependencies` を区別しているか | 本番に不要な依存を仕様書に含めてしまう |
| S2-2 | `peerDependencies` を確認したか | 暗黙の前提となる依存が漏れる |
| S2-3 | モンキーパッチ/プロトタイプ拡張がないか | 標準 API の振る舞いが変更されている可能性 |
| S2-4 | 動的 import（`import()`）を検索したか | 静的解析では見えないモジュール依存 |
| S2-5 | ワーカー（Web Worker, Worker Thread）の存在を確認したか | 並列処理が仕様に影響する |

---

## Step 3: アーキテクチャ

| # | チェック項目 | よくある見落とし |
|:---|:---|:---|
| S3-1 | レイヤー間の依存方向が単方向か確認したか | 逆方向依存はアーキテクチャ違反（仕様書に記録すべき） |
| S3-2 | Event Emitter / Message Queue の使用を確認したか | 非同期・イベント駆動のデータフローが見えない |
| S3-3 | WebSocket / SSE の使用を確認したか | HTTP 以外の通信プロトコルが仕様に影響 |
| S3-4 | 外部サービスとの連携（API 呼び出し）を全て特定したか | 外部依存が仕様書から漏れる |
| S3-5 | キャッシュ戦略（Redis, in-memory）を確認したか | キャッシュが仕様に影響する（TTL, 更新タイミング等） |

---

## Step 4: API 境界

| # | チェック項目 | よくある見落とし |
|:---|:---|:---|
| S4-1 | 内部 API（マイクロサービス間通信）も文書化したか | 外部 API のみに集中しがち |
| S4-2 | ファイルアップロード/ダウンロードのエンドポイントを確認したか | multipart/form-data 処理は見落としやすい |
| S4-3 | レート制限の実装を確認したか | ミドルウェアで設定されていることが多い |
| S4-4 | CORS 設定を確認したか | セキュリティ仕様に影響 |
| S4-5 | API バージョニング戦略を確認したか | `/v1/`, `/v2/` の分岐や Header バージョニング |
| S4-6 | GraphQL / gRPC の存在を確認したか | REST 以外の API スタイルを見落とす |

---

## Step 5: データモデル

| # | チェック項目 | よくある見落とし |
|:---|:---|:---|
| S5-1 | ソフトデリート（`deleted_at`）パターンを確認したか | 実際には削除されないデータがある |
| S5-2 | 楽観ロック（`version` / `updated_at`）を確認したか | 並行更新制御の仕様 |
| S5-3 | JSON/JSONB カラムの内部構造を確認したか | スキーマレスなデータが仕様から漏れる |
| S5-4 | Enum 型の値を全て列挙したか | ステータス値が不完全になる |
| S5-5 | 複合インデックスを確認したか | パフォーマンスに影響する設計判断 |
| S5-6 | DB トリガー/ストアドプロシージャの存在を確認したか | コードに現れない DB 側ロジック |

---

## Step 6: ビジネスロジック

| # | チェック項目 | よくある見落とし |
|:---|:---|:---|
| S6-1 | 例外処理のパターンを確認したか | カスタム例外クラスにビジネスルールが含まれる |
| S6-2 | Cron ジョブ/スケジュールタスクを確認したか | 定期実行されるビジネスロジック |
| S6-3 | メール/通知送信のトリガー条件を確認したか | 副作用としての通知ロジック |
| S6-4 | 権限制御（RBAC/ABAC）のルールを全て抽出したか | 認可ロジックはビジネスルールの重要部分 |
| S6-5 | トランザクション境界を確認したか | データ整合性に関わる重要な設計判断 |
| S6-6 | Feature Flag の使用を確認したか | 条件分岐に隠れた機能の ON/OFF |

---

## Step 7: 設定・デプロイメント

| # | チェック項目 | よくある見落とし |
|:---|:---|:---|
| S7-1 | 環境別の設定差分を確認したか | dev/staging/prod で異なる設定値 |
| S7-2 | シークレット管理方法を確認したか | Vault, AWS Secrets Manager 等の外部管理 |
| S7-3 | ヘルスチェックエンドポイントを確認したか | 運用に必要な `/health`, `/ready` |
| S7-4 | ログ出力の設定を確認したか | ログレベル、フォーマット、出力先 |
| S7-5 | メトリクス/トレーシング設定を確認したか | Prometheus, OpenTelemetry 等の計装 |

## 最終チェック（Step 8）

| # | チェック項目 | 見落とし時の影響 |
|:---|:---|:---|
| F-1 | 全 Mermaid 図が正しく描画されるか | 構文エラーで図が表示されない |
| F-2 | 仕様書間のリンクが全て有効か | 404 リンクでナビゲーション不能 |
| F-3 | 【推定】マークの総数を集計したか | 信頼度が不明なまま引き渡してしまう |
| F-4 | 【要確認】マークの確認担当者を提案したか | 確認が放置される |
| F-5 | コード変更時の仕様書更新方針を提案したか | 仕様書が再び陳腐化する |
