# Skill: Req Elicit（曖昧な要求から要件定義への橋渡し）

> **曖昧な要求を言葉の鉱脈とみなし、要件という純金を掘り出せ**

## Instructions

### ワークフロー内の位置

```
曖昧な要求・要望（自然言語）
  ↓
[req-elicit]
  ├─ Step 1: 要求の受領と本質分析
  ├─ Step 2: 主要な不明点の特定
  ├─ Step 3: 機能要件の質問生成
  ├─ Step 4: 非機能要件の質問生成
  ├─ Step 5: データ・連携要件の質問生成
  ├─ Step 6: 制約・ビジネス観点の質問生成
  └─ Step 7: 優先度付けと構造化出力
  ↓
優先度 S/A/B 分類の質問リスト（Markdown）
  ↓
ヒアリング実施 → story-map / distill へ
```

### 入力

| 入力 | 説明 | 例 |
|:---|:---|:---|
| 要求テキスト | 曖昧な要求・要望（1文〜数段落） | 「ユーザー管理機能を追加したい」 |
| ドメインヒント（任意） | システムカテゴリや業種 | 「医療系 SaaS」「社内ツール」 |
| ステークホルダー情報（任意） | 質問の受け手が誰か | 「非エンジニアのクライアント」 |
| 既知の制約（任意） | わかっている前提条件 | 「AWS 環境・React 使用」 |

### 出力

| 出力 | 形式 | 説明 |
|:---|:---|:---|
| 要求の解釈 | テキスト（1〜2文） | 要求の本質を言語化 |
| 主要な不明点 | 箇条書き（3〜5点） | 要件定義を阻む最大の曖昧点 |
| 質問リスト | Markdown（優先度・カテゴリ別） | S（最重要）/ A（重要）/ B（確認）の 3 段階 |

---

## Step 1: 要求の受領と本質分析

要求テキストを受け取り、「誰が・何のために・何を」の核心を掴む。
この分析が質問の精度を左右する — ドメインを誤認識すると的外れな質問を量産する。

### 1a. ドメイン・システムカテゴリの特定

要求テキストのキーワードからシステムカテゴリを推定する:

| カテゴリ | 典型キーワード | 固有リスク |
|:---|:---|:---|
| **Web アプリ** | サイト、管理画面、ダッシュボード | SEO・レスポンシブ・ブラウザ互換 |
| **モバイルアプリ** | アプリ、スマホ、プッシュ通知 | iOS/Android 分岐・オフライン対応 |
| **AI / ML** | チャットボット、自動化、予測、推薦 | 精度・ハルシネーション・学習データ |
| **データ基盤** | 集計、レポート、BI、分析 | データソース・鮮度・権限管理 |
| **業務システム** | 管理、発注、在庫、勤怠、会計 | 法規制・監査ログ・既存システム連携 |
| **社内ツール** | 社内、Slack、Notion、自動化 | 利用者数・認証（SSO）・管理コスト |
| **API / バックエンド** | API、連携、webhooks、SDK | レート制限・バージョニング・認証 |

詳細は [domain-risks.md](references/domain-risks.md) 参照。

### 1b. アクター（利用者）の仮説

| 確認軸 | 質問 |
|:---|:---|
| **主アクター** | 誰が日常的に使うか？（内部ユーザー/外部顧客/管理者） |
| **二次アクター** | システムに接触する他のロールは？（閲覧者/承認者/外部連携先） |
| **利用規模** | 同時利用者数のオーダー（〜10人/〜1000人/〜100万人） |
| **技術リテラシー** | 利用者はエンジニアか、非エンジニアか |

### 1c. ビジネス価値の核心抽出

要求の「なぜ」を 1 文で表現する:
- 「〇〇という課題を解決するために、〜を実現するシステム」
- これが後続ステップで質問の優先度を決める基準になる

**チェックリスト**:
- [ ] ドメイン/システムカテゴリを 1 つ特定した
- [ ] 主アクターを特定した（「誰が使うか」）
- [ ] ビジネス価値の核心を 1 文で言語化した
- [ ] 要求が複数システムにまたがる場合はスコープ境界を仮設定した

## Step 2: 主要な不明点の特定

「答えなければ要件定義が先に進まない」最重大な曖昧点を 3〜5 点絞り込む。
この不明点が **優先度 S の質問** の直接の原料となる。

### 2a. 不明点の発見パターン

| パターン | 例 | 対応する優先度 S 質問 |
|:---|:---|:---|
| **スコープ境界未定** | 「ユーザー管理」＝どこまで？ | 「どの機能がフェーズ1の必須で、どれが任意ですか？」 |
| **ステークホルダー不明** | 誰が承認者か不明 | 「この機能の最終決定権を持つのは誰ですか？」 |
| **成功基準未定義** | 「便利にしたい」の定量化 | 「どうなれば成功と判断しますか？指標はありますか？」 |
| **既存システム連携不明** | 「連携したい」の対象不明 | 「現在使っているシステム・ツールのリストを教えてください」 |
| **ビジネスルール未言語化** | 承認フローや計算ロジック | 「〇〇の条件は具体的にどのように決まりますか？」 |

### 2b. ドメイン固有の不明点チェック

[domain-risks.md](references/domain-risks.md) の対象ドメインセクションを参照し、
見落としやすい不明点を追加する。

**チェックリスト**:
- [ ] 「これがわからないと設計が始まらない」不明点を 3 点以上特定した
- [ ] スコープ境界の不明点を確認した
- [ ] ビジネスルールの不明点を確認した
- [ ] ステークホルダー・意思決定者の不明点を確認した

---

## Step 3: 機能要件の質問生成

「誰が・何を・いつ・どのように使うか」を網羅する質問を生成する。
ユースケース軸で考え、**主要フロー → 代替フロー → 例外フロー** の順で掘り下げる。

### 3a. 機能要件の質問フレーム

| 軸 | 質問のフォーカス | 例 |
|:---|:---|:---|
| **WHO** | どの役割が・どの権限で操作するか | 「管理者と一般ユーザーで機能が違いますか？」 |
| **WHAT** | どのアクション・操作が必要か | 「登録・参照・更新・削除のうちどれが必要ですか？」 |
| **WHEN** | いつ・どのタイミングで使うか | 「リアルタイムですか？バッチ処理でも構いませんか？」 |
| **HOW** | どのような操作フロー・画面遷移か | 「手動入力ですか？ファイルインポートも必要ですか？」 |
| **EXCEPTION** | エラー・失敗時はどう扱うか | 「失敗した場合のロールバックは必要ですか？」 |
| **NOTIFICATION** | 誰に・何を・いつ通知するか | 「完了時に通知は必要ですか？メール・プッシュどちらですか？」 |

### 3b. 典型的な機能要件の質問セット

詳細なカテゴリ別質問カタログは [question-catalog.md](references/question-catalog.md) 参照。

**チェックリスト**:
- [ ] 主要なユースケース（正常フロー）をカバーした
- [ ] 権限・ロール分岐の質問を含めた
- [ ] 例外・エラー処理の質問を含めた
- [ ] 通知・アラートの質問を含めた
- [ ] 生成した質問が具体的で回答可能か確認した（「何が重要ですか？」のような抽象質問は削除）

---

## Step 4: 非機能要件の質問生成

「-ility 軸」で機能以外の品質要件を引き出す。
非機能要件の未定義は技術的負債の温床 — 後から変更コストが跳ね上がる。

### 4a. -ility 軸の質問フレーム

| 品質属性 | 核心質問 | 見落としやすい盲点 |
|:---|:---|:---|
| **性能** | 何件/秒・何秒以内のレスポンスが必要か | ピーク時と平常時の差 |
| **可用性** | ダウンタイム許容は？SLA は？ | 夜間メンテナンス窓の有無 |
| **スケーラビリティ** | 利用者・データ量の成長見込み | 3年後・5年後の規模 |
| **セキュリティ** | 個人情報・機密データを扱うか | 法規制（GDPR・個人情報保護法・HIPAA） |
| **アクセシビリティ** | 障害者・高齢者への対応要件は？ | 社内ポリシー・法的義務 |
| **保守性** | 誰が・どのくらいの頻度でメンテするか | 内製 vs 外注・ドキュメント要件 |
| **多言語対応** | 日本語のみ？多言語対応が必要か | i18n 対応のコスト |

**チェックリスト**:
- [ ] 性能要件（レスポンス時間・スループット）の質問を含めた
- [ ] 可用性・SLA の質問を含めた
- [ ] セキュリティ要件（認証・認可・暗号化・個人情報）の質問を含めた
- [ ] スケーラビリティの質問を含めた
- [ ] ドメイン固有の法規制 ([domain-risks.md](references/domain-risks.md)) を確認した

---

## Step 5: データ・連携要件の質問生成

データはシステムの血液 — 入出力・保存・連携の設計不備は後で致命的になる。

### 5a. データ要件の質問フレーム

| 軸 | 質問のフォーカス |
|:---|:---|
| **入力データ** | どこから・どのような形式で・どの頻度でデータが来るか |
| **出力データ** | 何を・誰に・どの形式で出力するか（CSV/API/PDF/画面） |
| **保存・保持** | データの保持期間・削除ポリシー・バックアップ要件 |
| **マスタデータ** | 商品・ユーザー・組織のマスタはどこが主管か |
| **外部連携** | どのシステム・サービスと連携するか（API/CSV/DB直接） |
| **マイグレーション** | 既存データの移行は必要か・データ量はどのくらいか |

### 5b. 連携要件の確認

| 連携タイプ | 確認事項 |
|:---|:---|
| **外部 API 連携** | 認証方式・レート制限・エラー時のリトライ・サンドボックスの有無 |
| **DB 連携** | 既存 DB のスキーマ・アクセス権限・マスタ管理の主管 |
| **ファイル連携** | CSV/Excel の形式仕様・文字コード・ヘッダー有無 |
| **認証連携** | SSO（SAML/OIDC）・既存 IdP の有無 |

**チェックリスト**:
- [ ] データの入力元と形式を確認する質問を含めた
- [ ] データの出力先・形式を確認する質問を含めた
- [ ] 外部システム連携の有無を確認する質問を含めた
- [ ] データ移行（マイグレーション）の有無を確認する質問を含めた
- [ ] データ保持期間・削除ポリシーの質問を含めた

---

## Step 6: 制約・ビジネス観点の質問生成

技術選定・予算・期日・組織体制など、開発の自由度を制約する条件を引き出す。
これらの制約が未定義だと、「理想的な設計」と「実際の要件」が乖離する。

### 6a. 制約の質問フレーム

| 制約種別 | 核心質問 |
|:---|:---|
| **技術制約** | 使用必須の技術スタック・クラウド・言語はあるか |
| **予算制約** | 初期開発コストと月額ランニングコストの上限は？ |
| **期日制約** | リリース期日はあるか・フェーズ分けは可能か |
| **組織制約** | 開発チームの規模・スキルセット・内製 vs 外注 |
| **既存資産** | 流用できる既存コード・インフラ・ライセンスはあるか |
| **コンプライアンス** | 業界規制・セキュリティポリシー・監査要件はあるか |

### 6b. 将来性・拡張性の質問フレーム

| 観点 | 質問 |
|:---|:---|
| **フェーズ計画** | フェーズ 2 以降に追加予定の機能はあるか |
| **スケール予測** | 3〜5 年後の利用者数・データ量の見込みは？ |
| **運用体制** | リリース後の運用・保守は誰が担うか（内製/外注） |

**チェックリスト**:
- [ ] 技術スタック制約の質問を含めた
- [ ] 予算・コスト制約の質問を含めた
- [ ] 期日・フェーズ分けの質問を含めた
- [ ] 将来の拡張・スケールに関する質問を含めた
- [ ] コンプライアンス・法規制の質問を含めた（ドメイン固有リスク参照）

## Step 7: 優先度付けと構造化出力

Step 1〜6 で生成した質問群を整理・重複排除し、優先度 S/A/B で分類して出力する。

### 7a. 優先度判定基準

[priority-framework.md](references/priority-framework.md) の全基準を適用する。

| 優先度 | 判定基準 | 典型的な質問数 |
|:---|:---|:---|
| **S（最重要）** | この回答がなければ設計の方向性が決まらない | 3〜5 問 |
| **A（重要）** | 基本設計・技術選定に直接影響する | 15〜25 問 |
| **B（確認）** | あれば品質が上がるが、後でも回答可能 | 5〜10 問 |

### 7b. 質問の品質チェック

各質問が以下の基準を満たすか確認する:

| チェック | 基準 | NG 例 |
|:---|:---|:---|
| **具体性** | 回答者が迷わず答えられる | 「重要なことは何ですか？」 |
| **単一焦点** | 1 問に 1 つの質問のみ | 「予算と期日と担当者は？」（複合質問） |
| **非誘導** | 特定の回答に誘導しない | 「React を使いますよね？」 |
| **層別** | ビジネス層・ロジック層・データ層を混在させない | 機能要件に DB スキーマを聞く |

### 7c. 最終出力フォーマット

```markdown
## 要求の解釈
[1〜2文で要求の本質を言語化]

## 前分析で発見した主な不明点
- 不明点1: [具体的に]
- 不明点2: [具体的に]
- 不明点3: [具体的に]

## 質問リスト

### 優先度 S（最重要 — 先に回答が必要）
1. [質問] ← *[なぜ最重要か：1行]*
2. ...

### 優先度 A — 機能要件
1. [質問]
...

### 優先度 A — 非機能要件
1. [質問]
...

### 優先度 A — データ要件
1. [質問]
...

### 優先度 B — 制約・前提
1. [質問]
...

### 優先度 B — 将来性・拡張性
1. [質問]
...
```

**チェックリスト**:
- [ ] 優先度 S が 3〜5 問に絞られている（多すぎない）
- [ ] 優先度 A が機能・非機能・データの 3 サブカテゴリに分類されている
- [ ] 重複・類似質問を統合した
- [ ] 各質問が具体的で回答可能（抽象質問を排除した）
- [ ] ドメイン固有の質問（[question-catalog.md](references/question-catalog.md) 参照）を含めた
- [ ] 要求の解釈と主要な不明点のサマリーを含めた

## Examples

### Example 1: EC サイト「カート機能を追加したい」

```
「EC サイトにカート機能を追加したい」

→ Step 1: ドメイン = Web アプリ（EC）、アクター = 購入者/管理者
→ Step 2: 不明点 — ゲスト購入可否・決済連携先・在庫リアルタイム性
→ Step 3: 機能 — 商品追加/削除・数量変更・クーポン適用・お気に入り保存
→ Step 4: 非機能 — ピーク時（セール時）の性能・決済失敗時の補償
→ Step 5: データ — 商品マスタの連携元・カート保存期間・注文履歴の保持期間
→ Step 6: 制約 — 決済代行業者の指定・PCI DSS 準拠要否・リリース期日
→ Step 7: 優先度 S = 「ゲスト購入を許可するか？」「決済手段は何を使うか？」
```

### Example 2: 「チャットボットが欲しい」

```
「社内向けにチャットボットが欲しい」

→ Step 1: ドメイン = 社内ツール + AI、アクター = 社員全員
→ Step 2: 不明点 — AI 型かルール型か・対応領域（HR/IT/業務）・回答不能時の扱い
→ Step 3: 機能 — FAQモード・フリーテキストモード・エスカレーション先・管理画面
→ Step 4: 非機能 — 社内機密情報の外部送信可否・ログ保存要件
→ Step 5: データ — ナレッジベースのソース（Confluence/Drive）・更新頻度
→ Step 6: 制約 — LLM ベンダー選定（Azure/AWS/オンプレ）・セキュリティポリシー
→ Step 7: 優先度 S = 「社内機密データを LLM に送信してよいか？」「対応する業務領域はどこか？」
```

### Example 3: 「ユーザー管理機能を作りたい」

```
「管理画面にユーザー管理機能を追加したい」

→ Step 1: ドメイン = Web アプリ（業務システム）、アクター = 管理者/一般ユーザー
→ Step 2: 不明点 — ロールの種類・招待フロー・既存 IdP との SSO
→ Step 3: 機能 — 招待・CRUD・ロール付与・アカウント無効化・パスワードリセット
→ Step 4: 非機能 — 監査ログ（誰が何をいつ変更したか）・セッション管理
→ Step 5: データ — 既存ユーザーデータのインポート・他サービスとのユーザー同期
→ Step 6: 制約 — SSO 連携先（Google/Microsoft/SAML）・GDPR 対応要否
→ Step 7: 優先度 S = 「SSO は必要か？どの IdP と連携するか？」「ロールは何種類か？」
```

### Example 4: 「売上レポートを自動化したい」

```
「毎月手作業でやっている売上レポートを自動化したい」

→ Step 1: ドメイン = データ基盤/業務自動化、アクター = 営業/経営層/経理
→ Step 2: 不明点 — データソース・集計ロジックの定義・配信先と形式
→ Step 3: 機能 — 集計粒度（日次/週次/月次）・ドリルダウン・フィルタ・エクスポート
→ Step 4: 非機能 — データの鮮度（リアルタイム vs バッチ）・アクセス権限
→ Step 5: データ — 売上データのソース（RDB/Salesforce/CSV）・マスタ連携
→ Step 6: 制約 — BI ツールの指定（Tableau/Power BI/Looker）・既存 ETL パイプライン
→ Step 7: 優先度 S = 「現在どこからデータを取得しているか？」「集計のビジネスロジック（定義）は文書化されているか？」
```

### Example 5: 「在庫管理システムを作りたい」

```
「複数倉庫の在庫管理システムを作りたい」

→ Step 1: ドメイン = 業務システム、アクター = 倉庫担当/発注担当/経営層
→ Step 2: 不明点 — 倉庫数・ERP 連携・リアルタイム在庫 vs バッチ更新
→ Step 3: 機能 — 入庫・出庫・棚卸し・発注点アラート・ロット管理
→ Step 4: 非機能 — バーコード/QR スキャン対応・オフライン動作（倉庫内の電波）
→ Step 5: データ — ERP（SAP/freee）との双方向連携・商品マスタの主管システム
→ Step 6: 制約 — ハンディターミナルの機種指定・既存 WMS の有無・期日
→ Step 7: 優先度 S = 「ERP との連携は双方向か一方向か？」「在庫数はリアルタイムで必要か？」
```

### Example 6: 「ダッシュボードが欲しい」

```
「経営ダッシュボードを作って経営陣が毎朝見られるようにしたい」

→ Step 1: ドメイン = データ基盤/BI、アクター = 経営層（非エンジニア）
→ Step 2: 不明点 — KPI の定義・データソース・更新タイミング
→ Step 3: 機能 — 表示 KPI（売上・利用者数・等）・期間フィルタ・アラート通知
→ Step 4: 非機能 — モバイル対応・表示速度（毎朝の更新前に見る）
→ Step 5: データ — 複数データソース（GA/Salesforce/自社 DB）の統合
→ Step 6: 制約 — 閲覧端末（PC/タブレット/スマホ）・BI ツール or カスタム開発
→ Step 7: 優先度 S = 「最も重要な KPI は何か？5つ以内で絞ってください」「データの更新は何時が必要ですか？」
```

### Example 7: 「通知機能を追加して」

```
「アプリにプッシュ通知機能を追加したい」

→ Step 1: ドメイン = モバイルアプリ、アクター = アプリユーザー/管理者
→ Step 2: 不明点 — 通知トリガーの種類・iOS/Android 分岐・配信基盤
→ Step 3: 機能 — イベント駆動通知・定期通知・セグメント配信・受信設定
→ Step 4: 非機能 — 配信遅延の許容・大量配信時のスロットリング
→ Step 5: データ — 通知ログ保存期間・既存ユーザーデータとの紐付け
→ Step 6: 制約 — 通知配信基盤（FCM/APNs/既存 SaaS）・GDPRオプトアウト要件
→ Step 7: 優先度 S = 「どのイベントで通知を送るか？（リスト化してください）」「iOS と Android 両方が必須か？」
```

## Troubleshooting

| 問題 | 原因 | 解決策 |
|:---|:---|:---|
| 要求が1単語しかない（例:「在庫」） | 要求テキストが不十分 | 「もう少し教えてください。どのような課題を解決したいですか？」と確認してから生成する |
| 生成した質問が抽象的すぎる | ドメイン分析が不十分 | Step 1 に戻りカテゴリを再特定。[question-catalog.md](references/question-catalog.md) の具体例を参照 |
| 優先度 S の質問が 10 問以上になる | 絞り込み不足 | 「この回答がなければ設計が始まらない」の基準で 3〜5 問に再絞り込み |
| 機能要件と非機能要件の質問が混在する | カテゴリ分類の混乱 | 機能 = 「何ができるか」、非機能 = 「どの品質で動くか」で再分類 |
| 技術実装の質問が混入している | BA 視点の逸脱 | フレームワーク・DB スキーマ・クラス設計の質問を削除。それらは回答収集後の工程 |
| ドメイン固有のリスクを見落とした | [domain-risks.md](references/domain-risks.md) の未参照 | 特定したドメインのセクションを参照し、必須確認事項を追加する |
| 質問が重複・類似している | 各ステップで独立して生成したため | Step 7 で重複排除フェーズを明示的に実施 |
| 回答者が非エンジニアで質問が難解 | 専門用語の使用 | 「SLA」→「どのくらいのダウンタイムまで許容できるか」に言い換える |
| 要求が複数システムにまたがっている | スコープ境界が未定 | Step 2 でスコープ境界の確認を優先度 S に追加 |
| 質問が多すぎてヒアリング現場で使えない | 絞り込み不足 | 優先度 S のみ（3〜5問）を最初に提示し、A/B はフォローアップとして別資料化 |
| 同じカテゴリの質問が生成されない | CoT の思考過程が省略された | Step 3〜6 の各軸を順番にチェックし、質問が 3 問未満のカテゴリを補充する |
| 法規制・コンプライアンスの質問が抜ける | domain-risks.md 未参照 | 医療/金融/EC ドメインでは必ず [domain-risks.md](references/domain-risks.md) の規制セクションを確認 |
